## Major

**M1. A route walker sent to a spot beyond a shut gate never gets there, so Jun's ca12 stop still fails about half the time.**
B1 now sends a route walker to the stop through the single-room branch. When that path fails, the branch backs off for 2 s and retries from where he stands (`npc-behavior.js:2355-2363`). It never calls `_approachRouteGate`, which only the route branch uses (`:2523`). A shut gate is not walkable until an `openFor` NPC comes within `openRadius` (`door-gates.js:940-950`), and an inert gate (outside `activeIf`) still stays shut for NPC walkers. For ca12 (plan 1.3, ca12 shell todo line 16), Jun is on the lobby side for the Delphine leg and dwell, roughly half of each loop. If `ca12_world_done` fires then, the `patrolOverride` to his studio desk has no path, and he stands in the lobby, retrying every 2 s. Before the fix he stopped at a route waypoint instead. B1 is resolved for same-side stops; this case, the one the B1 text was about, is still open. The same gap affects any needs or script `goToAndStay` on a route walker through his own gate.
*Fix:* (a) in the single-room branch's no-path `else` (`:2355`), before the back-off: `if (this._stopOnArrival && this._approachRouteGate(pathfindingManager, null)) return;`. (b) At the end of a path (`:1574`), treat the approach like a sidestep so it does not count as arrival: `if (this._stopOnArrival && (this.patrolTarget?.isTemporary || this.patrolTarget?.gateApproach)) { ...same reset... }`. For a `gateApproach` target, keep `waypoints` as they are and reset `waypointIndex` to 0, `patrolTarget` to null, the path, and `_pathRetryAfter` to 0. Then the next choice re-plans to the stop through the now-open gate, and `gateOpened()` (`:2535`) already clears the back-off. Unit test: a route walker with `_stopOnArrival` whose `_planMovePath` answers no path, plus a `doorGates.approachPoint` stub. Assert the next target is the approach spot with `gateApproach`. Reaching it fires no `npc_arrived`. The leg after it plans to the stop. Live proof: `test_gate_tailgate` or `test_side_door_gate`, with a `patrolOverride` on the route walker sent while he is on the far side of the gate.

## Minors

**m1. A `startWhen` that holds while the restart is refused warns every frame.** `_tickStartWhen` (`npc-behavior.js:436`) calls `restartAuthoredPatrol` each tick while `startDeferred` stays true. During a walk-in it is refused (`:846-849`). With no authored patrol (all waypoints dropped by `parseConfig`) it is refused for good (`:840-843`). Both log a `console.warn` each frame. *Fix:* in the tick, `if (b._walk) continue;` before the call; and if the call returns false with no `_walk`, set `b._startWhenBad = true` so it stops.

**m2. `start_patrol` on a patrol that is already running restarts it.** `startPatrol` (`:393-397`) has no guard. `set_global` emits `global_variable_changed` on every call, same value or not (`npc-needs.js:824-826`), so a mapping on that event without `onceOnly` restarts the walker from waypoint 0 and resets the segment each time a script sets the global again, and suspends his needs each time. *Fix:* in `startPatrol`, return false when `!cfg.startDeferred && cfg.enabled && !b._patrolOverridden && !b._stopOnArrival`, matching the `resumePatrol` guard; say so at `apply-actions.js:506-514`.

**m3. A `walkIn`/`walkOut` and a patrol action for the same NPC in one mapping fail silently in practice.** The order is now right, but the walk has just set `_walk`, so the restart is always refused and only a console line says so (the comment at `npc-manager.js:2015` admits it). The same applies to `needs: "resume"` with `resume_patrol`: the restart's `onExternalMove` suspends the needs again straight away. *Fix:* a validator warning when one mapping has `walkIn`/`walkOut` (or `needs: "resume"`) and a `start_patrol`/`resume_patrol` naming the mapping's own NPC; point the author at `startWhen` (which retries after the walk once m1 is in).

**m4. Docs: the reload sentences are true, but they miss the stop half.** The fixer's worry does not hold as written. `apply-actions.js:510-512` and the `startDeferred` schema text (`scenario-schema.json:4858`) say that a `start_patrol` start is not saved and that `startWhen` is the one that survives. That is right. What is missing: (1) a patrol stopped by a `patrolOverride` restarts after a reload whenever `startWhen` still holds, because the override is not saved and an `onceOnly` stop mapping that already fired will not fire again. The condition must go false when the NPC should stand, as Jun's `&& !globalVars.ca12_world_done` does. (2) The `_tickStartWhen` doc (`npc-behavior.js:418`) reads "a start_patrol action has no reload gap to leave", which is garbled. (3) `startDeferred` says only `start_patrol` sets it off.
*Exact fix:*
- `scenario-schema.json:4857` `startWhen` description: `"E4: a global condition (globalVars grammar, utils/global-condition.js) read every tick. Implies startDeferred. The patrol starts the first time it holds, and again after a reload while it still holds. A stop (patrolOverride) is not saved, so write the condition to go false once the NPC should stand (e.g. \"globalVars.go && !globalVars.done\")."`
- `scenario-schema.json:4858` `startDeferred`: replace "until a start_patrol action sets it off (not saved: after a reload it is off again, use startWhen for that)" with "until a start_patrol action or patrol.startWhen sets it off (a start_patrol start is not saved: after a reload it is off again; startWhen is re-read)".
- `npc-behavior.js:417-419`: "Read every manager tick, so after a reload it starts on the first tick once the restored globals satisfy it, which a start_patrol action cannot do. One shot per page load: the restart clears startDeferred. A patrolOverride stop is not saved either, so the condition should turn false when the NPC must stand."
- `apply-actions.js:510-512`: "Neither is saved: after a reload a patrol started by start_patrol is off again, and one restarted by resume_patrol is back on its authored patrol (or off, if deferred). For a start that must survive a reload, author `patrol.startWhen` instead and make it false once the NPC should stand."
- `tmp/handover/ca0/ca12_shell_todo.md:16`: Jun's start is `patrol.startWhen: "globalVars.ca12_runner_go && !globalVars.ca12_world_done"`, not a `start_patrol` mapping.

## New-bug checks (no finding)

- **Per-frame cost.** `_tickStartWhen` loops the behaviours once per manager update. NPCs without `startWhen` hit the first `continue`. The condition is parsed once and cached (`_startWhenFn`), and the tick stops once the patrol starts. This is negligible.
- **Reload.** The globals are restored before the first manager tick (`main.js:19` loads the parser; `window.gameState.globalVariables` is the same source `door-gates.isInert` reads). `global_variable_changed` does not fire on restore, so a `startWhen` NPC and a `start_patrol` mapping on the same global cannot double-start after a reload. In the live session the mapping fires first, clears `startDeferred`, and the tick skips.
- **Existing patrols and needs.** The changes to shared paths are the `_stopOnArrival` guard (only for `multiRoom`), the route-state clear in `goToAndStay` (null for everyone else; nothing outside `npc-behavior.js` reads those fields), and the actions block move (no scenario has a mapping `actions` list). Route walkers today: `test_access_habits` (gary, sara), `test_npc_avoidance`, `test-multiroom-npc`, `test_gate_tailgate`, `test_side_door_gate(_east_start)`, and `lab_physical_pentest` (len). None has needs, a walk-in or walk-out, or a `patrolOverride`. m02 and `test_needs_sims` have no route walker, so their behaviour does not change. A conversation walk-home (`npc-manager.js:2360`) on a route walker now walks home instead of to the next route waypoint. It stops either way, as before.
- **E1 M2 walk-in approach leg** (`npc-walk.js:447-467`). It mirrors the closed-door approach directly below it: owner `walk`, `silentArrival`, and `onArrive` re-issues the through leg unless the walk is done. `approachPoint` returns null inside `openRadius`, for a gate that is already open, and for a non-`openFor` walker, so a re-issued `goTo` after a stall goes straight through. A gate held against a barred player leaves the walker at the door until the walk's `timeoutMs`, which matches `turnBackFromGate` (walkers never turn back). It does not interact with the E1 door-gate and door fixes from `244915830` on: those change what the player and inert clicks do and how a corridor is unmarked, and the NPC side of an inert gate is still `openFor`-only. `door-gates-r1-fixes`, `door-gates-r2-fixes` and `npc-walk-gate` all pass.

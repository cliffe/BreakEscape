## Findings

### m1. The east planter doubles up with the lobby map's own planter, and the map's two planters are hiding spots as well
Evidence: scenario 245-255 puts `reception_plant_east` (planter_fig1, 32x61) at (7.8, 3.95). The lobby map already has planter_fig1 as Tiled item 37 at x 7.69, foot at y 3.5, and item 40 at (1.25, 9.38) (room_aw_merrin_lobby.json, items layer). In screens3/reception.png two identical fig planters stand one above the other on the east wall, and there are four in the room. Plan 2.2 line 155 and C3 (line 641) say the tour's plants go "on other clear spots ... so nothing doubles up". `planter_` is a plant prefix and planter_fig1 is not a small plant (hiding_spots.rb:15-23), so `decor_spots` makes both map planters hiding spots too (hiding_spots.rb:176-212). With `spots: "plants"` the AP can go in any of the four. That works, but the plan never says so.
Fix: give one or both scenario plants a different large sprite that is still a spot and has an overlay offset: plant-large11, 12 or 13 (plant-hiding.js:52-57; not matched by SMALL_PLANT). Or move the east plant away from the map's planter. Then update plan line 155 and C3: "the map's two planter_fig1 are hiding spots too; the tour's plants are planter-size (not plant-large1..10, which are too small for the overlay)". Render reception again after the change.

### m2. The implant socket fails silently when the player has no front-desk keyboard session
Evidence: the socket's client gate checks only that `kit_injector` is held (285-307). With the injector held and no keyboard session at reception_pc (or only a box-route or `from` session), the confirm dialog opens, the player confirms, the server answers 422 `not_ready` (network_access.rb:496-505, 639-640), and network-links.js:500-504 returns quietly. No toast and no event. The injector stays held, so nothing is lost, but on stage the click seems to do nothing. Stop 14 signs in first, so the scripted route never meets this. The sam_dock fixture behaves the same, so this is engine behaviour.
Fix: in slice 6, add a presenter note to the run sheet ("sign in at the front desk keyboard first; plugging in before that does nothing"). As an engine follow-up for AC0 (outside the tour): a toast for a `session`-shape `not_ready`, for example "Nothing happened: the injector needs a PC you are signed in at."

### n1. The plan calls the implant refusal `implant_not_ready`, but the JSON reason is `not_ready` (AC0 question 2)
Evidence: `implant_not_ready` is the method name (network_access.rb:639). The body is `{ success: false, reason: 'not_ready', error: 'The device did not take.' }` (network_access.rb:422, 640), and the client keys on `not_ready` (network-links.js:494). Plan lines 83, 506 and 586 give `implant_not_ready` as the answer. The 2.7 presenter notes never name the reason. The run sheet comes in slice 6. The devices test (7cf5b35fb:312-341) asserts `not_ready`, which is right.
Fix: in plan lines 83, 506 and 586 write "answers 422 with reason `not_ready` (implant_not_ready, network_access.rb:639-640)". The run sheet should use `not_ready`.

### n2. Finance share 404 compared with 403 (AC0 question 1): there is no inconsistency
Evidence: GET /container answers an unadmitted share as an invented id, 404 "Container not found", in the resource branch before any sign-in check (games_controller.rb:629-636). The branch doesn't care which foothold made the request. From the implant foothold the only session held is Delphine's (role reception, scenario 419), so `session_admits?` is false and the answer is 404. The meeting_jack foothold with no session gives the same 404, and slice 2's test asserts that at 44b1c66a4 (demo_access_tour_test.rb:561-562, 571). The 403 came from the draft test at b7a1c9bc1 (`assert_response :forbidden`), which 44b1c66a4 corrected. The server never answered 403 there. The network view's `open` is the static `resource['access'].nil?` (network_access.rb:1080), so it is false for both. No plan stop opens the Finance share through the implant. Admission is player-wide (network_access.rb:1580-1627), so with Julian's session still held at stop 14, the share would open from the implant foothold too, as plan section 1 says.
Fix: tighten the devices test (7cf5b35fb:370 and 576) from `[403, 404]` to `:not_found`. Test agents only.

W6b F would show only if the door controller isn't done, which is unlikely after an unplug.
Fix: none needed. Add one line to the slice 6 run sheet's off-route list.

### n4. The julian mappings come ahead of slice 5, and the capture mapping trips a validator warning until then

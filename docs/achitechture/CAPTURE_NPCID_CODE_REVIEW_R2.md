## Minor

**m1. A semicolon in the query string slips past the query guard in both the capture and the scanner.** Rack 2.2.23 (the bundled version) builds the query hash with `parse_query(query_string, '&;')` (`rack/request.rb:430`), so `;` separates parameters as well as `&`: `Rack::Utils.parse_nested_query("x=1;npc_id=lena")` gives `{"x"=>"1", "npc_id"=>"lena"}`. The capture uses `URL.searchParams`, which splits on `&` only, so `?x=1;npc_id=lena` has the single key `x` and the row is tagged from the body (`response-capture.js:42`). The scanner does the same with `query.split('&')` (`access_leak_scanner.rb:775`). A hand-written `POST /feed_post?x=1;npc_id=lena` with a body naming `jake` therefore reveals Lena's post while the row is tagged `jake`, which is the exact case round 1 m1 set out to close: Jake gets a share for a reveal he never had, and Lena's reveal moves to first-line credit, so an earlier bootstrap showing her post goes unreported. The engine never sends a query on this route, so it takes a hand-written request. Fix: in the capture, leave the row untagged when the decoded `url.search` contains `npc_id` anywhere (over-matching only falls back to the old rule, which is safe); in the scanner, split on `/[&;]/` or apply the same "contains `npc_id`" test to `CGI.unescape(query)`. Test both with `?x=1;npc_id=lena`.

**m2. The contradiction check skips readable answers without a post.** `prepare_feed_base` reaches the tag check only for a row whose `body['post']` is a Hash (`access_leak_scanner.rb:830-834`). A `done`, `refused` or `tooSoon` answer also names `npcId` in its body (`social_feed.rb:42`, `:50`, `:63`, `:70`), and in a long playtest these can outnumber answers with posts. A capture that tags wrongly (a body/query mismatch, or a future change to the client's request shape) is only caught when one of its wrong tags lands on an answer with a post. Round 1 m1 asked for the check on "any readable `/feed_post` row". Fix: move the tag comparison above the `post` guard, for every 200 `/feed_post` row whose body is a Hash with a String `npcId`, and keep `in_log` counting only answers with posts. Test: a readable `tooSoon` answer tagged `lena` with body `jake` sets `feed_tags_ignored`.

**m3. The ruled-out note claims more than the code knows.** `@feed_ruled_out` takes an NPC that still has first-line credit when any lost row is tagged for another NPC (`access_leak_scanner.rb:860`). The note then says "no lost /feed_post answer in the log was theirs (each was tagged for another NPC)" (`access-leak-check.rb:78-79`), and the attribute comment says the same (`access_leak_scanner.rb:219-220`). Neither holds in two cases the condition admits: an NPC missing two reveals, with one lost row tagged for her and one tagged for Jake (she gets a share of 1 and a base of 1, and is listed); and an NPC whose other lost rows were untagged but captured after her last saved reveal (dropped by the 5 s rule, not by a tag). A tester told "no lost answer was hers" may stop looking at lost rows that were hers. Fix: either list her only when no lost row may be hers (`share` is 0) and at least one is tagged for another NPC, or reword to what the code does know, for example "some lost /feed_post answers were tagged for other NPCs, so reveals of theirs that the remaining lost answers cannot cover count from the first line: a resumed game or a response the capture missed. Check that the log began after their reveals". Add a test for the two-reveal case.

## Nit

**n1. The capture's header comment leaves out the query case.** `response-capture.js:16-19` says the tag "is left out when the request body is missing, not JSON or names no NPC"; it is also left out when the query names `npc_id` (and should be when m1's fix lands). The function comment at `:35-39` is right. Fix: add "or when the URL's query names an `npc_id` too".

**n2. The skill doc was edited on the branch.** `3f2bc1cb5` changes `.claude/skills/playtest-scenario/SKILL.md:297`, using round 1 n2's wording, which round 1 marked "for the user to apply". The user approved the skill-script change on 2026-11-12, and q09 in `docs/handover/2026-11-11_USER_DECISIONS.md` approves builders' playtest-scenario skill sentences; check that one of these covers this line before merging. The wording itself is accurate.

**n3. Pre-existing, not from this change: a format suffix or trailing slash takes a `/feed_post` answer out of the feed rules.** Rails serves `POST /feed_post.json` and `/feed_post/` from the same route. The capture tags only paths ending `/feed_post` (`response-capture.js:103`), which is the safe side, but the scanner's own feed rules (`feed_unreadable?`, `in_log`, `note_feed_served`) also match on `end_with?('/feed_post')`. A readable answer on such a path is not counted in the log, so its reveal is credited from the first line, and a bootstrap that showed the post before it would pass. It needs a hand-written request. Suggest a backlog entry: strip a `.json` suffix and trailing slash before matching the route in the scanner.

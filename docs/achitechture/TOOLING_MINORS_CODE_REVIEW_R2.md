## What was checked, and held

- **Round 1 fixes are in.** M1 (values hidden), m1 (realpath), m2 (extractor fallbacks gone), m3 (temporary-file test), m4 (shared lookup and walker), m5 (cached walk), m6 (production root through `#ink` and the resolver) and nits 1 to 5 and 7 are all present and tested.
- **Requires warning, lock types.** The values are shown only on an allow-list (`%w[rfid key]` on the room, `validate_scenario.rb:6347`), so every other type is hidden by default: pin, password, login, flag, biometric, bluetooth, ble, ransomware_display, any custom or misspelt type, a room with no `lockType`, and a `connectedRoom` that names no room. Probed: a pin room with the entry's `requires` as a Hash says "(values not shown)"; an integer `4812` against `'4812'` compares equal and draws nothing. The other door-entry warnings name the field only (`postitNote`, `passwordHint` and so on never print their value). One hole remains, through the allow-list itself (minor 1).
- **Realpath guard, every caller.** `InkStoryFile.find` has four production callers: `GamesController#resolve_and_compile_ink` (and so `#ink`), `TtsLineResolver` (and so `#tts` and the narrator lookup), `TtsLineExtractor#resolve_ink_path` and `TtsExpectedLines#resolve_story`. All go through `confined` and then `really_inside?` on the JSON, the .ink and, before a compile, the target. A JSON that resolves outside makes `find` return nil even when a valid sibling exists, which fails closed. The compile target is checked with `realdirpath`, so a folder symlink is caught before anything is written. `File.rename` onto an existing symlink replaces the link, not its target.
- **Include-walk cache.** The cache entry records the mtime of the root .ink, of every include it read, and of every include name it looked for and did not find (as nil). A changed include, a deleted include (mtime becomes nil), a new nested INCLUDE (its includer's mtime changes) and a missing include that appears (nil becomes a time) all force a fresh walk, and the test covers the last two. The cached arrays are frozen and `includes` hands out a copy, so a caller cannot change the cache. Keys are bounded by the number of .ink files the lookups reach. The one weakness, an edit that leaves the mtime unchanged (`touch -r`, `cp -p`), is shared with the mtime staleness check that predates this branch, so it is not new. The compiled JSON taking the pre-compile source mtime also handles two workers racing on the same story: the older compile, renamed last, carries the older mtime and is recompiled next time.
- **ghost-protocol demo.** The three storyPaths now name `scenarios/ink/{netherton,chen,haxolottle}_hub.json`, which exist, so `#ink` serves them; on main it answered 404. Compared with main's scenario file under the branch validator, the only change is that the three ❌ INVALID lines go and one block of issues appears. ## Minor

### m1. A PIN on a door entry is printed when the room is rfid or key
`scripts/validate_scenario.rb:6347-6350`. The allow-list looks only at the room's `lockType`. When an author puts the lock on the door entry by mistake, which is the very case this check exists for, the entry carries its own `lockType` and `requires`. Probed: room `vault` with `lockType: 'rfid', requires: 'SAM-1'` and an entry with `lockType: 'pin', requires: '4821'` prints "(4821, the room's SAM-1)". An entry with no `lockType` and `requires: 'hunter2'` against a key room prints `hunter2` too. The game never asks for that value on this door, but it is the PIN the author meant to set, often copied from another lock in the mission, and the section header still promises "Messages never quote a password". The existing test only varies the room's type.

Fix: quote the entry's values only when the entry has no `lockType` or one in `rfid`/`key`, and its values look like ids rather than codes; the simplest safe form is to always quote the room's value (a card or key id on an rfid or key room) and never the entry's. Add a test with an rfid room and an entry carrying `lockType: 'pin'` that checks the entry's value does not appear.

## Nit

1. **Time of check to time of use.** `really_inside?` runs before the read in `#ink` (`games_controller.rb:636`) and before `compile!`, and nothing pins the file between them. A symlink swapped in after the check is followed by `File.read`, and inklecate opens the predictable `<output>.<pid>.<thread>.tmp` with an ordinary create, so a symlink planted at that name would have the compiled JSON written through it, anywhere the server can write. Both need write access inside scenarios/ already, which is why this stays a nit; but it is the one route from scenarios/ write access to writing elsewhere. Cheap fixes: compile into a fresh `Dir.mktmpdir(nil, File.dirname(output))` (mkdir fails if the name exists) and rename from there; in `#ink`, open the file once and check `File.realpath` of the opened path, or read through `File.open(path, File::RDONLY | File::NOFOLLOW)`. Separately, the class comment (`ink_story_file.rb:16-19`) should say the guard holds at lookup time. The pre-existing `rescue JSON::ParserError` in `#ink` echoes the start of a non-JSON file in its 500 message, which matters only together with a symlink.
2. **INCLUDE names are not confined.** `walk_includes` (`ink_story_file.rb:126-145`) reads `File.join(root_dir, name)` for any name, `../` included, and inklecate compiles it into the JSON `#ink` serves. Ink is authored content, so this is the author's choice rather than an escape by storyPath, but it sits beside a comment that promises a storyPath cannot reach other files. Either confine include paths with `really_inside?` (and add the "INCLUDE not found" warning for one outside) or note the exception in the comment.
3. **TtsExpectedLines still falls back to stories the game will not serve.** `tts_expected_lines.rb:244-255` tries `InkStoryFile.find` first, then the absolute path, `Engine.root.join(ref)`, and two scenario-folder guesses. Round 1 m2 dropped the same fallbacks from the extractor so that the batch reads what `#ink` serves. Here they are partly needed (`inkPath`/`inkFile` refs to an .ink, and fixtures), so the expected-line set can include a story `#ink` answers with 404 and report no "story file not found" for it. Harmless for pruning, misleading for "which lines have no audio". Keep the fallbacks only for refs ending in `.ink`, or add a warning when a `.json` ref is found only by a fallback.
4. **Build log wording, and the validator's count.** The build log says 28 warnings appeared in npc-hub-demo-ghost-protocol. They are 1 warning (the lockpick in `chen_lab` has no `puzzle_graph_unlocks`, and the demo has no key lock for it to open) and 22 generic suggestions comparing the demo with m01; the "28" counts output lines, and the debrief suggestion takes 6. They are real but not worth a backlog entry: the demo is a hub-dialogue showcase, and the suggestions ask it to become a mission. If anything goes in the backlog, one line for the demo (a narrator voice, which the ink uses, and dropping the lockpick) would do. Correct the build log's figure; the line-counting header is pre-existing validator behaviour and out of scope.

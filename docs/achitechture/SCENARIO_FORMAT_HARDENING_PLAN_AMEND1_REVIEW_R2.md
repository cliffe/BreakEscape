## What was checked and holds

- **The fetch wrapper covers the request sites.** On d8fb32450 the only `XMLHttpRequest` traffic is Phaser's loader (`core/game.js:98`, `:1621`, `:1641` and the `load.audio` sound files, all static). No `sendBeacon`, `EventSource` or `WebSocket` reaches an engine route. Every other request is a bare `fetch`, `win.fetch` (`utils/scenario-brief.js:37`, `client-purchase.js:178`) or a `fetch` reference taken at call time (`music/conclude-mission.js:37`, `systems/office-presets.js:34`, `systems/office-room-tone.js:33`), so all of them resolve to the wrapper. Files with `fetch(` that the plan's list does not name (`client-purchase.js`, `person-chat-portraits.js`, `phone-chat-conversation.js`, `music-controller.js`, `music-widget.js`, `tts-manager.js`, `hacktivity-cable.js`) also pass through it; the builder's re-anchored list should add them. The classic scripts that run before `main.js` (`client-platform.js` and the inline blocks in `games/show.html.erb`) keep no `fetch` reference; the inline `reset` and `new_session` handlers call `fetch` at click time. `hacktivity-cable.js` and `session-resume-keys.js` are separate module scripts that run after `main.js`.
- **Reload loops.** `sessionStorage` is per tab and the key holds the game and both versions, so each tab reloads at most once per pair. The flush's own sync response sees the same mismatch and is absorbed by the once-per-page rule. `syncConfirmed({ attempts })` (state-sync.js:677) and `flush()` (:698) are where the plan says.
- **The header leaks nothing.** It carries the code's format number, the same for every game and user. Same origin, so no CORS exposure question arises.
- **M3 and M4 rules.** `version_of` is sound: jsonb returns JSON integers as Ruby Integers, and only the server writes the field. The deep-copy compare is sound for this use: Ruby `Hash#==` ignores key order and compares values with `==`, JSON floats round-trip exactly, and NaN cannot occur in JSON. `1 == 1.0` is true, so a step that only retypes a number reads as unchanged, which is harmless. `SYNC_STATE_COLUMNS` (games_controller.rb:1955) holds no `scenario_data`, which matches "sync never upgrades".
- **Hacktivity readers.** A grep of Hacktivity's `app` and `lib` for `scenario_data` and `player_state` finds only the five sites the plan lists. Hacktivity's `config/puma.rb` runs one process with no workers and no phased restart, so mixed code versions within one deploy are not a concern.
- **Design calls.**
  - The `window.fetch` wrapper: agreed. It is the one place every request passes, and the static scan stops a module from keeping a reference.
  - Renaming the `leftBehindBy` event key to `owner`: agreed. Events are not stored, and the reload check covers tabs on old code.
  - Keeping `affordance: {}`: agreed. `AccessWork.affordance` merges `own || {}` over the preset, so `{}` and an absent block agree in Ruby where presets apply. `preset_id` returns nil for an object with a `lockType`, so for a sign-in PC with no preset, dropping the block would remove it from the JS needs lists (`o.affordance &&`). Keeping `{}` is the only choice that changes nothing.
  - `BREAK_ESCAPE_FORMAT_TEST_STEP`: right in intent, with the gaps in m4.
- **Step order.** 2b after step 2 and before steps 3 and 8, and step 7 after sync-deltas, both hold. 8a, 8b and 8c are in sequence, and 6a-1 comes after 8c. The one gap is m5.
- **Tests that fail without their step.** Step 7's tests do fail without it (no module, no header, sync guarded by the raised fixture CURRENT). In step 2b, the fingerprint-owner and wearable tests fail today, as they should. The exceptions are M1 and n3.

### Majors

**M1. Step 2b, Tests and Live proof: the foothold test uses the plant route, which never reads `grant_foothold`.**
- *Problem.* The Rails test says a `grant_foothold` inside `_draft.triggerOnInteract` "is not honoured by `POST network/plant`", and the live proof sends "the plant ... with `apiClient.networkPlant`". On d8fb32450, `network_plant` calls `Game#plant_device!`, which reads `NetworkModel.rogue_device_definitions` (network_access.rb:137, through `DeclaredGrants.for` for granted devices). `grant_foothold` actions are read only by `POST network/implant`: `network_implant` calls `implant_foothold!`, then `grant_foothold_action_for` (network_access.rb:423-427, 447-450), which calls `NetworkModel.grant_foothold_actions`. The client call is `apiClient.networkImplant(pcId, shape, path)` (api-client.js:183).
- *Why it matters.* As written, the foothold test passes with or without the skip, so the claim that "each test fails with the skip removed" is false for the step's main case, and the live proof would show a refusal that has nothing to do with the note. This is the helper-passes, live-path-untested pattern.
- *Suggested change.* Use `POST network/implant` with the PC and shape of the note-held action, and `apiClient.networkImplant` in the live proof. Keep a plant-route test only for a rogue device granted by a `give_item` inside a note. That test does reach `DeclaredGrants.for`, through `rogue_device_definitions`, so the skip in `DeclaredGrants.collect` covers it. Also note that `grant_foothold_action_for` takes the first match per [pc, shape] (`.find`), so today a note-held duplicate placed before the real action would win; add that case as a fixture.

**M2. Step 2b, item 1: `ID_MAPS` as path patterns with `*` and `[]` cannot equal the schema's id maps.**
- *Problem.* The schema on e13392d17 has about 70 nodes whose `additionalProperties` is a schema (a walk of `scenario-schema.json` lists them). Several sit inside definitions that recur to any depth: `item.hintOnlyFlags` (items nest through `contents[]`, `itemsHeld[]` and `give_item` actions anywhere), `eventMapping.needs.set` (wherever an event mapping sits), `npc.interests`, `npc.onUse` and `npc.chatter` (room NPCs, top-level NPCs, NPC records elsewhere), `room.connections` and `room.lighting.emitters`. A finite list of patterns using `*` for a key and `[]` for an index cannot name a map at unbounded depth, so the node test "fails if the constant and the schema's id maps differ" cannot be written as stated. The list in the plan also names `networkLinks`, which is an array of pairs, not a map, and omits `interests`, `onUse`, `chatter`, `connections`, `disguises` and `social.characters`.
- *Why it matters.* A wrong entry in either direction costs something. A missing id map turns a real `_`-named entry into a note, so a walker skips live content; a spurious one keeps a note live. A builder given this spec will either write a test that cannot pass or narrow the test until it proves nothing.
- *Suggested change.* Pick one of two buildable rules and state it. (a) Key the decision on the parent's property name: `AuthorNotes::ID_MAP_KEYS` is the finite set of property names whose value is an id map anywhere in the schema (`rooms`, `networks`, `resources`, `roles`, `policies`, `accountProfiles`, `globalVariables`, `needs`, `interests`, `onUse`, `chatter`, `connections`, `emitters`, `hintOnlyFlags`, `set`, `characters`, `disguises` and the rest). `note?(parent_key, key)` is true for a `_` key unless `parent_key` is in the set. The node test collects the property names of every id-map node in the schema and compares the two sets. Where a name means a map in one place and an object in another (for example `needs` on an NPC and on an event mapping), the rule errs towards "id", which is today's behaviour. (b) Move step 2's schema-driven resolution (`schema_map_value`, `schema_node_keys`) into `lib/` and have the server walkers carry the schema node, as step 2's walker does. (a) is smaller and needs no schema load at run time. Either way, drop `networkLinks`.

**M3. Step 2b, item 4: the `each_capture_writer` split names neither its callers nor which side each takes, and two of them must agree.**
- *Problem.* `CaptureModel.each_capture_writer` has seven callers on d8fb32450, and they point both ways:
  - `capture_writers`, then `declared_target_ids` and `client_target_ids` (capture_model.rb:70, 80, 294): the target ids a client capture may carry. This widens.
  - `all_capture_candidates` (:385): the entries a client capture is matched against. This widens.
  - `Game#build_authored_capture_secrets` (game.rb:1454-1475): the secret the server serves for a target id once its proof holds. This serves a secret, so it widens. It keeps the first writer per id (`out[id] ||=`), so a note-held writer met first would shadow the real one with a different secret or proof.
  - `shorthand_proofs`, then `proofs_for` (:120): alternative proofs, any one of which serves an account password (`account_capture_served?`, capture_proofs.rb:104-115). This widens.
  - `declares_proofs?` (:151): turns proof-gating on for the whole scenario. This narrows.
  - `action_proofs` (:134) and `scripts/validate_capture_log.rb:27, 221`: validator only.

  The plan says only "the withholding pass visits notes, and the list of writers the server accepts a capture from skips them".
- *Why it matters.* A builder cannot tell from the plan which of these is "the withholding pass". Two of them are a trap. If `declares_proofs?` visits notes while `proofs_for` skips them, an `addCapture` with a `proof` that sits only in a note turns proof-gating on and supplies no proof, so every account password whose value opens something is withheld for good: an honest player is blocked. If both skip notes, nothing changes from today for a note-only proof.
- *Suggested change.* Give the split as a table: every caller above, the side it takes and why. `build_authored_capture_secrets`, `all_capture_candidates`, `declared_target_ids` and `shorthand_proofs` skip notes. `declares_proofs?` takes the same side as `shorthand_proofs` (skip), so proof-gating and the proofs that satisfy it always come from the same writers. The validators follow the server. Implement it as one iterator with a `notes:` keyword (default `:skip`), and make `:visit` an explicit choice at each secrecy call. Add tests: a note-held `addCapture` with a secret is not served and does not shadow a live writer with the same target id; a note-held proof neither turns gating on nor satisfies it.

**M4. Step 7, "The header" and "Refusal": the header is lost on every refused or halted response, and `sync_state` has no refusal.**
- *Problem.* The header is set by an `after_action` in `BreakEscape::ApplicationController`. Rails skips `after_action` callbacks when a `before_action` renders or redirects, and when an exception is answered by `rescue_from`. The refusal is rendered from `set_game`, which is a `before_action` (games_controller.rb:27, 1932), so every 409 refusal goes out without the header. So do the other early exits: `require_game_in_host_event`, `refuse_oversized_body` (a `prepend_before_action`), `protect_from_forgery with: :exception` and the Pundit `rescue_from`. Separately, `sync_state` loads only `SYNC_STATE_COLUMNS` (no `scenario_data`) and goes through no version check, so on code older than the game (the plan's own case: a rollback, or an older worktree on the shared database) it goes on writing player_state for a game that every other route refuses.
- *Why it matters.* Take a tab holding version 1 against a server that reads only up to 0. Its room and container fetches get a 409 with no header, so the wrapper sees no mismatch, the tab does not reload to the refusal page, and play breaks with no message. Meanwhile its syncs succeed, against the plan's "Nothing is written". The test "every engine controller's response carries the header", run on one ordinary route per controller, passes while this is broken.
- *Suggested change.* Set the header in a `prepend_before_action` in `BreakEscape::ApplicationController`, which runs first and survives a halt; the response headers are kept when a later callback renders. Test it on the 409 refusal, on a CSRF failure and on a Pundit refusal. Add `sync_state` to the refusal list: it plucks `scenario_data->'formatVersion'` (one indexed jsonb read, inside the same row lock) and answers 409 `format` when the value is above CURRENT or unreadable. Also state the client side: a JSON 409 with `error: "format"` on any route counts as a mismatch (reload once by the same key, then the banner), so the refusal does not depend on the header alone.

### Minors

**m1. Step 2b, item 2: `OwnerClaim.mappings` is a widening whole-subtree walk the list omits.** `OwnerClaim.mappings` (owner_claim.rb:183-195 on d8fb32450) collects every Hash at any depth under an owner's `eventMappings`, and `might_leave` uses `patrolOverride`, `navigateToPlayer` and `changeStoryPath` from them to allow an owner claim. A `_draft` inside a mapping that holds `patrolOverride` allows a claim the client would never produce. *Change:* add it to the skip list. It carries no path today; give it one, or apply the parent-key rule from M2.

**m2. Step 2b, item 3: the secrecy list is incomplete, and fixed-key filters never reach a note.** Two problems. (a) The list omits `Game#filter_inventory_for_client!` (game.rb:843), which already visits every value. (b) More important, the guarantee in "a secret written in a note must still be withheld" holds only for the recursive walkers. The fixed-key withholding never sees a note: `WITHHELD_NPC_KEYS` (game.rb:5323) deletes `creds` and `habits` by name, not a `_creds_old` beside them; the same goes for the top-level deny list, `networks.*.wifi.psk` and the feed record. 6a-1's class 4 value check catches a note that copies a real secret, but only in the scenarios the scan runs over. No engine JS reads a `_` property (checked by grep). *Change:* either (preferred) strip `_` property notes, never `_` ids, from every client payload in the bootstrap, room and inventory filters with the step 2b helper, which closes the gap and drops about 500 comment strings from payloads; or reword item 3 to say that notes are protected by the recursive walkers and 6a's class 4 check, and list the fixed-key filters as not covering notes.

**m3. Section 2 "Old games for live proofs" and step 8 "The stored-game live proof": the swap-then-prepare recipe gives the wrong order, and the two sections disagree.** Section 2 says the swap tool "never stands in for an old game"; step 8 then makes the test-scenario old games with the base's swap tool. More important, the swap tool runs `initialize_player_state` on the raw render (swap-scenario-game.rb, after `g.scenario_data = sd`), so preparing afterwards leaves a player_state built from unprepared data. A created game prepares first (`before_create :generate_scenario_data`, which calls `prepare_scenario_data!`, then `initialize_player_state`, game.rb:33-35 and 5377-5407). *Change:* in the base worktree, a one-off `bin/rails runner` script (not committed) renders, calls `prepare_scenario_data!`, then `initialize_player_state` and `set_scoring_totals`, in creation order. Reword section 2 so it allows the base's own code to make a test-scenario game this way.

**m4. Step 7, Live proof: the `BREAK_ESCAPE_FORMAT_TEST_STEP` switch.** (a) "Raises CURRENT to 1" means reassigning a constant at boot, which Ruby warns about, and other code may already have read the old value. Make the version a method (`FormatUpgrade.current`, the last step's version or 0) that the switch affects through `STEPS`. (b) The initializer also runs in `test`, so a builder who exports the variable to start the server and then runs `bin/rails test` in the same shell changes CURRENT for the whole suite, and the "CURRENT 0" tests fail for no visible reason. Honour it in development only, and unit-test the initializer's method directly. (c) The proof game is left stamped 1 by a no-op step. Once 8a lands as the real format 1, that game would skip 8a's transform. Record its id in the build log as unusable for any later proof.

**m5. Section 5, item 7: step 7 depends on step 2b, and the order does not say so.** Step 7's `STEPS` transforms and `retired_keys_in` call `AuthorNotes.note?`, and its unit test needs "skips one inside `_draft`", yet item 7 lets step 7 be "built alongside steps 3 to 5" with no dependency on 2b. *Change:* "Step 7, after build/sync-deltas and step 2b".

### Nits

**n1. Step 7, "The header" and "One place every request passes".** `StaticFilesController` inherits `BreakEscape::ApplicationController`, so every JS module, sprite, sound and static JSON file it serves (routes.rb:5-9) carries the header too, along with the TTS `send_file` answers. "A response without the header (a non-engine URL, an asset ...) is ignored" is therefore not what happens. It is harmless while the value is current, but a response the browser serves from its HTTP cache comes back with whatever header it was stored with. Skip the header on `StaticFilesController` (or compare only `/break_escape/games/` URLs) and say so.

**n2. Step 7, "What changed means".** Name the deep copy: `Marshal.load(Marshal.dump(data))` or a JSON round trip. `deep_dup` is ActiveSupport, and `format_upgrade.rb` is plain Ruby.

**n3. Step 2b, Tests.** "A PIN inside `_draft` ... is still stripped" and "the same two actions in a room whose id is `_annex` are honoured" pass today and after the step. They are guards against over-applying the helper, not tests that fail without the step. Label them as guards so the "fails without it" audit does not count them.

**n4. Step 2b, "When it lands".** "Step 3's walks and every step 8 transform use the helper" contradicts item 3, where step 3's `each_lock_answer` keeps visiting notes and needs no helper. Say "every step 8 transform uses the helper; step 3's walks visit notes by item 3".

**n5. Step 2b, item 2.** `Game#merge_biometric_samples!`'s `collect` lambda (game.rb:394) and `OwnerClaim.scenario_objects`' `add` lambda carry no key path, so `AuthorNotes.note?(keys, k)` cannot be called as written. **n6. Section 2, "Old games for live proofs".** The proof needs two assigned ports per builder; the common brief assigns one. Say that the orchestrator assigns the second.

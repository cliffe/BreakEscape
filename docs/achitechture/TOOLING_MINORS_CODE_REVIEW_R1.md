# Tooling minors: adversarial code review, round 1

Branch `build/tooling-minors` against `main` (commits a14d5f8fe, 99ada76d5, a31455443), read with docs/achitechture/TOOLING_MINORS_BUILD_LOG.md. Line numbers are on the branch.

Counts: 0 blocker, 1 major, 6 minor, 7 nit.

## What was checked, and held

- **storyPath guard against `..`, absolute and encoded paths.** Probed `InkStoryFile.find` with the default roots (scenarios only): `scenarios/../config/routes.rb.json`, `/etc/passwd.json`, an absolute path through `scenarios/../`, `scenarios%2F..%2Fconfig.json`, `~/x.json`, `SCENARIOS/...`, a bare `scenarios` and `scenarios/.json` all return nil. `scenarios//ink/x.json`, `scenarios/./ink/x.json` and the absolute form of a real story are found, as they should be. The prefix check uses `root + "/"`, so a sibling such as `scenarios_evil/` is refused. Percent-encoding is not decoded anywhere on this path, so it cannot help. Symlinks do get through: see minor 1.
- **Every scenario's ink lookup.** Each of the 176 `scenario.json.erb` files was built with `Game#generate_scenario_data`, with no build errors, and every `storyPath` found anywhere in it (357 distinct pairs) was looked up with the new `find` and with main's lookup. The results differ for 0 of 357. Three come back nil both times: the `story_design/ink/*_hub.json` paths in npc-hub-demo-ghost-protocol (nit 5). No shipped story depends on a runtime compile from a missing JSON either: every other path finds committed JSON with `compile: false`.
- **Test-only roots leaking into production.** The extra roots are added only in `test/test_helper.rb:37`, which nothing outside the test suite loads. The production default is `[Engine.root/scenarios]` (`ink_story_file.rb:31`). No leak. The test roots do hide a gap in the tests, though (minor 5).
- **Atomic compile and the per-path lock.** Inside one process the lock serialises compiles of the same output, and the second check inside the lock stops a second compile (the 4-thread test fails if the lock or the re-check is removed). Across Puma workers there is no shared lock, but each worker writes its own `<out>.<pid>.<thread>.tmp` and `File.rename` is atomic on one filesystem. The worst case is one redundant compile, and no reader ever sees half a file. The lock key is the expanded path, so `a//b` and `a/./b` share one lock. Safe. The atomicity itself has no test (minor 3).
- **X.json over X.ink.json for the 8 pairs.** All 8 pairs are in `scenarios/test_scenarios/ink/`, each has its `.ink`, each `X.ink.json` is byte-identical to its `X.json` on main and on the branch, and each `X.ink.json` is named by exactly one storyPath. Copying the fresh compile over it is right for all 8 and keeps them identical. `compile-ink.sh` only walks folders named `ink`, which is where all 8 sit.
- **Validator across all 176 scenarios.** Main's validator, lib and schema (from `git archive main`, with the same assets) and the branch's were run on every `scenarios/**/scenario.json.erb` with `--no-graph`. The ❌/⚠️ lines are the same for every one of the 176 files, with 106 ❌ lines both times and the same exit codes (161 zero, 15 one). The builder's "nothing changed" claim holds.
- **Do the tests fail without the change?** With main's versions of the five changed source files: door-gates-validator fails 4 of 33 (the four new or changed lock and null-entry tests); `tts_expected_lines_ink_json_test` fails; the new `npc_habits_test` assertion (blank connection) fails. Most `ink_story_file_test` failures on main come from the unknown `allowed_root:` keyword rather than from behaviour, so I mutated the branch code one change at a time: removing the lock, the re-check, the root check, the `.json` check, or `File.file?` (back to `File.exist?`), or putting main's extractor lookup back, each makes a named test fail. Three mutations pass every test: writing straight to the output with no temporary file (minor 3), putting back `&& !narrator` on the voice-marker strip (nit 3, all 191 tests in `test/unit/break_escape` pass), and the dungeon-graph gate-label test, which passes on main as well. The build log says no graph change was needed, so that one is a regression guard and is fine.

## Major

### M1. The new requires warning prints the lock answer
`scripts/validate_scenario.rb:6345-6349`. When a door entry's `requires` differs from the room's, the warning quotes both values. For a `password`, `pin` or keypad room, the room's `requires` is the answer, and the entry's is often a stale copy of it. The section header at `validate_scenario.rb:6109` says "Messages never quote a password", and validator output gets pasted into build logs, reviews and agent context. No shipped scenario trips this today (the 176-file run shows no new lines), but the first author who leaves an old PIN on a door entry will see the live PIN printed.

Fix: quote the values only when the room's `lockType` is `rfid` or `key` (card and key ids, which the test's `SAM-1` is). For any other lock type, say "differs from the requires on room 'X' (values not shown)". Add a test with `lockType: 'pin'` that checks the warning fires and contains neither value.

## Minor

### m1. A symlink inside scenarios/ escapes the guard, for reads and for compiles
`app/services/break_escape/ink_story_file.rb:62-67`. `confined` uses `File.expand_path`, which does not resolve symlinks, and `compiled_json` and `ink_source` use `File.file?`, which follows them. Tested: `scenarios/zz_link.json -> Gemfile.lock` is returned by `find`, and so is `scenarios/zz_dir/x.json` where `zz_dir -> /tmp`. With `compile: true` a symlinked folder also lets the temporary file and the rename land outside scenarios/. Someone has to place the symlink inside scenarios/ first, which already takes write access to the tree, so this is minor. But the class comment (lines 16-19) promises that a storyPath "cannot name, or have compiled over, any other file the server can reach", and that promise is not kept.

Fix: after choosing `json`, `ink` and the compile target, check `File.realpath` of each one that exists (`File.realdirpath` for a target not yet written) against the `realpath` of each root, and return nil when any resolves outside. Add a test with a file symlink and a folder symlink in a temporary root.

### m2. The extractor still falls back to stories the game will not serve
`app/services/break_escape/tts_line_extractor.rb:647-654`. m2 was meant to make "the batch read what `#ink` serves". When `InkStoryFile.find` returns nil (a path outside scenarios/, or a missing file), the extractor still tries `scenarios/<mission>/<basename>` and `scenarios/<mission>/ink/<basename>.json`. If either exists, the batch voices a story the game answers with a 404. Fix: drop both fallbacks. If a scenario depends on them, log a warning naming the storyPath, so the author fixes the path instead.

### m3. The atomic write has no test
`ink_story_file.rb:124,133`. With `tmp = output_path` and no rename, all 11 `ink_story_file_test` tests still pass: inklecate writes nothing when it fails, so the "leaves no file behind" test cannot tell the two apart, and the threads test never looks at a half-written file. Fix: stub `Open3.capture3` (or wrap the real call) to record the `-o` argument, and assert that it ends in `.tmp`, is not the output path, and is gone after the call.

### m4. TtsExpectedLines keeps its own include walker and story lookup
`app/services/break_escape/tts_expected_lines.rb:240-262`. n1 says the walker moved into `InkStoryFile.includes`, but `with_includes` still resolves each nested INCLUDE against the including file's folder. I checked inklecate with `root.ink -> INCLUDE sub/a.ink -> INCLUDE b.ink`: it uses the root story's `b.ink`, not `sub/b.ink`. So for nested includes from a subfolder, the TTS expected-line set reads a file inklecate does not, or reports "INCLUDE not found" for one it does. `resolve_story` also does not try the X.json to X.ink.json swap that `#ink` makes, so a storyPath naming X.json with only X.ink.json on disk draws "story file not found". Fix: use `InkStoryFile.find(ref, compile: false)` first in `resolve_story`, and build `with_includes` on `InkStoryFile.includes`, keeping the "INCLUDE not found" warning.

### m5. Every lookup now reads the .ink and all its includes
`ink_story_file.rb:104-109`, called from `find` with `compile: true`. Before, the staleness check cost two `stat` calls. Now it reads the .ink and walks every INCLUDE on every `/ink` and every `/tts` request. `TtsLineResolver#narrator_line_in_stories` (`tts_line_resolver.rb:207-211`) calls `find` for every story in the scenario on each narrator line, so in m10 (31 stories that include `m10_carryover_vars.ink`) one request reads about 60 files. Fix: cache the include list per `[ink path, ink mtime]` in a small hash (or in the same lock map), so the walk runs again only when the .ink changes. Then stat the cached includes.

### m6. Nothing tests the production root through a real caller
`test/test_helper.rb:37` adds `Dir.tmpdir` and `Engine.root/tmp`. Every guard test passes `allowed_root:` explicitly. The only check on the default is `allowed_roots.first(1)` (`ink_story_file_test.rb:71`), which passes even if a later change widens the default. So no test shows that `GamesController#ink` or `TtsLineResolver` refuses a storyPath outside scenarios/. Fix: add a test that sets `InkStoryFile.allowed_roots` to the default for its duration (restoring it in `ensure`), writes a story under `Dir.tmpdir`, and checks that `#ink` returns 404 and the resolver returns its "not found" error. Also assert `allowed_roots.size == 1` on a fresh default, by resetting `@allowed_roots` to nil inside the test.

## Nit

1. `ink_story_file.rb:93`: the INCLUDE pattern keeps a trailing `// comment` as part of the file name. inklecate accepts `INCLUDE b.ink // note` (checked), but the walker looks for `b.ink // note`, skips it, and the staleness check misses edits to `b.ink`. No shipped ink has such a line. Fix: strip `\s*//.*\z` from the captured name.
2. `tts_expected_lines.rb:220`: for a ref that ends in neither `.json` nor `.ink`, the new `sub` leaves `ink == path`, so the ref file itself goes into `ink_files` (main's `sub_ext('.ink')` did not do that). Fix: set `ink` only when the path matches `/(\.ink)?\.json\z/` or ends in `.ink`.
3. `tts_line_extractor.rb:329` (n4): the narrator change has no test. Putting back `&& !narrator` passes all 191 tests in `test/unit/break_escape`. Add one extractor case: a `Narrator:` line marked `voice:`.
4. `ink_story_file_test.rb:76`: `scenarios/../config/database.yml.json` does not exist, so the assertion passes with no guard at all. Use `scenarios/../package.json`, which exists at the engine root.
5. `scenarios/npc-hub-demo-ghost-protocol/scenario.json.erb:254,319,412`: these storyPaths name `story_design/ink/*_hub.json`, which do not exist. The stories are at `scenarios/ink/{netherton,chen,haxolottle}_hub.json`, inside the new root. This was already broken on main. Point the three paths there.
6. The 8 `test_scenarios/ink` pairs are byte-identical duplicates, each `X.ink.json` named by one storyPath. Pointing those storyPaths at `X.json` and deleting the copies would remove the copy step from `compile-ink.sh` and the duplicate check from the staleness test.
7. `ink_story_file.rb:133`: the renamed JSON has the mtime of the end of the compile. An .ink saved while inklecate is running ends up older than the JSON, so that edit is never compiled. This can only happen in development. Fix: record the newest source mtime before compiling, and `File.utime` the output to it after the rename.

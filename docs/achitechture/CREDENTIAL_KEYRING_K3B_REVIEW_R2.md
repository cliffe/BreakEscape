A trigger during a request on the wire is never lost: `_queued` is already null by then (`:273`), so it builds a new ask behind the running one. ## Findings

**m1a. A trigger that arrives while the queued ask is flushing the sync is folded into an ask that cannot carry its change.** `keyring.js:267` to `:278`, with `:273`.
`_queued` is cleared only after `await syncConfirmed()` returns. While that await is in flight (one PUT /sync_state round trip, whenever the first ask had pending changes), a second trigger returns the same `_queued` promise. `StateSync._syncRun` (`state-sync.js:756`) builds its body at the start of a run; a second `syncConfirmed` call during a run would queue a follow-up run (`_next`) that carries the new change, but a joiner never calls it. The GET then goes out with the second trigger's unsynced state missing from the server. Scenario: the player takes the SV-OPS-01.rdp (ask A, with a pending inventory delta), and within that round trip a second add or a plant lands (`network_foothold_gained`); ask A's GET answers without the second change, no further ask is queued, and the second find (or the new foothold's `ops_cookie` entry) neither toasts nor gets a Connect entry until some later trigger. Connect itself is unaffected (it does its own flush and GET). The wire-time case R1 cared about is handled; this is the window before the wire.
Fix: clear `_queued` as the first statement of the ask callback, before `await syncConfirmed()`. Same-tick triggers (the case the comment promises) still join, because the callback does not run until the microtask after they have all called `refresh()`; a trigger after the callback starts then builds the next ask behind it, whose own `syncConfirmed` carries its change. Test: `window.stateSync.syncConfirmed` returns a deferred, call `refresh()`, let the callback start, call `refresh()` again, and assert the second returns a different promise and a second `syncConfirmed` and GET happen after the first resolves.

**m1b. A page-start prime answered after a newer ask is dropped whole, including the reload set.** `keyring.js:167` to `:175`, `:193`, `remember` at `:152`.
`prime()` goes through `fetch(null, { primed: true })`, so it gets a sequence number, and the first inventory trigger at page load (`trayChanged` always asks on its first call, `_trayIds` null) sends its own background GET. If the later GET is answered first, the prime's answer is dropped before `remember` runs, so `firstAnswerIds` is never set (only a prime sets it, `:152`; the failed-prime path sets it at `:195` and does not run here because nothing throws). It stays null for the page, `foundVisible` (`:219`) has nothing to match, and a registry password the player had already found before the reload stays hidden until its file is opened again. I confirmed this with a probe test (prime pending, a second background fetch answered first, then the prime): `firstAnswerIds` is null. Needs two page-start GETs answered out of order, so rare, and it only re-hides a password that opening the file brings back.
Fix: in the stale branches, when `primed` and `firstAnswerIds === null`, set `firstAnswerIds` from the dropped answer's entry ids before returning (the dropped answer is still the page-start state for the reload rule), or exempt `primed` fetches from numbering. Test: the probe above, asserting `firstAnswerIds` holds the prime's ids.

**t1. A background GET with no timeout stalls the chain.** `keyring.js:267` to `:278`, `api-client.js:237`.
`ApiClient.get` has no abort, so a request that never settles keeps `_running` pending; every later background trigger joins one `_queued` ask that cannot start, so finds stop toasting and the tray's entries freeze until the page reloads. Before this change each trigger asked on its own and a hung one blocked only itself. Connect is not affected (it uses `fetch` directly). Fix if wanted: give the chained ask a cap (for example `Promise.race` with a 10 s timer around `fetch`) so the chain moves on; the stale drop already handles a late answer.

**t2. The Pundit 403 shares step 7's line.** `keyring.js:430` to `:432`.
`user_not_authorized` answers `{ error: 'Not authorized' }` with no `reason`, which the `!why` branch reads as "can't be reached from here". It cannot happen to a signed-in owner of the game, so this is only a wrong sentence on an unreachable path. Fix: on a reason-less 403, give step 7's line only when `result.message` is the "PC not reachable" text, else `CONNECT_FAILED_TEXT`; or have the server add `reason: 'unreachable'` to its three reason-less bodies and drop the `!why` branch. Either way add the matching test row.

**t3. K3a's teaching toast option is untested.** `password-minigame.js:2240`.
No test checks that `teachAfter` passes `whole: true`; I could not find one outside `keyring-client.test.mjs`, which checks Connect's own teaching toast only. Removing the option there fails nothing. Add one assertion in `keyring-signin.test.mjs` on the `gameAlert` options.

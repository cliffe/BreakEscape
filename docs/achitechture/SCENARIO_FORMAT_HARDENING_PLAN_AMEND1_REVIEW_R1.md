### Majors

**M1. Section 2 and step 2 follow-up: the orchestrator's `_` key ruling has no step.**
- *Problem.* The ruling (the server ignores `_`-prefixed property keys as author notes; ids in id maps are not notes) appears nowhere in the plan. Step 2's build log on build/harden-step2 (R1 table, "Left as is") records the gap: `NetworkModel.grant_foothold_actions` (lib/break_escape/network_model.rb:254-273) walks every key, and `DeclaredGrants.executed?` (declared_grants.rb:96-112) looks only at the last path segments, so a grant inside `_draft.triggerOnInteract` is honoured at run time. `DeclaredGrants.collect` (declared_grants.rb:114-125) has the same shape for `give_item` grants. Other whole-tree walkers on the server: `CaptureModel` (capture_model.rb:158, 187), `OwnerClaim` (owner_claim.rb:190), `WearableModel` (wearable_model.rb:38, 65), and `Game#merge_biometric_samples!`'s known-owner walk (game.rb:354-363, which runs inside `sync_state`).
- *Why it matters.* Step 2 makes the validator skip `_` notes, so a grant or `give_item` in a note passes the validator silently while the server treats it as declared. A declared grant is part of what the server hard-enforces under the cheat policy (forged items, footholds), so a note widens the server's allow list. No corpus scenario has a structured `_` value today (491 `_comment`, 8 `_note` and four others, all strings), so nothing breaks now; the risk is the next author who comments out an action block.
- *Suggested change.* Add a small step (for example "2b", landing after step 2 and before step 3) with one plain-Ruby helper that says whether a key is a note: a `_` key is a note unless its parent is an id map (`rooms`, `networks`, `resources`, `roles`, `policies`, `accountProfiles`, `globalVariables`, an NPC's `needs`, and the rest of step 2's id-map list; a node test checks the list against the schema's `additionalProperties` maps). Apply it in the behaviour walkers: `grant_foothold_actions`, `DeclaredGrants.collect`, `WearableModel`, `OwnerClaim`'s walk, the biometric known-owner walk, and `validate_network.rb`'s grant walk so validator and server agree. Keep the secrecy walkers visiting `_` keys (the bootstrap and room filters, the capture-descriptor withholding, `CaptureModel`'s answer sets, step 3's `each_lock_answer`), because `_` notes ship to the browser today (nothing strips them) and skipping them there fails open. Say in 6a-1 that a leaf under a `^_` pattern key is class 4 (value check), never class 3. Say in step 7 that `retired_keys_in` and each step's transforms skip `_` notes. Tests: a `grant_foothold` and a `give_item` inside `_draft.triggerOnInteract` are not honoured through the real plant and give routes (each test fails with the skip removed); the same actions in a room whose id is `_annex` are honoured; one fixture run through both the validator and the server walk gives the same verdict.

**M2. Step 7, the client: the header check sits in a wrapper most game requests bypass.**
- *Problem.* The plan puts the check in `api-client.js` and says a tab's "next request after the upgrade sees the new number, whether that is a sync, a room fetch or a container fetch". On b7d500ccf the bootstrap is loaded by Phaser's loader (`core/game.js:1620`, `this.load.json`), the room fetch is a bare `fetch` (`core/rooms.js:981`), as are the container fetch (`container-minigame.js:373`), `update_room` (`room-state-sync.js`, five sites), `inventory` (`inventory.js:709`, `item-drop.js:157`, `consumables.js:235`, `apply-actions.js:58`), objectives (`objectives-manager.js`, six sites), flags, and ink. `sync_state` is a bare `fetch` on main (`state-sync.js:523`); on build/sync-deltas it goes through `ApiClient.put` except the unload flush (`state-sync.js:721`). The 409 refusal has the same gap: a 409 on `GET scenario` fails Phaser's file load, which shows no text.
- *Why it matters.* The node test (the wrapper reloads once) would pass while the live path never reloads on a room or container fetch, which is the "helper tests pass, live path breaks" pattern. The refusal page "shows that text" only for `show`, which is HTML.
- *Suggested change.* Name every client call site that reaches a games route (the list above, re-anchored on the main step 7 starts from) and route the check through one function they all call, or a single same-origin `fetch` hook installed at boot for `/break_escape/games/` URLs. State the refusal per route: `show` renders an HTML page with the message; JSON routes answer 409 with the message, and `core/game.js` shows it when the bootstrap load fails with 409. Add to the live proof: a tab open on a game, the server restarted with a test-only no-op step that raises CURRENT, then one sync and one room fetch each showing the single reload, and saving resuming after it.

**M3. Step 7: an absent `formatVersion` and "stops saving" can lose saves for every existing game.**
- *Problem.* With CURRENT 0, a game created before step 7 is never upgraded (0 is not below 0) and never stamped, so its `scenario_data` has no `formatVersion`. The plan says only that "the bootstrap carries `formatVersion`". If the bootstrap passes the stored value through (the top level is a deny list), the client sees `undefined` against header `0`, stops saving and reloads; after the reload the mismatch remains, the session flag blocks a second reload, and saving stays stopped for the session. That covers every production game of the four deployed scenarios.
- *Why it matters.* Silent loss of progress on Hacktivity, on the step that is meant to change nothing.
- *Suggested change.* The bootstrap writes `FormatUpgrade.version_of(scenario_data)` (absent is 0) as an integer, and the client compares numbers, treating a missing header as no mismatch. Key the session flag on the pair (stored version, header version) so a later release can reload again. After the one reload, a second mismatch shows a message asking the player to reload, never a silent stop. Before reloading, send the pending sync (sync carries no renamed key, and `sync_state` never upgrades), so the last seconds of play are not discarded. Node tests: a bootstrap with no field and header `0` does nothing; header `1` reloads once; a second mismatch after that reload shows the message and does not stop saving silently.

**M4. Step 7 and section 8 risks: re-running `prepare_scenario_data!` on a no-op upgrade changes deployed games.**
- *Problem.* "After the steps run at load, `prepare_scenario_data!` runs again." `upgrade!` returns the steps it ran, and from 8a on every production game of the four deployed scenarios runs step 1 (a no-op on their data) and is then re-prepared. `prepare_scenario_data!` was added on 2026-11-09 (12d0f5e65), so games created before then were never prepared: re-preparing applies `normalise_access_model!`, `NpcHabits.expand!` and the held-item id stamping (`<npcId>_held_<n>`, game.rb:5067-5076) to games in progress. The plan says "their games are only stamped", and the corpus equivalence check compares only freshly rendered templates, so nothing tests this.
- *Why it matters.* An in-progress production game can gain ids or filled fields that its player_state (KO drops pending, held items) was not built against. This is the one path where the plan touches deployed data while claiming to touch none.
- *Suggested change.* Each step's transform reports whether it changed anything; `prepare_scenario_data!` runs again only when one did. A no-op upgrade writes `formatVersion` and nothing else. Add a Rails test per deployed scenario: an unprepared render stored at version 0 (as a pre-11-09 game holds) upgrades to data equal to the input plus `formatVersion`.

**M5. Step 8, "The stored-game live proof": the swap tool does not make an old game.**
- *Problem.* `tools/playtest/swap-scenario-game.rb` sets `scenario_data` to the raw render and rebuilds player_state; it never runs `prepare_scenario_data!` (lines 42-67). A real stored game holds prepared data. `--rendered <file>` of the merge base's render therefore gives raw old data, and the branch cannot prepare it the old way (the new loader fills `habits.screen`, not `screenHabit`). 8c's proof on test_access_habits "with a preset-filled habit" tests nothing, because the fill exists only in prepared data. The plan also has no way to "seed player_state to hold the step's item": the tool rebuilds player_state.
- *Why it matters.* The stored-game proof is the safeguard the plan names for its riskiest step (8b) and the raw-versus-prepared question it raises itself ("Two data shapes").
- *Suggested change.* Make the old game with the old code: in a worktree at the merge base, render and prepare the scenario (`bin/rails runner` building an unsaved `Game` with the render and calling `prepare_scenario_data!`) and dump the prepared JSON, or create and play the game on a merge-base server on the builder's second port up to the beat (the shared database makes the row visible to the branch server). Give the swap tool `--prepared <file>` (stored verbatim, no prepare) and `--state <file>` (player_state merged after the rebuild, for the held phone or item). Record both files in the build log.

## What was verified and holds

- **Withheld work fields reach the browser by the real path.** `compile_npc_plan!` (game.rb:5722) attaches `work`, built by `AccessWork.plan` (access_work.rb:1147), only when `work_plan?` (access_work.rb:147) holds (a `work` need and a non-empty work list), so SIMS-9 depends on a valid top-level `resources` block, as 5.9 states. `withhold_npc_secrets!` (game.rb:5742) strips `workNeeds`, `frustration`, `feed` and keeps only `habits.screen`/`habits.print`. The plan resource's `offWhen` and `object` are copied into the plan entry at access_work.rb:1156-1157, and the browser's verdict reads the plan resource's `offWhen` (npc-work.js `failures`:63). The 5.9 note that "the `offWhen` must be on the resource" is correct.
- **Frustration is server-owned and bounded, and `sian_frustration` is a real synced global.** The level is held in `player_state['npcFrustration']` (game.rb:1782) and served back as `npcFrustration` (controller:435). The browser also mirrors it into the `${npcId}_frustration` global (npc-needs.js:2516), written only on a change, and again on reload only if it differs (npc-needs.js:2533), so SIMS-9's `sian_frustration` delta claim is accurate. `report_npc_uses!` caps at 20 reports, 20 missing, 8 causes (npc_frustration.rb:17-22) and refuses an oversized body before parsing (controller:35, 1432), so the per-NPC record is bounded.
- **Nothing grows with play time from the repeating beats.** Coupled-break and `room_entered` mappings carry no `onceOnly`/`maxTriggers`, so they never set `triggered.persist` (npc-manager.js:1431) and are never exported (npc-manager.js:2105). They fire indefinitely but write nothing synced. Objective ticks persist once each. Globals, `triggeredEvents`, `npcVisibility`, `npcHostility` sync as keyed-section deltas (state-sync.js:13), so only changed keys travel.
- **KO drops and player drops are cheat-safe for a secret-free floor.** A drop with `source_type: 'npc_defeated'` is accepted outside the NPC's scenario room only once the KO is recorded (game.rb:480, 499), must match an authored `itemsHeld` entry (`find_npc_held_item`, game.rb:1151), and dedups by id (game.rb:510). Carried world objects that are not in `itemsHeld` are refused, matching 5.1(b). Nothing here guards a secret, key or code, so the server's trust of the browser's KO claim is within cheat-resistance-policy (control-flow with a server sanity check).
- **Condition syntax is supported.** `safeEvaluateCondition` (npc-manager.js:25) handles `data.a.b.c === 'x'` at any dotted depth (resolveLHS:59, dig:45), `.includes(...)` on arrays (:94-99) and `&&`-joined `globalVars.` terms, so SIMS-1 Dee's `data.lockable.scenarioData.id`, SIMS-6's `data.skipped.includes('office_coffee')` and Neil's `&&` condition all evaluate.
- **Hacktivity fixtures untouched.** The plan adds `test_needs_attack` and extends `test_needs_sims`; it does not rename or delete `test_objectives` or `test_simple_success`, which Hacktivity resolves from BE main (hacktivity-fixture-scenarios). 3.1 states this correctly.

## m1 (minor): `WITHHELD_WORK_NPC_KEYS` contents mis-stated, with a stale line cite

The list is `%w[workNeeds frustration feed]` (game.rb:5706); there is no `usbHabit` key. The USB habit never ships because it lives in `habits` and the allow-list `SHIPPED_HABIT_KEYS = %w[screen print]` (game.rb:5714) drops every other habit key (game.rb:5750-5757), which the same sentence then states correctly for `habits`. The net effect is right, but the mechanism named is wrong. Section 5.9 (line 440) and 6.2 (line 492) also cite `game.rb:5624`/`5656-5657` for this constant; it now sits at 5706, applied at 5747. No slice here builds on a USB habit, so this does not affect the work.

Fix: in 6.2 drop `usbHabit` from the `WITHHELD_WORK_NPC_KEYS` sentence (leave the list as `workNeeds`, `frustration`, `feed`) and let the following `habits` allow-list sentence carry the USB habit; refresh the `game.rb:5624`/`5656-5657` cites to the constant names (`WITHHELD_WORK_NPC_KEYS`, `SHIPPED_HABIT_KEYS`) as the plan does elsewhere, since these are constants, not the function-anchored references the plan's convention uses.

## m2 (minor): reload inside the 6 s auto-print delay loses the print, and no proof covers it

The auto-print mapping (SIMS-1 Eli, SIMS-3 Neil) fires through `_scheduleDelayedMapping` (npc-manager.js:915), which calls `_handleEventMapping` only after `delayMs` (npc-manager.js:932-934); the `onceOnly` trigger is marked persisted only at that fire (npc-manager.js:1431). If the player reloads in the window after the conversation closes but before the 6 s print fires, the pending timer is lost and `conversation_closed:<npc>` does not re-emit on reload, so the page never prints and no reveal global is written. The plan's reload proofs (5.1(i), 5.3 third run) cover only a reload after the page has landed, where the behaviour is correct (the reveal global is set and synced, and the persisted `onceOnly` stops a reprint). This is a narrow, no-secret edge on a test floor, not a cheat or sync fault.

Fix: add one line to the SIMS-1 and SIMS-3 live proofs that reloads inside the delay window and records the outcome (no page, nothing printed) as the expected result, so the gap is documented rather than discovered in a mission that reuses the pattern; or note in the README that the auto-print is lost if the player reloads during the delay.

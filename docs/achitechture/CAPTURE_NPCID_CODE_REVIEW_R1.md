## What was checked

- The client sends `/feed_post` from one place: `ApiClient.post` (`public/break_escape/js/api-client.js:31`) with `Content-Type: application/json` and `JSON.stringify({ npc_id, object_id })`; the `liveDeps` fallback in `systems/social-feed.js:233` sends the same shape through `api.post`. There is no form-encoded, batched or `sendBeacon` sender. A form or non-JSON body is left untagged, so it falls back to the old rule, which is the safe direction.
- The server reveals for exactly `params[:npc_id]` when it is a String (`games_controller.rb` `feed_post`, `social_feed.rb:37`), with no trimming, and writes only `feedRevealed[id]`. The capture's untrimmed tag and the scanner's exact `tagged != npc_id` match that.
- A tag naming an NPC with no feed, or one not met (403, which `feed_unreadable?` skips anyway), credits nobody. That is stricter than before, not looser.
- Caps: a tagged row now counts for at most one NPC in both places that use `lost_answer_may_be?` (the share in `prepare_feed_base` and the per-row count in `note_feed_unreadable`), so the shares from tagged rows can never add up to more than the number of tagged lost rows. The 5 s time rule still applies to a tagged row.
- Tests without the fix: with `main`'s scanner, 3 of the 4 new Ruby tests fail (the untagged one is the regression pin and passes both ways). With `main`'s capture, the positive JS test fails and the "left out" test passes (see n1). On the branch: `access_leak_scanner_feed_test.rb` 29 runs, 0 failures; `playtest-session-capture.test.mjs` 8 pass.
- Live captures, game 1358: `npcid-responses-1358.jsonl` and `npcid-responses-1358-untagged.jsonl` both give "no leaks found", exit 0, with the same note for Jake (see n3).

## Minor

**m1. A query-string `npc_id` beats the body on the server, but the capture tags from the body.** `.claude/skills/playtest-scenario/scripts/response-capture.js:36-44` reads `npc_id` from `postData()` only. Rails 7.0.4 builds `params` as `request_parameters.merge(query_parameters)` (actionpack `http/parameters.rb:55`), so `POST /feed_post?npc_id=lena` with a body naming `jake` reveals Lena's post while the capture tags the row `jake`. A wrong tag loosens the check twice: Jake gets a share for a reveal he never had, and Lena's missing reveal moves to the first-line fallback (`tools/playtest/lib/access_leak_scanner.rb:815-824`), so a server bug that showed her post in a bootstrap before the lost row is no longer caught. The engine never sends `npc_id` in the query, so this needs a hand-written `eval` or `fetch` in a playtest. Fix: in `feedPostNpcId`, take the request URL too and return null (untagged) when its query carries `npc_id`; in the scanner, treat a row as untagged when `row['query']` has an `npc_id=` key, and when any readable `/feed_post` row has an `npcId` tag that differs from `body['npcId']`, ignore every tag in the log and print a note. Test both: a JS case with a query `npc_id`, and a Ruby case with a readable row whose tag and body disagree.

**m2. A tag widens the first-line fallback for the other NPCs, and the note then names the wrong cause.** `tools/playtest/lib/access_leak_scanner.rb:815-824`: when the only lost row is tagged for Jake, Lena's missing reveal is no longer credited from the lost row on but from line 1 (the first test asserts exactly this). That is right for a resumed game, as the spec intends. On a log that starts at a fresh game, though, it means a reveal the capture missed altogether (a response dropped between two capture files, a browser crash) now gets first-line credit where it used to get credit only from the lost row, which can hide an early bootstrap leak. The note at `tools/playtest/access-leak-check.rb:73-76` still says "a resumed game or a lost response body", though a tagged row has ruled out the lost body for her. Fix: add a third case to that note when the NPC's missing reveals are not covered by any row that may be hers (for example "no lost answer in the log was hers: a resumed game or a response the capture missed"), so the tester knows to check that the log began after her reveal. A stricter option, for a later round: give first-line credit only when the log's first `GET /scenario` already carries that NPC in `feedPosts`, and otherwise credit from the first row after which her saved `at` falls.

**m3. No test for a mixed log, or for a tag naming an NPC with no feed.** `test/unit/access_leak_scanner_feed_test.rb:261-305` covers one tagged row and one untagged row, each on its own. The spec says to cap the shares at the number of lost rows, and with untagged rows still under the old rule the sum can pass that number (one untagged row gives a share to every NPC it may be), which is the intended old behaviour but is not pinned. Fix: add (a) one row tagged `jake` plus one untagged row, both NPCs missing one reveal, asserting Jake and Lena each get exactly one share and that a Lena leak before the untagged row is still found; (b) one lost row tagged with an NPC that has no feed (for example `omar`), asserting neither Jake nor Lena gets a share from it.

## Nit

**n1. The JS "left out" test cannot fail on `main`.** `test/js/playtest-session-capture.test.mjs:145-157` passes with the old capture, since the old capture never writes `npcId`. It pins the guards, which is worth having, but it does not show the fix. Fix: put one valid tagged `/feed_post` in the same loop and assert that only that line has `npcId`, so the test fails if tagging is missing or too eager.

**n2. The skill doc's field list for the capture is out of date.** `.claude/skills/playtest-scenario/SKILL.md:297` lists "method, path, status, body and the session log `seq`" for `--capture-responses`. Proposed wording, for the user to apply (skill files are not edited in this review): "...method, path, status, body, the session log `seq` of the command that was running and, on a `/feed_post` line, the `npcId` its request named...".

**n3. The live sample does not exercise the change.** In game 1358 Lena's answer (line 8) kept its body, so only Jake has a missing reveal, and the tagged and untagged files give the same result and the same note. The unit tests carry the two-NPC case; a live proof of the difference would need two NPCs whose answers are both lost, or one lost answer with another NPC's reveal before the log began. No change needed unless a live proof is wanted.

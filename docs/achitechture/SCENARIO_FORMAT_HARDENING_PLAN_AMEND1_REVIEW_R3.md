## Claims the planner flagged as unchecked

- **TTS answers are not long-cached.** True. `tts` is `POST /games/:id/tts` (routes.rb:25), called by `ApiClient.getTTS` as a `fetch` POST (api-client.js:228). Every answer is a bare `send_file` or `render` (games_controller.rb:726-776) with no `expires_in`, `fresh_when` or `Cache-Control`. A browser does not reuse a stored POST response for a later request, so a TTS answer can never come back from cache with an old header. The plan's "the builder confirms ... and if they are cacheable, `tts` skips the callback" can be settled now (n1).
- **`grant_foothold` actions carry a `needsHeld` field that tells two copies apart.** True for the session shape only. `NetworkModel.grant_foothold_actions` (network_model.rb:253-272) records `needs_held: node['needsHeld']`, and `implant_foothold!` reads it only on the `session` branch (`inventory_item_matching(action[:needs_held])`, network_access.rb:478); the `dropped` branch reads `needs_dropped` (:492). test_access_networks uses the session shape with `needsHeld` (scenario lines 732, 813). The first-match test is buildable, but only if it names the shape (m2).
- **`pick` returns a JSON integer as a Ruby Integer.** True on this project's stack (Rails 7.0.4, pg 1.4.4, PostgreSQL 16; Hacktivity's Gemfile.lock has the same Rails and pg). Checked with `Game.unscoped.limit(1).pick(Arel.sql("'<lit>'::jsonb"))`: `1` gives Integer 1, `900` Integer 900, `-1` Integer -1, `"1"` String, `1.0` Float 1.0, `null` nil; `scenario_data->'formatVersion'` on a row without the field gives nil, and on no row gives nil. So `version_of` sees exactly the types its rules name.

## The planner's choices beyond the ruling

- **The re-prepend in `GamesController`.** Sound. `prepend_before_action` with a callback already in the chain goes through ActiveSupport's `CallbackChain#prepend`, which deletes the duplicate and puts the callback at the front, so repeating it after `prepend_before_action :refuse_oversized_body` (games_controller.rb:35) moves `set_format_header` ahead of it. It is the only `prepend_before_action` in the engine, and every engine controller inherits `BreakEscape::ApplicationController` (grep of `app/controllers`); Hacktivity subclasses none of them. The test (first `before` callback of every descendant, read from `_process_action_callbacks`) fails without the re-prepend, and the header test on `refuse_oversized_body`'s answer fails too. One wording gap: `StaticFilesController` skips the callback, so "every engine controller" must exempt it (n3).
- **`rescue_from ActionController::InvalidAuthenticityToken` answering 422.** Nothing in the engine relies on today's behaviour: the engine JS treats any non-OK answer as an error (`api-client.js:19-56`, `state-sync.js:684` checks only 403), and the one `csrf` code in the engine JS (`client-purchase.js:352`) comes from Hacktivity's own `PlayPurchasesController`, which has its own `rescue_from` and is unaffected. Engine tests run with `allow_forgery_protection = false` and assert nothing about the exception; Hacktivity's tests that touch CSRF are for its own controllers. Hacktivity's `ApplicationController` rescue (redirect to referrer) does not reach engine controllers, which inherit `ActionController::Base`. What does change is the HTML case in Hacktivity, and the JSON/HTML split is not defined for most engine fetches (m3).
- **The eight ambiguous names treated as ids everywhere.** Treating them as ids is safe where it is applied: none of the non-map objects under those names holds an action or a grant (the event mapping `needs` holds `print` or `set`, the others are social text, a wifi row list, a queue rule). But the count is ten, not eight, by the plan's own rule, and treating a name as an id map changes the context of every property under its object use, which breaks the rule one level down (M1, m1).
- **The `ID_MAP_KEYS` count.** Recounted with a script over `scripts/scenario-schema.json` at e13392d17, by the plan's naming rule (properties take their name, `items`, `anyOf`, `oneOf`, `allOf` and `$ref` keep it, a map's value takes `p.*`): 73 nodes whose `additionalProperties` is a schema, all reached and named, 61 names, none unnamed. The plan's figure is right. The list of names matches the plan's examples (`flipMontageByChoice.*` is among them).

### Blockers

### Majors

**M1. Step 2b, item 1: the run-time context does not match the schema names, so 13 id maps are read as notes, and open maps are left out.**
- *Problem.* Two gaps, both outside what the node test checks.
  - (a) `child_context(context, key)` returns `"#{context}.*"` whenever `context` is an id-map name, without asking whether `key` is a declared property of an object at that name. That holds for a pure map, but not where an id-map name also names an object with declared properties (the ambiguous names), or where a map node also declares properties. At run time those properties get the context `p.*`, not their own name, so a map under them is never recognised. Simulating `child_context` over the schema with the 61 names finds 13 map nodes reached under a context that is not in `ID_MAP_KEYS`:
    - `eventMapping.needs.set` (context `needs.*`: `needs` is the NPC's map, so an event mapping's `needs` object passes `needs.*` to `set`);
    - `socialTriageSet.labels.{callActions, kind, pushActions, queue, verdict}` (context `labels.*`);
    - `socialAwarenessEpisode.strings.{flipDefenderLineByChoice, flipMontageByChoice, stages, stepLabels}` (context `strings.*`), and so the values of `flipMontageByChoice`, which the plan lists as `flipMontageByChoice.*`, are never reached under that name;
    - `socialPhishTarget.replies.byChoice` (context `replies.*`) and `socialPretextCall.tells.techniques` (context `tells.*`): `replies`, `tells` and `socialPretextCall.labels` are nodes that are a map and declare properties at once.
    In each, a `_`-prefixed id is a note at run time: skipped by the granting walkers and deleted by `strip_notes!`. The plan's claim that the ambiguous names leave "no walker" changing "what it reads there" is true for the `_` key directly under the name and false for the maps one level down.
  - (b) `ID_MAP_KEYS` counts only nodes whose `additionalProperties` is a schema. Maps declared open, with `additionalProperties: true` and no properties, are id maps too, keyed by global, variable or VM names: top-level `flags` (keyed by VM name), `setGlobal` on `task.onComplete`, `socialPretextAsk.grants`, the three `socialPretextCall.outcomes.*` and `socialPhishTarget.outcome`, `setVariable` on `item.onRead` and `item.onPickup`, and NPC `externalVariables` and `persistentVariables`. A `_` global name in a task's `setGlobal` is therefore a note: `strip_notes!` removes it from the bootstrap. That contradicts the rule in section 2 ("an id in an id map is never a note, whatever its first character") and the guard "a `_` global name ... ship and work", which as written would pass on `globalVariables` alone.
- *Why it matters.* The corpus has no `_` id today (491 `_comment`, 8 `_note`, `_worked`, `_comment_r39`, `_comment_hints`, `_client`), so nothing breaks at once. But the node test compares two name sets computed by the schema rule, so it passes while the run-time walk disagrees with it, and a builder following the plan ships a helper whose central guarantee fails in 13 places plus every open global map, with a green test. These are the cases the step exists to get right.
- *Suggested change.*
  1. Make `child_context` property-aware for names that are both: a third frozen constant, `MAP_OBJECT_PROPERTIES`, maps each such name to the declared property names of its object uses (`needs` gives `print`, `set`; `labels` gives the triage-set and pretext-call properties; `strings`, `replies`, `tells` and the rest likewise). `child_context(context, key)` returns `key` when `key` is in `MAP_OBJECT_PROPERTIES[context]`, else `"#{context}.*"` for an id-map name, else `key`.
  2. Add the open id maps to `ID_MAP_KEYS` by a schema mark: `"x-id-map": true` on each `additionalProperties: true` node keyed by names (the list in (b)), and the node test counts marked nodes as maps. The other open objects (`voice`, `ttsVoice`, `creds.card`, `fx`, `bondVisualiserOpts`, `onAbort`, `onLaunch`, `timers` items) stay unmarked, so a `_` key in them stays a note. A new open map without the mark is then the one case the test cannot see; say so in the README note of item 8.
  3. Change the node test so it simulates the run-time walk: walk the schema computing each node's context with the same `child_context` rule (read from the Ruby constants), and fail if any map node, or any marked open map, is reached under a context not in `ID_MAP_KEYS`. On e13392d17 that simulation lists the 13 nodes above, so the test fails today and passes once item 1 is in.
  4. Add unit and guard cases: a `_` need name under an event mapping's `needs.set`, a `_` key under `socialAwarenessEpisode.strings.stages`, and a `_` global name in a task's `onComplete.setGlobal`, each an id that ships.
  Option (b) of round 2 (carry the schema node through the walkers) would also close this, at the cost of a schema load at run time.

### Minors

**m1. Step 2b, item 1: the ambiguous names are ten, not eight, by the plan's rule.** The plan counts `networks` as ambiguous because the triage page's `networks` is "a list of objects", so an array's object items carry the name. By that rule two more qualify: `accounts` (a map in `socialTriageSet.playerSentAuth`, and `social.mailClient.accounts[]`, whose items are `socialMailAccount` objects) and `domains` (a map in `playerSentAuth`, and `socialLandingBrand.domains[]` of `socialLandingDomain` objects, also `socialLandingMenuOption`). Counting bare arrays of strings as well would add five more (`facts`, `roles`, `rooms`, `stages`, `tells`), so the test needs the definition stated: a name is ambiguous when it is used for a node with `type` `object` or declared `properties` that is not a map, with array items carrying the property's name. Neither extra name holds a grant or a secret, so treating them as ids is safe. *Change:* state the definition, list ten names, and let the node test confirm it. Also fold in the three nodes that are a map and an object at once (`socialPhishTarget.replies`, `socialPretextCall.tells`, `socialPretextCall.labels`), which M1's constant needs.

**m2. Step 2b, Tests, the first-match case: name the shape.** "Where the two differ (a different `needsHeld`)" works only for the `session` shape: the `dropped` branch never reads `needs_held` (network_access.rb:492). *Change:* "two `grant_foothold` actions with `needsSession: true` for the same PC, the note-held one first with a `needsHeld` the player does not hold, the live one with a `needsHeld` the player holds and a different `name`: the implant succeeds and the stored foothold's `name` is the live action's". Without the skip, the note-held copy wins and the answer is `not_ready`, so the test fails as it should.

**m3. Step 7, "The header", the CSRF `rescue_from`: the JSON/HTML choice is undefined for most fetches, and the HTML branch changes Hacktivity's error page.**
- Most bare `fetch` POSTs send `Content-Type: application/json` but no `Accept` (for example `systems/room-state-sync.js:43`, 119, 168, 223), so `request.format` is not JSON and a `respond_to` would take the HTML branch for them. The header still comes back either way, so the wrapper works, but a builder needs a rule to write.
- In Hacktivity, an engine CSRF failure today reaches `config.exceptions_app` (application.rb:35), which renders Hacktivity's styled `errors/422` view with its layout. The plan's HTML answer, "the host's `public/422.html`", replaces that with Hacktivity's static page for the engine's HTML form posts (`games/new.html.erb:20`, 80, 134 and the preference forms). The header is of no use on an HTML navigation, since the wrapper sees only `fetch` responses.
- *Change:* answer locally only when the request is a JSON request by body or accept (`request.content_mime_type&.json? || request.format.json?`), with `{ "error": "invalid_authenticity_token" }` and 422; otherwise re-raise, so the host's error page is unchanged. The CSRF test then uses a JSON POST; add one assertion that an HTML form POST without a token still raises (with `show_exceptions` off in test).

### Nits

**n1. Step 7, "The header", TTS.** Replace "the builder confirms they are sent without long-lived cache headers, and if they are cacheable, `tts` skips the callback too" with the fact: `tts` is a POST answered by `send_file` or `render` with no cache headers, and a browser never reuses a stored POST answer, so the TTS answers keep the header.

**n2. Section 2, "Old games for live proofs", the runner script.** The order given (render, `prepare_scenario_data!`, `initialize_player_state`, `set_scoring_totals`) leaves out `sync_vm_set_id_column`, `resolve_imported_globals` and `set_started_at` (game.rb:32-37), and a `Game` still needs a host `mission` and a `player`, as the swap tool sets them. The simplest exact recipe: build `Game.new(player:, mission: <host>, scenario_data: <render>)`, call `prepare_scenario_data!` on the unsaved record (it does not save; game.rb:1199-1205), then `save!`, so `generate_scenario_data` returns early on the present data and the remaining `before_create` callbacks run in their real order.

**n3. Step 7, Tests, the first-callback test.** "`set_format_header` is the first `before` callback of every engine controller" fails on `StaticFilesController`, which skips it by design. Exempt it in the test, and assert there that the callback is absent.

**n4. Step 2b, item 1, walkers without a key path.** `OwnerClaim.mappings` (owner_claim.rb:183-195) also walks with `each_value`, so it carries no key either. Add it beside `merge_biometric_samples!`' `collect` and `scenario_objects`' `add`: it changes to `each` and passes the context down.

**n5. Step 2b, item 5.** `each_capture_writer` returns `enum_for(:each_capture_writer, data)` when called without a block (capture_model.rb:51), and most callers use that form. The new keyword must go through it (`enum_for(:each_capture_writer, data, notes: notes)`), or a `notes: :visit` caller silently gets `:skip`. One line in the plan saves a builder the trap.

**n6. Step 2b, item 1.** `accounts` is listed among "the access and office-life ones", but on e13392d17 the only `accounts` id map is `socialTriageSet.playerSentAuth.accounts`; the access model's accounts sit under `accountProfiles` and NPC `creds`. Move it to the social group.

## 2. Rules every step follows

- **Cheat policy.** The server hard-enforces secrets, keys and forged items; ink-gated steps and tailgating stay best effort with an NPC sanity check. A secret is any value that, read from the browser, lets a player skip a lock: a PIN, password, combination, cryptex word, flag answer, account password, Wi-Fi key, capture secret or a declared grant's contents. Steps 3 and 6 exist to keep every one of these on the server until it is earned.
- **Sync size rule (q77).** player_state and any per-game record the client re-sends must change by delta or stay bounded. Steps 1 to 6 add nothing to player_state and no new sync traffic; step 2b makes client payloads smaller by the author notes they carried; step 3 removes one key from the bootstrap and changes only which capture secrets and account passwords the server serves, read from the authored scenario per request, with nothing stored. Step 7 adds one integer to `scenario_data` (never to player_state), one integer to the bootstrap and one constant response header. Steps 8a to 8c rename keys inside item copies already stored in player_state, in place, on the server, once per game; a copy keeps its size or gains at most one short key, and nothing is re-sent because of it. Each step's section states its effect.
- **Tests.** Every step ships with node tests for validator behaviour (`test/js/validator-*.test.mjs`, the `check_*` function called through `ruby -e`, as `test/js/validator-pin-locks.test.mjs` does) and fixtures, Rails tests for any server change, and a corpus run of the validator over every scenario with the before and after counts in the build log. Builders run every test file their change touches plus every file that imports a changed module, without the shared lock; the orchestrator runs the full suites once per merge batch.
- **Corpus.** 177 `scenarios/*/scenario.json.erb` on b7d500ccf. build/del-scen deletes basic_mission and vm_free_mission, leaving 175; a step that lands after it counts 175.
- **Merge-batch validator rule.** Each merge batch runs the validator (`--no-graph`, ink on) on every test scenario a merged branch touched and needs 0 unlisted `❌` (the exit code, step 1).
- **Live proof** for every engine change (steps 2b, 3, 6b, 7, 8a, 8b and 8c, and any filter fix 6a's scan leads to): a keyless server on the builder's own port, a browser run through the real routes, and `tools/playtest/verify-run.rb` showing progress on the server. Helper tests alone do not count.
- **Author notes.** A `_`-prefixed property name is an author note (step 2's schema rule). From step 2b, no walker that grants, serves or derives access or footholds reads inside a note, every walker that keeps secrets on the server still visits notes, and no client payload carries a note. Whether a `_` key is a note is decided by the schema, through one resolver in `lib/` (`BreakEscape::ScenarioSchema`, step 2b) that every such walker walks beside the data: a key of an id map (a schema node whose `additionalProperties` is a schema, or one marked `"x-id-map": true`) is an id and never a note, whatever its first character; any other `_` key is a note. No list of names decides it anywhere.
- **Shared development database.** Every worktree's server uses one development database. A builder never upgrades a game it did not create for its own proof: no sweep (step 7's tool) runs against the development database except with `--dry-run`. A game upgraded by a newer branch refuses to load on older code (step 7), which is the intended, visible failure.
- **Old games for live proofs.** A proof that needs a game made before a step (steps 7, 8a, 8b, 8c) makes a real one with the old code, as the sync-deltas build did for its old-save case: a base worktree made by hand at `git merge-base main <branch>` (never with an isolation worktree, which can land in another repo), with its own keyless server on the builder's second port, sharing the development database. The common brief assigns each builder one port; the orchestrator assigns the second when it briefs a step with this proof. The old game is made by the base's own code, in one of two ways:
  - a scenario with a Mission row is created and played through the base server's real page;
  - a test scenario with no Mission row is made by a one-off `bin/rails runner` script run in the base worktree and not committed, in three steps: build `Game.new(player: <a player>, mission: <a host mission>, scenario_data: <the render>)`, as the swap tool picks a player and host mission; call `prepare_scenario_data!` on the unsaved record (it does not save, game.rb:1199-1205 on d8fb32450); then `save!`. `generate_scenario_data` returns at once on the present data, and every other `before_create` callback (`sync_vm_set_id_column`, `resolve_imported_globals`, `initialize_player_state`, `set_started_at`, `set_scoring_totals`, game.rb:32-37) runs in its real order. The game is then played on the base server's real page.
  Either way the game is played up to the beat, the base server is stopped, and the same game id is loaded on the branch's server, so the stored `scenario_data` and player_state are exactly what the old code wrote, prepared or not. `tools/playtest/swap-scenario-game.rb` is not used to make an old game: it builds player_state from the raw render before any preparation, which no created game holds. It stays for checks that need only a scenario (a test scenario's new game on the branch, the refusal of a too-new game). The base worktree runs no `db:` task and no migration, and is moved to `tmp/delete/` after the proof. The build log records the base commit, both ports, the game ids, how each old game was made and the beat played on each side.
- **No new gems or npm packages, and no database migration.** The validator already has `json-schema`; `formatVersion` lives inside the `scenario_data` JSON, so no column is added.

## 4. The steps

### Step 1. The validator's exit code matches its output

Built; on main at b7d500ccf. The specification stays here because steps 3, 6a and 7 reuse its list format, its decisions file and its message rules.

**Why.** `scripts/validate_scenario.rb` exits 1 only for directory, structure, schema, ink-compile, ink-check and graph-key failures (on 33c003230: lines 6748, 6770, 6818 for the schema, 6854 for ink, 7003, 7065, 7076). Every other `❌` is printed and the run ends with `exit 0` ("warnings don't cause failure", lines 7089-7091). On a schema or ink failure it exits early, before the common issues, habits report and work report are printed, so an author meets a second wave of errors after fixing the first. Agents are told to count `❌` lines by hand.

**Change.**
1. Fix the false positives and the true errors in this build's test scenarios, and the schema-failing fixtures this build owns (the build log, step 1, lists them).
2. One label. Every hard finding is `❌ ERROR:`. Today there are `❌ INVALID` (108 sites in validate_scenario.rb), `❌ ERROR` (53 there, 117 in validate_npc_needs.rb) and `❌ SOCIAL` (validate_social.rb). The rename is mechanical and the text after the label stays: social lines become `❌ ERROR: SOCIAL: <text>`, so the existing tests that match `SOCIAL: schema:` keep their match. Tests that match on an old label are updated in the same commit (see Tests, the audit).
3. Schema errors print as `❌ ERROR: schema: <json pointer>: <message>`, with the opaque schema id removed and, where the pointer reaches a room, object or NPC, its id or name added.
4. Print every section before deciding the exit code. Neither a schema failure nor an ink-check failure exits early; an ink compile failure still skips the checks that need the compiled JSON, and says so. The common checks assume schema-shaped data (`rooms` a Hash, `objects` Arrays) and today never see data that failed the schema, so each check call runs under its own rescue: one per `common_issues += ...` line (the common stage is 19 such calls, validate_scenario.rb:6949-6970 on 33c003230, including `ValidateNpcNeeds`, `ValidateAccessWork` and `ValidateNpcHabits`) and one per ink, schema, habits, work and social call. An exception prints `❌ ERROR: <check name> could not run: <message>`, counts as an error, marks that stage as not run in full, and the run continues with the next call, so one crashing check never hides the checks after it.
5. Count by construction: all output goes through one writer that counts lines starting with `❌` and tags each with the stage that printed it (`ink`, `schema`, `common`, `habits`, `work`, `social`), so a module that prints its own lines cannot slip past. The run ends with `Result: <n> errors (<k> known), <m> warnings` (step 3 adds `, <c> acknowledged clues`), plus `<j> known failures not checked (<stage> skipped)` when a stage did not run in full. It exits 1 when an unlisted error remains.
6. Social schema errors become fatal on every run. Today `ValidateSocial.split_schema_errors` (`validate_social.rb:94`) moves `#/social` schema errors into the social lints, which fail the run only under `--strict-social`. The corpus has none, so nothing changes today, but the builder states it in the README's validator section.
7. `--strict-social`. The CI social job (`.github/workflows/ci.yml:144`, `--strict-social --no-graph --skip-ink` under `set -euo pipefail`) went green when build/c3-replies merged. After step 1, `--strict-social` adds nothing and stays accepted, because CI passes it.
8. The known-failures list (below).
9. Wording. Six skills mention `❌` or `INVALID`: validate-scenario, scenario-design-review, mission-puzzle-chains, walkthrough-scenario, npc-dialog-review and break-escape-dungeon-graph. The builder proposes new wording for all six to the orchestrator (the exit code is the answer; a listed failure prints with its owner; the label is `❌ ERROR:`), and edits the README validator section in the branch. The "count every `❌`" rule lives in the orchestrator's common brief for builders, not in the repository, so the builder proposes its replacement line to the orchestrator ("the validator's exit code is the answer: 0 means no unlisted `❌`"). AGENTS.md gains one line, in its validator paragraph: "The validator exits 1 on any `❌` not in `scripts/validator_known_failures.json`; each merge batch diffs that file and `test/fixtures/files/payload_scan_exceptions.json` and greps for `acknowledgedClues`, and every added entry or marker needs a dated sign-off in `docs/agents/VALIDATOR_DECISIONS.md`." (The exceptions file arrives with 6a-1, which adds its name to this line if step 1 lands first.)

**The known-failures list.** Step 1 lands before every other track has fixed its lines, so the gap is held in a file the validator reads, never in a build log.

- `scripts/validator_known_failures.json`: an array of entries `{ "scenario", "stage", "match", "count", "owner", "added", "reviewBy", "approved", "note" }`.
  - `scenario` is the repo-relative template path, the form the validator receives: `scenarios/<dir>/scenario.json.erb`.
  - `stage` is one of `ink`, `schema`, `common`, `habits`, `work`, `social`, the stage whose line the entry matches.
  - `match` is a substring of the `❌` line that does not depend on line numbers (for example `contains '//'`); `count` is how many lines of that scenario and stage it covers, exactly. An entry never matches a `could not run`, `stale known failure` or `Result:` line: the validator skips those lines when matching, so a crashing check or a stale entry always counts.
  - `added` and `reviewBy` are ISO dates; `owner` names a track or person (labs track, escape-room track, the m08 owner).
  - `approved` is the exact text of a heading in `docs/agents/VALIDATOR_DECISIONS.md`, where the orchestrator recorded the sign-off for this entry. The file is created by step 1, holds one dated heading per approved entry (`## 2026-11-14: lab_exploitation ink headings`), and does not depend on the pass name, so a pass change never breaks an entry. Under each heading the orchestrator writes one fenced `json` block that restates the identifying fields of the one entry it approves, with the same values: `scenario`, `stage`, `match` and `count` for a known failure; `lock`, `in` and `reason` for an acknowledged clue (step 3); `scenario`, `route` and `paths` for a payload scan exception (6a-1). Prose may follow the block. The tests parse that block and nothing else, so all three lists share one reader (a small helper in the node test directory). A heading backs exactly one entry across all three lists; a second entry needs its own heading.
- The validator reads the list by default (`--known-failures <file>` to point elsewhere, `--no-known-failures` to see the raw result). A matched line still prints, marked `(known: <owner>, since <added>)`, and does not count towards the exit code. An unmatched line counts.
- **Stale entries.** For an entry whose stage ran in full on this run, fewer lines than `count` prints `❌ ERROR: stale known failure: <scenario> <stage> '<match>' now matches <n> of <count>; update or remove it`, and more lines than `count` counts the extra ones as unlisted. For an entry whose stage did not run in full (`--skip-ink`, an ink compile failure, a section that raised), the entry is not checked and is counted in the `not checked` line. So `--skip-ink` runs, including CI's social job, never fail on a listed ink line.
- **Swaps within an entry are accepted.** Fixing one `contains '//'` line and adding another in the same scenario keeps the count and passes. The swap stays within one owner, one stage and one class of line, which is what the entry already allows.
- **The node test** (`test/js/validator-known-failures.test.mjs`) checks each entry: the scenario file exists; `stage` is one of the six; `match` and `owner` are non-empty; `count` is positive; `added` and `reviewBy` are valid dates with `added` not in the future; `approved` appears as a heading in `docs/agents/VALIDATOR_DECISIONS.md`, and the fenced `json` block under that heading holds this entry's `scenario`, `stage`, `match` and `count` with the same values; no two entries (across this list, every `acknowledgedClues` list and the payload scan exceptions file, once 6a-1 adds it) name the same heading; `match` does not contain `could not run`, `stale known failure` or `Result:`; and `match` is not a substring of `❌ ERROR: ` (which every line holds, so such an entry would match anything). The validator's skip of those three line kinds is the runtime guarantee; the test stops an entry that was written to aim at them. An added entry or a raised `count` therefore needs a new or edited section in the decisions file, which shows in the branch diff; the merge-batch diff below is the second line of defence.
- **A passed `reviewBy`** (here, and on a payload scan exception, 6a-1) prints a warning and skips that assertion, unless `MERGE_BATCH=1` is set, when it fails. The orchestrator sets `MERGE_BATCH=1` for the merge-batch suites, so a date passing never turns main or an unrelated branch red, and the decision is forced at the next batch.
- **Merge-batch check.** Each batch runs `git diff <main>...<branch> -- scripts/validator_known_failures.json test/fixtures/files/payload_scan_exceptions.json` for every merged branch, and stops on any added entry or raised `count` that the batch notes do not name. The orchestrator signs off each one in `docs/agents/VALIDATOR_DECISIONS.md` under the heading the entry's `approved` names. AGENTS.md states this in the one line item 9 adds.
- This build's own fixtures are fixed, never listed.
- **First contents**, if the owners have not fixed their lines when step 1 lands: the 6 VM labs (labs track, 49 lines in 8 entries, 47 of them `stage: ink`), and the 5 escape rooms (escape-room track, 24 lines in 6 entries). Each with a `reviewBy` the owner agrees and an `approved` heading the orchestrator writes.

**When it landed.** After this build's lines and fixtures were fixed and every remaining line was fixed or listed. Step 1's own corpus run produced the list's first contents, so no line was listed by guesswork.

**Tests.**

### Step 2b. Author notes are not live

**Why.** Step 2 makes `_`-prefixed property names author notes: the schema accepts any value under them and the validator's `grant_foothold` walker skips them. The server does not agree. `NetworkModel.grant_foothold_actions` (`lib/break_escape/network_model.rb:254-273` on d8fb32450) walks every key and asks `DeclaredGrants.executed?` (declared_grants.rb:96-112), which looks only at the last path segments, so a `grant_foothold` inside `_draft.triggerOnInteract` counts as declared. `POST network/implant` reads that list (`network_implant`, then `Game#implant_foothold!` and `grant_foothold_action_for`, network_access.rb:423-450 on d8fb32450), so it honours the note-held action. `grant_foothold_action_for` takes the first match per PC and shape (`.find`), so a note-held copy placed before the real action would also win over it. `DeclaredGrants.collect` (declared_grants.rb:114-125) has the same shape for `give_item` grants, and through `NetworkModel.rogue_device_definitions` it also decides which rogue devices `POST network/plant` accepts. A declared grant is part of what the server hard-enforces under the cheat policy (forged items, footholds), so an action an author commented out by moving it under `_draft` widens the server's allow list while the validator says nothing. Notes also ship: nothing strips them from client payloads today, so a secret an author parks in a note reaches the browser unless a recursive filter happens to catch it. The corpus holds no structured `_` value today (491 `_comment`, 8 `_note` and four others, all strings), so nothing breaks now; the risk is the next author who comments out an action block or keeps an old password beside a new one.

**When it lands.** Right after step 2, in its own batch, and before steps 3, 7 and 8a: every step 8 transform and step 7's `retired_keys_in` use the helper, and step 3's walks visit notes by item 4 below.

1. **One schema resolver in `lib/`, so the schema is the single source.** Step 2's validator already tells a note from an id by walking the schema beside the data (`validate_grant_foothold_actions`, with `schema_deref`, `schema_resolve`, `schema_map_value` and `schema_node_keys`, validate_scenario.rb:236-400 on e13392d17). Step 2b moves that resolution into `lib/break_escape/scenario_schema.rb` (`BreakEscape::ScenarioSchema`), plain Ruby (`json` only), required with the guarded form the other lib files use. A Node is the set of schema locations that may describe the value, after following local `$ref`s and flattening `allOf`, `anyOf` and `oneOf` into their branches, keeping the branches that can hold the value's kind (an object for a Hash, an array for an Array). ### Step 3. Secret-leak check, with acknowledged clues

**Why.** Nothing stops an author copying an answer to a place the browser receives at game start. `globalVariables` ships in the bootstrap and in player_state; `minigameData` ships with the room. m08 already does it: `suite_code = "5386"` (scenarios/m08_the_mole/scenario.json.erb:117) is a global so that Netherton's voiced ink can say it, which puts the interrogation-suite PIN in the browser from the start. Separately, the server strips `requires` only when the node's own `lockType` is present and is not biometric, bluetooth or rfid (game.rb:4697-4699 and games_controller.rb:1930), so `"locked": true, "requires": "4821"` with no `lockType` ships the PIN, and so would a door entry with a PIN in `requires` and no `lockType` of its own.

**How a lock type is resolved.**
- A room, object or item: its own `lockType`.
- A `rooms.*.doors[]` entry: the entry's `lockType`, else the connected room's. This is the client's rule: the client takes the `doors[]` entry whose `connectedRoom` and `direction` both match (`public/break_escape/js/systems/doors.js:494` and 565) as the door's lock properties and fills each gap from the connected room (lines 526-527: `lockType: lockProps.lockType || connectedRoomData?.lockType`, `requires: lockProps.requires || connectedRoomData?.requires`), copies the result into the sprite, and the gate code reads `props.requires` for the clone-as-entry credential and the door sign (`door-gates.js`). A card id in a door entry's `requires` is live on the client.
- **The server checks the room.** The server validates a door unlock against `room_data(target_id)` alone (`Game#validate_unlock`, game.rb:2701, and the rfid and mastermind helpers it calls). It never reads a door entry's `requires` or `lockType`. A door entry's `requires` is therefore a client-side value (the gate sign, clone-as-entry), and the step says so in the README's door section. A door entry PIN that differs from its room's opens nothing on the server, so withholding a capture secret equal to it (below) is harmless but protects nothing; it is not a new lock.

- **One normaliser.** `CaptureModel.answer_key(lock_type, value)`, plain Ruby (no ActiveSupport), returns a String or nil:
  - `combination`: the existing `numbers` lambda from `Game.lock_answer_matches?` (game.rb:2684 on e937b75f8), moved verbatim: an Array's elements are converted with `to_s` and stripped, a String is split on `/[^0-9]+/`, empty parts are dropped, and any part that is not all digits gives nil. The result is `"combination:"` plus the integers joined by `-`, so `[12, 30, 5]`, `"12-30-05"`, `"12 30 5"` and `"L12 R30 L5"` all give `"combination:12-30-5"`. No numbers at all (`nil`, `""`, `"twelve"`, `[]`) gives nil.
  - `cryptex`: nil unless the value is a String whose `strip` is non-empty; otherwise `"cryptex:"` plus `strip.downcase(:fold)`. The server compares a cryptex today with `casecmp?`, which applies Unicode case folding, and `downcase(:fold)` is the same folding (checked: `"ÉCOLE"` and `"école"`, `"Straße"` and `"STRASSE"` agree under both), so the comparison is unchanged. A unit test asserts that the two agree for every cryptex answer in the corpus and for those two pairs.
  - Every other kind: nil for nil or a value whose `to_s` is empty; otherwise `"<kind>:"` plus `to_s`, exactly. Passwords and PINs stay exact because the server's unlock compares them with `to_s ==` (`Game#validate_unlock`); folding their case would withhold values that open nothing.

    false
  end

### Step 6. Secrecy as a schema property

**Why.** Which values are secret is decided by hand-kept lists, and the format does not show them:
- The bootstrap (`Game#filtered_scenario_for_bootstrap`, game.rb:1094-1186) allow-lists room fields but deny-lists the top level by name: `flags`, `accountProfiles`, `roles`, the network keys, feed facts, capture secrets, grant contents, `targetFlags`. A new secret-bearing top-level block ships unless someone adds it to the list.
- Two near-copies strip `requires` with the same rule, keyed on the node's own `lockType`: `Game#filter_requires_and_contents_recursive` (game.rb:4668) and `GamesController#filter_requires_recursive` (games_controller.rb:1917, called on the bootstrap at line 286). build/unlock-gaps-r1 adds `strip_lock_answers!` (combination and cryptex answer copies, and start-inventory answers) to both.
- Per-feature lists: `WITHHELD_NPC_KEYS` and `WITHHELD_WORK_NPC_KEYS` (game.rb:4783-4787), `NetworkAccess::WITHHELD_OBJECT_FIELDS`, the `puzzle_graph_*` strip, `DeclaredGrants`, and the capture-descriptor walk that withholds every `capture`, `addCapture` and `usePayload` secret at any depth.
- 33 schema descriptions say "never sent to the browser" in prose; nothing machine-readable.

Once unlock-gaps-r1 is in, no leak is known in these filters. Step 6 therefore starts with marks and scans that would catch the next one (6a), and replaces the filters (6b) only if the scans find a gap.

**Two shapes of response.**
- *Subtree payloads:* the authored part of `GET scenario` (the top level and rooms), `GET room/:id`, `GET container/:id` and the bootstrap's `playerInventory`. Each is a filtered copy of authored data, so each response leaf has a source path: the route's subtree root plus the leaf's relative path (for an inventory item, the authored path of the item with that id). The path check applies to these payloads only.
- *Constructed answers:* `GET network` rows, `GET login_accounts` tiles, the bootstrap's `feedPosts` and `POST friendface_phone`, and the other server-added bootstrap keys. The server builds them, so their leaves have no authored source path, and they are judged by value only.

**Where a leaf came from: four classes.** The scan puts every response leaf in one class by its source, and step 3 stays the single judge of authored clue text:
1. **A source path marked `x-serverOnly`** (with the resolved lock type for `requires`, and the lock-type condition for `combination`), on a route its `x-servedBy` does not name: fails (the path check).
2. **A source path under `globalVariables`, `minigameData` or `scenarioData`:** step 3's leak rule, with acknowledged clues. A constructed leaf that copies a global (`savedGlobalVariables`) is judged here, as that global. This is close to, but not exactly, step 3's verdict: step 3 reports only a match found under both seeds, and the scan renders once under `srand(1)`, so a coincidence under seed 1 alone fails the scan on every run while step 3 stays silent. Such a case goes to the exceptions list with that reason.
3. **A source path that is a declared field with no mark** (a note's `text`, `postitNote`, `observations`, a name): passes. This is authored clue text, which step 3 already allows.
4. **A source path the schema does not declare** (an unknown key on an open core kind; a leaf under an author note is not in this class, see below), **or no source path** (a constructed answer): the value check. It fails when the leaf matches an authored secret value by step 3's rule (equality after the text forms, or a whole word inside a string leaf for an answer of 6 or more characters), unless that value is also authored in a field whose `x-servedBy` names this route (and, where the mark names a key, the leaf sits under that key). So a written-down password passes in a `GET login_accounts` tile's `postitNote`, a feed post's text passes in `feedPosts`, and a joined network's `psk` passes in `GET network`; the same values fail anywhere else in class 4.
   **An author note in a payload** is a finding whatever its value: step 2b strips every `_` property note from every client payload, so a note the scan meets means a route missed the strip. A `_` id in an id map is not a note (`AuthorNotes.note?`).

### Step 7. `formatVersion` and the load-time upgrader

**Why.** A game stores the rendered scenario at creation (`before_create :generate_scenario_data`, game.rb:33; `Game#generate_scenario_data`, game.rb:4992 on b7d500ccf), and the access loader `prepare_scenario_data!` (game.rb:1097 on b7d500ccf) runs only then. A stored game keeps the names the format had on the day it was made, so every reader must accept every old spelling for as long as old games exist; the `key_id` to `opens_lock` fallbacks in `window.lockRef` and `lib/break_escape/item_identity.rb` show the cost. An ordered list of upgrade steps keyed on a version number lets every reader see only the current names. Step 7 builds the mechanism with no renames, so it is proven on its own before step 8a puts the first rename in it.

**formatVersion.**
- A top-level integer in `scenario_data`. 0 is the format before step 8a: every game created before step 7, and any data with no field. Step 8a makes it 1, 8b 2, 8c 3. Each later change that renames a stored field adds one.
- **A missing field is 0, everywhere.** One reader on the server, `FormatUpgrade.version_of(data)`: an absent or nil `formatVersion` is 0; a non-negative Integer is itself; any other value (a string, a float, a negative number) raises `FormatUpgrade::Unreadable`, which refuses the game as a too-new one does (below), because only the server writes the field. Every server path that needs the version calls it; none reads `data['formatVersion']` directly. The client applies the same rule to the bootstrap (below).
- `BreakEscape::FormatUpgrade.current` (in `lib/break_escape/format_upgrade.rb`) is the code's version: a method that returns the `version` of the last entry in `STEPS`, or 0 when `STEPS` is empty. It is a method, never a constant, so nothing caches an old value and the test switch below needs no constant reassigned. Step 7 lands it as 0. "CURRENT" in this plan means its value.
- Templates never carry it. A rendered template already has the current names (the validator rejects retired keys, below), so the server stamps the number. The validator errors on a template that sets `formatVersion` ("the server stamps formatVersion at creation; remove it").
- Stamped at creation: `Game#generate_scenario_data` sets it to CURRENT after `prepare_scenario_data!`. When the caller supplies `scenario_data` (the method returns early when it is present, which tests use), a `before_create` stamps CURRENT if the field is absent; an upgrader test that wants an old game sets `formatVersion: 0` itself. `tools/playtest/swap-scenario-game.rb` stamps CURRENT on the data it swaps in, and gains `--format-version <n>` for the refusal proof only (the proof uses 900, far from any real format). It is never used to make an old game (section 2, "Old games for live proofs").
- **A game created before step 7 is never written because of step 7.** Its `version_of` is 0, equal to CURRENT, so it is not upgraded and not stamped; the bootstrap reports 0 and the header says 0, so the client neither reloads nor stops saving. It is stamped by the first step that raises CURRENT, and only then.
- Declared in the schema as a top-level integer, minimum 0, and shipped in the bootstrap, because the client's reload check reads it (6b marks it `x-client: true`).

**The upgrader.** `lib/break_escape/format_upgrade.rb`, plain Ruby (no Rails), required with the guarded form the other lib files use.
- `STEPS`: an ordered list, one entry per version: `{ version:, name:, scenario: ->(data) { ... }, player_state: ->(state) { ... }, retired: [{ path:, key:, now: }] }`. Both transforms change their argument in place, are idempotent, and leave data that already has the new names unchanged. Neither reads or writes inside an author note: each walks with step 2b's resolver (`ScenarioSchema.root` for `scenario`, `#/definitions/item` for each item copy in player_state) and skips what `AuthorNotes.note?` calls a note, so a note that names an old key, or holds an old-shaped block, is left as written. `retired` lists the keys the step removes, the path pattern where each lived and its new spelling; the validator and step 2's message read it.
- `ALIASES`: old keys a deployed scenario still uses, each with the step that retired it. Empty (section 1). An alias would be applied to a freshly rendered template at creation, between `mission.generate_scenario_data` and `prepare_scenario_data!`, and by the validator and `scripts/generate_dungeon_graph.rb` on their rendered copies (one call, `FormatUpgrade.apply_aliases!`). Those are the only places an old name would be read; no reader in the engine JS, Rails or the validator's checks keeps a fallback, because every copy they see has passed through one of them or through the load-time upgrade.
- `upgrade!(data, state)`: reads `version_of(data)`, runs each step above it in order on both, sets `formatVersion` to CURRENT and returns `{ ran: [<step names>], scenario_changed: <true or false> }`. A stored version above CURRENT raises `FormatUpgrade::TooNew`.
- **What "changed" means.** Before the first step runs, `upgrade!` takes a deep copy of `data` without `formatVersion`, as `Marshal.load(Marshal.dump(data))` (`format_upgrade.rb` is plain Ruby, so ActiveSupport's `deep_dup` is not used). After the last step, `scenario_changed` is true when `data` without `formatVersion` is not `==` to that copy (Ruby Hash and Array equality, key order ignored). A step's own report is not trusted for this; the comparison is the definition. player_state changes do not count, because `prepare_scenario_data!` reads and writes only `scenario_data`. The copy is taken once per upgrade, which happens once per game.
- `retired_keys_in(data)`: every retired key present in rendered data, with its path and new name, skipping author notes the same way (`AuthorNotes.each_live` from the root).

**Two data shapes.** A stored game holds prepared data (`prepare_scenario_data!`: `normalise_access_model!`, `stamp_scenario_object_ids!`, `NpcHabits.expand!`, which writes filled habits into the data), except a game created before 2026-11-09 (commit 12d0f5e65 added the loader), which holds the raw render. Each step is written against raw-shaped fields and must accept both shapes.

**Re-preparing only what changed.** `Game#ensure_current_format!` calls `prepare_scenario_data!` again only when `upgrade!` reports `scenario_changed: true`. A game the steps did not change has `formatVersion` written and nothing else, so an unprepared game stays unprepared and a prepared one keeps the ids and fills it was played with. This matters for every game of the four deployed scenarios, which steps 8a to 8c do not change: re-preparing a pre-11-09 game would add `normalise_access_model!` fills, `NpcHabits.expand!` fills and held-item ids (`<npcId>_held_<n>`, game.rb:5067-5076 on b7d500ccf) that its player_state (pending KO drops, held items) was not built against. Only games of the test scenarios and lab_physical_pentest that a step rewrites are re-prepared, and each step's tests show that upgrading prepared data and preparing again gives the same result as preparing the new template.

**When it runs.**
1. **At load, on the server, always.** One helper, `Game#ensure_current_format!`, runs `with_lock { reload; upgrade if still old; save }` when `version_of(scenario_data)` is below CURRENT. It is called from `set_game` (games_controller.rb:1932 on d8fb32450, a plain `Game.find` today) and from every other path that reads `scenario_data` without `set_game`. The builder lists those paths (`grep -rn scenario_data app lib`) in the build log, each either calling the helper or shown not to read a renamed key. `with_game_lock` covers only some routes (games_controller.rb:2091 on d8fb32450) and leaves out `show` and `scenario`, which run first on a load, and the client fetches rooms while the bootstrap is in flight; the row lock and the reload inside it mean a second request finds the work done. A game already at CURRENT costs one integer comparison.
2. **`sync_state` never upgrades.** It loads only `SYNC_STATE_COLUMNS` (games_controller.rb:1955 on d8fb32450) under the same row lock (`Game.lock.select`), and it refuses a game stored above CURRENT before writing anything ("Refusal", below), so a sync and an upgrade never interleave: the sync writes either before the upgrade, which then sees its write, or after it, on upgraded player_state. Sync does read stored `scenario_data`, in two places: the biometric known-owner walk reads `fingerprintOwner` (`merge_biometric_samples!`), and `stored_scenario_data` (game.rb:784 on d8fb32450) feeds the capture sync step. Neither `fingerprintOwner` nor any capture field is renamed by steps 8a to 8c. The rule for later steps: a step that renames a key sync reads, or anything a sync writes (globals, NPC state, timers, clocks), must upgrade inside sync or refuse the sync; each step's section confirms which applies for its keys.
3. **Readers outside the engine.** Hacktivity code that reads or writes a game's `scenario_data` or player_state, found read only (Hacktivity is not edited by this plan):
   - `app/services/user_anonymiser.rb:121-124` reads `scenario_data['player']` and writes the whole `scenario_data` back with `update_columns`, outside the game's row lock. If an upgrade runs between its read and its write, it writes back the pre-upgrade `scenario_data` (with the old `formatVersion`) over a game whose player_state the upgrade already changed. The upgrader handles that mixed state: the next load sees the old version, runs the step's `scenario` transform again, and runs the idempotent `player_state` transform on already upgraded state, which changes nothing. A unit test covers it (below). This is listed for the user as a known interaction; taking the game's row lock in the anonymiser would close it, and is the user's call.
   - `app/services/event_progress.rb:338` uses `score_breakdowns`, not `scenario_data`.
   - `lib/playtest/solve.rb:20` and `:464` read `scenario_data['flags']`, which no step renames.
   - `app/services/game_slot_start_service.rb:56` seeds player_state before creation; `app/controllers/game_slots_controller.rb:146` calls `reset_player_state!`. Neither reads a renamed key.
   Any Hacktivity reader of a key a later step renames goes to the user before that step lands.
4. **A tool, optional.** `tools/format/upgrade_games.rb`, run with `bin/rails runner`, walks games in batches of 100, each through the same helper under its own row lock. `--dry-run` reports counts per stored version and per step, and how many games each step would change, and writes nothing. It lets a release upgrade games before players load them; load time stays the guarantee. It never runs without `--dry-run` against the shared development database (section 2). `lib/tasks/break_escape_migrate_key_id.rake`, the earlier one-off migration of stored `key_id` names, stays as it is: it predates `formatVersion` and is not replaced. Turning the `key_id` to `opens_lock` fallbacks into a `FormatUpgrade` step is later work, filed with the closure (section 7).
5. **The validator and the dungeon graph** render templates, which carry current names, so they run no step. The validator calls `retired_keys_in` (below).

**Refusal.** A stored `formatVersion` above CURRENT (code rolled back after games were upgraded, or an older worktree opening a game a newer branch upgraded), or an unreadable one, does not load. Nothing is written. The message is "This game was saved by a newer version of Break Escape (format <n>; this server reads up to <m>)", or "This game's saved format cannot be read" for an unreadable value. One body is used for every JSON refusal: `{ "error": "format", "message": "<the message>", "current": <CURRENT> }`. Per route:
- `show` (HTML) renders a page with the message, styled with the game's pixel fonts and 2px borders.
- Every JSON route that goes through `set_game` answers 409 with the body above, from `set_game` (games_controller.rb:1932 on d8fb32450), before any other work.
- `sync_state` does not go through `set_game` (it loads `SYNC_STATE_COLUMNS`, games_controller.rb:802 on d8fb32450), so it gets its own check. Inside its transaction, after `Game.lock.select(*SYNC_STATE_COLUMNS).find` and the `authorize`, and before `stale_sync_request?` or any merge, it plucks the stored version under the same row lock (`Game.where(id: @game.id).pick(Arel.sql("scenario_data->'formatVersion'"))`, one jsonb read; `pick` returns the JSON value as a Ruby Integer, nil or another type) and passes it to `FormatUpgrade.version_of`. Above CURRENT, or `Unreadable`, it rolls back and answers 409 with the same body. So a tab on newer code than its server, or a server older than its game, writes nothing to player_state. `sync_state` still never upgrades: a version below CURRENT is synced as today and upgraded on the next load.
- The bootstrap (`GET scenario`) is loaded by Phaser's loader (`core/game.js:1621`, `this.load.json`), which shows nothing on a failed file. `core/game.js` listens for the loader's `loaderror` on the `gameScenarioJSON` key; on it, it fetches the same URL once with `fetch`, and when the answer is a 409 with `error: "format"` it shows `message` in the `#loading` element as plain text (`textContent`) and stops the boot. Any other failure keeps today's behaviour.

**The client.**

Most engine `fetch` POSTs send `Content-Type: application/json` and no `Accept` (for example `systems/room-state-sync.js:43`), which the body test catches. For a refusal (a 409 `format` body) the text is the body's `message`, followed by "Progress cannot be saved on this server.", because the server refuses every request for that game.

### Step 8a. One outage field (format 1)

## 8. Risks

- **Step 1 blocks other work.** Once errors fail the run, any branch carrying an unlisted `❌` fails its merge batch. The known-failures list keeps other tracks' lines visible with their owners without blocking, a stale entry fails the run so the list cannot rot, and the stage rule keeps partial runs (`--skip-ink`, CI's social job) from failing on lines they never checked.
- **The known-failures list or the clue markers grow quietly.** Every known-failures entry, acknowledged clue and scan exception needs its own `approved` heading in `docs/agents/VALIDATOR_DECISIONS.md`, whose `json` block restates that one entry; the tests check the block matches and that no heading backs two entries across the three lists, and that file does not move with the pass; every batch diffs `scripts/validator_known_failures.json` and `test/fixtures/files/payload_scan_exceptions.json` and greps for `acknowledgedClues`, and the orchestrator signs off each addition. Markers are counted in every summary line. A passed `reviewBy` fails the merge-batch suites.
- **A clue marker hides a real leak.** A marker cannot name its own lock or anything inside it, and the `global:` form always prints as a warning and needs its own signed heading.
- **Step 3 tells an author to delete a live field.** The door-entry lock type is resolved from the connected room, as the client does, and a door entry is never told to delete its `requires`; two corpus door entries are fixtures.
- **Step 3 changes which capture secrets and account passwords the server withholds.** The extended `hard_access_values` withholds non-account capture secrets equal to door-entry, combination and cryptex answers until their proof holds (`authored_capture_secret`); the extended `lock_answer_keys` withholds account passwords equal to combination and cryptex answers in proof-declaring scenarios (`password_opens_lock?`). One normaliser, shared with `Game.lock_answer_matches?`, decides what equal means, so a stray number beside a combination is not withheld, and a blank, nil or malformed answer never opens a lock.

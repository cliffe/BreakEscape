## The rule for `call_in_after_sweep` (item 2)

**Every bring-in completes its own call-in task on the `[Bring me in.]` reply line, before the bracket `[On my way. #ending_check]`. It never waits for "End the mission now".**

Why: `openOptionalObjectives` (`ending-check.js:55`) lists every active optional task and has no exclusion. If the call-in task were still open when the bracket asks, the overlay would always list "call HaX to bring you in", even to a player who has nothing else left and is calling HaX at that moment. The live run shows the current placement works. The overlay lists only the real optionals, and it asks again correctly after Keep going and a redial. The cost is that a player who answers Keep going sees the task ticked while still in the building. That matches what they did: they called in and asked to be brought in. Moving the completion would need an engine exclusion for the asking task, and the oddity doesn't justify that.

It is already uniform. On `build/phone-calls-writing`, m03 (`:628`), m04 (`:467`), m05 (`:995`) and m06 all put `#complete_task:call_in_after_sweep` on the `[Bring me in.]` reply, with `[On my way. #ending_check]` next. m01 (`closing_debrief`) and m07 (`bring_me_in`) have no call-in task, so the rule doesn't apply to them. Whatever writes a future bring-in should follow the same rule; README_ink_best_practices.md could say so in one line (orchestrator's call).

## How a sign-in is attributed to a PC
A real capture holds no request body and no PC id on a keyboard sign-in (only a remote one has a `host` label), and the recorder is not edited. Order: a recorder `login` tag if a log has one; the answer's host label (a label that names no PC earns nothing and never guesses); the `--signin` entry for THAT row (`<account>@<pc>#<n>`, n = the account's n-th successful sign-in answer counting remote and relay ones too, or `<account>@<pc>@<row time>`), credited from that row only, for that account only; else the one PC that admits the account; else nothing (fail closed). An entry whose PC does not admit the account is an `ArgumentError` (exit 2). Entries are strict: `#n` is `[1-9]\d*`, the PC and account must exist, a duplicate key is refused, and `scanner.unused_entries` (the leak check exits 2 on it) lists entries that matched no row. `ops_steps` cannot name an admin session.

## Every option of the leak check
- `--signin <account>@<pc>#<n>` / `@<row time>`: names the PC of one keyboard sign-in. Name every keyboard sign-in, an ordinary account's too.
- `--resume <account>@<pc>@<row time>`: ONE 200 desktop row after a 403 `off` or `not_responding` at that PC; accepted only if that row's session is the account held when the 403 came, no other end came in between (sign-in, lock, logout, `endedPcIds`, bootstrap end, a desktop or host row without admin, a 403 of another kind); restores the account and, if it was held and the row shows `access: "admin"`, the step and its token deadline, from that row only. A 200 answer never restores by itself. Needed for the survived-power-cut desktop (PLAYTEST beat 8).
- Both are repeatable, go after the game id and before the files, and an entry that matches nothing is exit 2.

## Ops S5a fix, R4 pass (reviews/S5a_R4.md)
- `--resume` (`apply_priv_resume`) restores only when ALL hold: the row is not past the saved token deadline (R4-1), its session is the same account and the same kind (`via`, relay) as the one that earned the step (R4-2), the record was not dropped by an end, a grant (R4-6), a lock (`locked` on a desktop, host row or bootstrap) or another account's row. A session shown as another kind loses the step for good, whether it is shown as admin (`check_priv_kind`) or WITHOUT admin (a claim or relay is never shown as admin: R5-2, `downgrade_priv_step(session:)`; `lose_priv_step`); `access: admin` with `via: claim` or `relay: true` is an `ops:key:access` finding wherever it appears.
- A `GET /network` host row is judged by username like the desktop and bootstrap (R4-3): another account shown, even as admin, ends the step; the account shown is NOT assigned (R5-3).
- R4-4 settled by making the rule work on the real shape: an off PC's host row (no `session`, `responding: false`, `heldAs` = the held account's display name) suspends the step like a power cut; a repeat of a downgrade answer (each PC is listed twice) keeps the record (`downgrade_priv_step(keep: true)`); a desktop row without admin still drops it. PLAYTEST beat 8's text is corrected.
- `--logout` and `--signin` names are cross-checked (exit 2, `ArgumentError`): after a named logout the first later answer listing that PC's session state (desktop 200, host row, bootstrap) must not show the account (R4-5); after a named keyboard sign-in the first later 200 desktop of that account (password, not remote) must be the named PC, or one where the run already holds the account (R4-7). Where no such row follows, the name stands (a logout with no later listing of that PC, a sign-in with no desktop answer after it). Code: `check_priv_named`.
- Engine (R4-8, R4-9): `OpsLogEvents.profile_shown_name` gates the profile cell: the owner's display name only at a PC whose `loginPicker` is `"accounts"` (or unset) and that admits the owner; else the kind word. `profile_named` stays the existence check. A18 has the sentence.
- Real captures after the pass: `adel@store_pc#5` gives 0 findings, 38 with the sign-ins only, 112 with nothing named (unchanged). `adel@bay_pc#5` as the logout is now an error (row 142's host row shows adel at `bay_pc`).

## Session ends tracked
Before the answer is judged (`note_privilege_before`): the token deadline (`expiresInS` + the sign-in row time, per PC, for an earned step); a 200 desktop answer with no session (step and account), another account's session (ends the session; the account is not assigned, R5-3) or no `access: "admin"` (step); a `GET /network` host row of a sign-in PC with no `session` (step and account, unless it is the off shape: suspended), a locked session or another username (ends), or without admin (step); a bootstrap `sessions` map with the PC absent or locked (step and account), another account (ends it, no assignment, R5-3) or no `access: "admin"` (step, R3-C3). After the answer (`note_privilege_ends`): a later sign-in at the PC (named PC or every admitting PC), `POST /lock_session` (`pcId`; none ends every PC), a PC in `endedPcIds`, a 403 desktop answer (the resumable record is kept for `off` and `not_responding`), a successful `POST /logout` (every PC, or the one PC a `--logout` entry names).

## Ops S5a fix, R5 pass (reviews/S5a_R5.md)
- R5-1: a record survives a repeat of an off or downgraded answer only when the answer shows the SAME held account (`downgrade_priv_step(shown:)`: the host row's username resolved to an NPC, the bootstrap's `npcId`); another account's row drops it, also after a 403 `off` (no account is held then, so the record's own account is the comparison).
- R5-2: a downgrade answer whose session is another kind than the step's (or than the suspended record's) loses the step (`lose_priv_step`), so a claim or relay shown without admin drops the record.
- R5-3: the desktop, host-row and bootstrap rules only END a session or report; none assigns the account shown. The real-run tests and the four captures (0 findings with the five named entries, 38 with sign-ins only, 112 unnamed) give the same results without the assignment, so no row depends on it.
- R5-4 (engine): `profile_shown_name` gives the kind word also for a headless PC and for a PC whose policy's `remoteScreen` is `typed`.

## Remaining limits
- A sign-in of an ordinary account named at a different PC that also admits it: refuted (exit 2) by the desktop that follows it if the run holds no session of that account at the PC shown; with no desktop row after it the name stands and the PC it really displaced keeps the step until a desktop answer, host row or bootstrap for it shows who holds it.
- A power cut or token lapse is invisible when no network view, desktop answer or bootstrap comes before the leaking request (the token case is covered by the deadline). A hand-back whose answer names no PC ends only at the next such answer.
- The ADMIN_READ rule credits one earned read per profile and PC (two admin accounts reading one profile at one PC earn one: a false alarm). A reload does not re-earn: give every capture file. The logout takes back every PC's step, so a second still-held admin session elsewhere needs a new sign-in. The capture fixtures predate the scenario's later edits (R3-B3); a fresh capture follows the replay.

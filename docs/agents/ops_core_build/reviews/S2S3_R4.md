## Check 1: `_followVisibility` (`compromise-marks.js:117-131`)

**What it does.** Finds the `visible` accessor on the prototype chain (`:118-120`), defines an own
accessor on the sprite instance that delegates to it with `this` = the sprite and copies the value
to the bolt (`:124-126`), and returns a function that deletes the own accessor (`:127-130`).

**Restore.**
- Prototype accessor (the Phaser case): `delete sprite.visible` uncovers the prototype accessor
  again; the value lived in Phaser's `_visible` and `renderFlags` all along, so the restore is
  exact. Confirmed by reading and by the first new test (`hasOwnProperty` false after unmark).
- Own data property (a stub sprite): the value is kept in the closure and written back as a plain
  data property (`:129`). Exact for the cases in use.
- Unmark: `_unmark` calls `entry.unfollow` before destroying the bolt (`:107-108`). Correct order.
- Marked, unmarked, marked again: the first unfollow removes the own property, so the second mark
  wraps the bare sprite afresh. No double wrap. Marked twice (two passes while held): `_sync`
  returns at `:87` for a held sprite and never reaches `:95`. No double wrap.
- Sprite destroyed, or its room gone: nothing unwraps at that moment. The next `refresh()` unmarks
  any sprite with `active === false` (`:163-165`), which takes the wrapper off and destroys the
  bolt. Until an event fires, the `marks` Map holds the dead sprite and its wrapper. That hold is
  the same as before this commit (the Map was already keyed by sprite); the wrapper adds a closure
  over the bolt and nothing else. Setting `visible` on a destroyed Phaser image only flips bits, so
  a late setter call cannot throw. This codebase has no room unload (searched `core/`, `systems/`
  for `unloadRoom`, `destroyRoom`: none) and the page reloads between games.
- Scene shutdown: the scene destroys sprite and bolt together; `bolt.destroy()` on a destroyed
  Phaser object is a no-op.

**Other wrappers.** `Object.defineProperty` appears in three places under
`public/break_escape/js` (outside `lib/`): `mail-scheduler.js:837` (on `window`),
`password-minigame.js:219` (a result object), and this one. Nothing else redefines `visible` on a
sprite: the behind-wall fade uses alpha (`behind-wall-fade.js:341`), the lighting system sets
`visible` and alpha on its own images (`lighting.js:1412`, `:1890`), plant hiding calls
`setVisible` (`plant-hiding.js:384`). If an own accessor were already there, `:122` declines to
wrap and the bolt falls back to the per-pass copy in `_place`. Safe.

**Readers and `setVisible`.** The getter returns what the prototype getter returns; `setVisible`
assigns `this.visible`, so it goes through the wrapper and then the original setter, with
`renderFlags` set as before. No behaviour change for a reader or a caller. The own property is
enumerable; no code enumerates a sprite's keys (the two `Object.assign` uses in
`room-state-sync.js:190` and `rooms.js:2933` write into objects, they do not read a sprite).

**Can the bolt show when it should not?** After this commit the bolt is hidden whenever anything
sets the sprite's `visible` to false: room not revealed (`rooms.js:457`), `hideUntilReveal` and
`hideRevealedObject` (`rooms.js:3080`, `:3097`). That is an improvement on the old code, which
could leave a bolt showing over a sprite hidden after the mark was made. Two cases remain where
the bolt and sprite can disagree, both older than this commit:
- a sprite destroyed without a source event keeps its bolt until the next `refresh()` (see above);
- alpha is not followed (finding R4-1).

**Alpha and the behind-wall fade.** Only visibility is followed. `behind-wall-fade.js:341`
multiplies a room object's alpha by `k` when the player is behind the wall in front of it, and
fades the object's `_fadeCompanions` with it (`:302-305`). The bolt is neither in
`room.objects` (it has no `scenarioData.id`) nor a companion, so a marked PC behind a wall dims
while its bolt stays at full strength: the player sees a bright bolt over a ghosted PC. The
reveal path also sets `obj.alpha` (`rooms.js:3167`, 0.3 for an inactive object); not relevant to a
marked sprite, which is active. Not caused by this commit and not what PL6 reported.

**Would a simpler rule have done?** Partly. `_place` already copies visibility on every pass
(`:158`), but passes run only on the five events and at `syncRoom`, and `syncRoom` runs before
`revealRoom` (`rooms.js:1044` then `:1053`). So the simpler rule needs a hook: one line at the end
of `revealRoom` and one in `showRevealedObject` / `hideRevealedObject` calling
`window.compromiseMarks?.syncRoom?.(roomId)`. That is three call sites in `rooms.js` against one
wrapper here, and it would miss any later caller of `setVisible` on a marked object. The house
pattern for "an image that belongs to a sprite" is plant hiding's: copy visibility once
(`plant-hiding.js:384`) and join `_fadeCompanions` (`:387`). The wrapper is more general than
either and its restore is exact. It is the only place in the game that patches a live Phaser
object, which is the cost: the next person debugging a sprite's `visible` will not expect it.

**Judgement.** Acceptable to land. The restore is exact for Phaser sprites, there is no double
wrap, and no other system wraps the same property. After landing: R4-1 (alpha), R4-2 (truthiness),
R4-3 (tests), and a line in the module header (`:14-24`) saying the sprite's `visible` is wrapped
while marked (the header still says only "Event driven, never polled").

### Findings

**R4-1 (minor, older than this commit).** `compromise-marks.js:94-96`, `behind-wall-fade.js:302-305`.
The bolt does not fade with its sprite behind a wall: full-strength bolt over a dimmed PC.
Fix: in `_sync` after the bolt is made, `(sprite._fadeCompanions ||= new Set()).add(entry.bolt)`,
and in `_unmark` `sprite._fadeCompanions?.delete(entry.bolt)` before `destroy`. The fade's
companion pass checks `c.scene && c.active !== false && c.visible`, so a hidden bolt is skipped.
Add a node test with a stub companion set. Check in a browser that the fade's `drawnRect` logic
does not need the companion in `room.objects`.

**R4-2 (minor).** `compromise-marks.js:125` and `:158`. The bolt uses `v !== false`; Phaser's
setter uses truthiness (`if (value)`). `sprite.visible = 0`, `null` or `undefined` hides the sprite
and shows the bolt. Every caller found passes a boolean (`setVisible(lit)` in `lighting.js` is on
its own images), so nothing triggers it today. Fix: after calling the original setter, read back,
`image.visible = !!get()`; in `_place`, `image.visible = !!sprite.visible` when it is defined.

**R4-3 (minor, tests).** `test/js/compromise-marks.test.mjs:281-322`. Covered: hidden at
`syncRoom`, shown by `setVisible(true)`, direct assignment, the wrapper gone and the value right
after unmark (accessor case); the data-property case through mark only. Not covered: a second
mark after an unmark (wrap, unwrap, wrap, then the bolt still follows and one own property
exists); two passes while held leave one wrapper (assert `setVisible` moves exactly the one
bolt after two `refresh()` calls); the data-property case after unmark (the value written back,
`:129`); the decline branch at `:122` (an own accessor already present: no throw, the original
accessor untouched after unmark). Add these four asserts; the code is right by reading for each.

**R4-4 (minor, stub-only).** `compromise-marks.js:123-130`. Two edge cases that a Phaser sprite
cannot reach: (a) a sprite with no `visible` anywhere gets a wrapper whose value is dropped at
unfollow (`own` was undefined, so `:129` does not write it back); (b) an own data property on a
sprite whose prototype also has the accessor would be read through the prototype getter, not the
own value. Fix for (a): track whether a value was ever set and write it back. (b) needs no fix; a
comment would do.

## Check 3: the file-order guard

`access_leak_scanner.rb` `file_order_problem`; `access-leak-check.rb` exits 2 before `scan`.

**Legitimate use refused?**
- Two files whose first rows share a timestamp: passes (`t >= prev_t`).
- A single file, or no files: passes (tested).
- A file with no timed rows: skipped, passes (tested).
- A hand-written DOM capture file after the response file (`lab_physical_pentest/PLAYTEST.md:118`):
  passes, since the response file starts at game load; a DOM file with no `t` is skipped.
- Files from two different games: not refused, and it is not this guard's job. The script takes
  one `game_id` and never compares it with the rows' paths; that was so before. See R4-6.
- Timestamps are the recorder's `toISOString()` form (UTC, milliseconds, `Z`), so text order is
  time order. A file from a recorder with another format would compare wrongly; none exists.

**Wrong order slipping through?**
- Only first rows are compared, and against the adjacent file only. A file with no timed rows
  between two timed files hides the pair on either side: `[A at 21:12, untimed, C at 21:09]`
  passes (R4-5).
- Two captures that overlap in time (two browser tabs recording at once) pass the guard in either
  order, yet reading one whole file then the other is not time order. Not seen in the runs so far
  (the second run's files were one after another). R4-5 covers it.
- A later file whose first row is early because of a cached or replayed row: `t` is stamped by the
  recorder when it sees the response, so a replay gets the current time. Not reachable.

**Callers of the exit code.** No shell script or test under `tools/playtest` or `test` runs the
script (searched `*.sh`, `*.rb`, `*.mjs`, `*.js`). The `PLAYTEST.md` files give it as a command for
a tester who reads the `VERDICT` line. Exit 2 was already "usage error" in the header, and the
message goes to stderr with the cause. A tester who checks only `$?` != 0 would read it as a
failure, which is the safe side. No caller treats non-zero as "leaks found".

### Findings

**R4-5 (minor).** `tools/playtest/lib/access_leak_scanner.rb` `file_order_problem`. Compare each
file's first time with the last KNOWN earlier first time, not the adjacent file's (carry
`prev_t` across untimed files), and also refuse when a file's first time is earlier than the
previous timed file's LAST time (overlap), or state in the message that overlapping captures must
be merged. Add a test for `[first, untimed, earlier]`.

**R4-6 (minor, older).** `tools/playtest/access-leak-check.rb:46-57`. Rows from another game are
judged against this game's scenario without a warning. Fix after landing: warn (or exit 2) when a
row's `path` names `/games/<n>/` with `n` other than `game_id`.

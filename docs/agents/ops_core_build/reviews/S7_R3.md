### A2. The late fixes, read closely

- **The token as sent (R2-1).** The client shows the server's string, trimmed, through `textContent`. Nothing regroups
  it. If the server ever sent a token without dashes it would show as one run of 24 characters; the scanner's token
  shape rule would flag that capture.
- **The cracked password at the sign-in screen (R2-2).** The tile is tagged "Cracked" and the player types the
  password. On that screen a captured password that the keyring holds is filled in (`password-minigame.js:420`),
  and a password found in a file is typed, with a line that names the file. A cracked password is held by the
  keyring like the first and typed like the second, and it gets no line saying where to read it. It is consistent
  with "in file", not with "captured". Neither reading is a fault; it is owner question 3. A tile that is both
  captured and cracked still fills from the capture, and one that is both in a file and cracked teaches the file
  lesson first; both are reasonable.
- **Re-reading the keyring on `intel_collected` (R2-7).** No loop: a refresh emits `keyring_changed` only, and
  nothing in it grants a fact. No lost state: `adoptRow` keeps the answer on screen, keeps every pick that is still
  a listed fact, and moves the countdown only when there is no answer yet. The listener is removed in `cleanup`.
  The fault is that the event does not arrive in the case that matters (R3-1).
- **`ApiClient.unlock` applies `grant_fact` rewards (R2-5).** The server puts `rewards` on an unlock answer only in
  the `method == 'flag'` branch (`games_controller.rb:1331-1351`), and a second claim answers
  `{ type: 'skipped' }`, so no door, key, PIN, RFID or NPC unlock can grant anything. The client filters to
  `grant_fact` and leaves every other reward type alone, as before. A reward for an unknown fact carries no `entry`
  and `grantFact` refuses it. A flag lock's `give_item` reward is still not applied on the client until a reload;
  that is older than S7 and is noted for the owner.
- **The validator (R2-3, R2-4, C2).** `ops-unchanged-validator.test.mjs` passes, and the wider survey above shows no
  shipped scenario gains a line. The second-path error also fires for a fact on an item nobody can take, which is
  right now that such a fact is withheld.
- **Wording.** The cracker prompt ("Pick the facts you think it was built from, then press Crack.") answers the
  playtest's worry that Dana's chips appear on every account. `PLAYTEST.md` beats 4 and 6 match the game. The
  capture banner's new parenthesis is shown in places that have no cracker (R3-2).

### B6. The limits the fixers list

As the project runs a check (a game, every capture file, oldest first):

1. **Earned facts are read once, at the end.** After a complete run the game has earned every fact, so the game
   check adds nothing and the rule rests on place, shape and order. What passes: an entry sent early in one of the
   three places where entries are sent, for a fact the player earns later (R3-7). For that the server would have to
   pick ids other than the added item's or the accepted flag's and also stop filtering them by the earned set
   (`earned_fact_entries` answers earned ids only). No leak passes in a run where that one filter holds. The inventory half can
   be closed with the `inv` tag the capture already holds.
2. **Without a game only place, shape and order are judged.** Unit tests only; the CLI always has a game.
3. **A cracked answer is checked per account, and the running, runs and infeasible flags are per run, not per
   record.** No scenario gives an account two hash records. With two strong records, one record's `infeasible`
   answer would excuse an early `infeasible` row on the other: that tells a class early, not a password. Closes
   with a `hashId` tag on the `POST /crack` row. Needed before a shipped mission has hash records, not now.
4. **The salted wait is not timed.** A grant before the wait is over gives the same password early. Not a leak of
   anything unearned. The Rails scenario test checks the clock with frozen time.
5. **A proof lost after a crack** (an item given away) would flag honest rows. Fails closed.
6. **`credential_unheld` still skips when the game lacks `credential_proof_holds?`.** `Game` has it, and any
   scenario with a hash record now requires it. A rename would be caught there first.

None of the six lets a password, a fact's text or a network's name through in a run as the project runs them, short
of the server fault described under 1.

## For the owner

Open design questions, from all rounds:

1. **The capture log as the only way to the cracker.** The validator now refuses a hash scenario without one.
   Should the cracker also open from the hash file or the "Hash collected" toast, and should Close return to the
   log?
2. **Auto-finish.** A scene reopened after the wait posts by itself within half a second, though it says "Press
   Finish". Keep it, or wait for the press?
3. **The cracked password at the PC.** As built: tagged "Cracked", typed by the player, no line saying where to
   read it. A captured password the keyring holds is filled in. Fill the cracked one too, or keep the typing and
   add a line that points at the capture log?
4. **`grant_fact` on a flag: award path or stand-in?** The social validator still warns on it, so the feature
   scenario validates with one warning where the brief says none.
5. **One award path per fact.** Now an error for actions, highlights and calls beside an item or flag reward.
   Confirm the rule, and extend it to OSINT elements (R3-3).
6. **How easy is easy.** Unlimited instant guesses on an unsalted guessable record; `missingCount` falls by one per
   recipe fact earned, which is close to saying which facts matter; a guessable password can be typed at the PC
   from the three facts without the cracker; Crack may be pressed with no pick. All intended?
7. **Scenarios edited under live games.** A player who already holds a fact item never earns its fact and does not
   see it. Documented as a limit; accept?
8. **A strong record in the dungeon graph.** Draw the dead end, or leave it out?
9. **The hash form of `flagRewards`.** Now read everywhere for `grant_fact`. Is it meant to carry one? If not,
   refuse it in the validator (R3-8 then goes away).
10. **Facts are not per account.** Every earned fact is a chip on every account's cracker. The new prompt makes
    this read as a choice. Intended, or should chips be limited to the record's subject?
11. **The feed fact is earned when served, the chip needs a re-read.** Accept R3-1 as a limit or fix it?

Recorded limits:

1. Feature: at most 64 earned facts and 64 cracked accounts per game (a 65th account answers `cracked` and is never
   listed). No reset entry for a cracked account. One look for the cracker, its CSS injected by the scene with
   fixed colours and no focus style. Keyring cost with many hash records is not measured. Two entries for one
   account fold into one row and one tile. A flag lock's `give_item` reward reaches the client only on a reload.
   The station reads "requires external VM" while it takes a typed flag.
2. Feature, authoring: a guessable recipe cannot use a fact from dialogue, an object action, an OSINT page or a
   mail highlight. A readable item should not repeat its fact's text word for word, and a reward `label` should not
   hold it (R3-6).
3. Not verified in a browser: the reload during a wait (beat 7); the token as sent and the Cracked tile (changed
   after the playtest).
4. Scanner: a cracked answer is checked per account, and the run-order flags are per run; the `POST /crack` row
   carries no `hashId`. Close before the first shipped mission with hash records.
5. Scanner: one `running` answer is one credit, and a second click during a wait is a second credit.
6. Scanner: the salted wait is not timed.
7. Scanner: proofs, facts and held partners are read at the end of the run; a fact's grant is taken from the
   answer that carries it (R3-7).
8. Scanner: without a game, proofs, facts, tokens and held partners are not checked (unit tests only).
   `credential_unheld` still skips if the game lacks its method.
9. Scanner: strings are matched case-exact, a text inside a longer string only from 20 characters, a label only as
   a whole string, and hash keys are never read. The older rules still match routes with `end_with?` and read some
   statuses with `to_i`; a row with `status: true` ends the CLI with a backtrace (fails closed).

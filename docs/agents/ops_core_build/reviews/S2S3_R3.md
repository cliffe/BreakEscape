### The label lookup (`ops_session_owner`, LS:2498-2504; `ops_host_labels`, LS:2506-2517)

- The label is computed as the server computes it (`pc['host'].presence || pc['name']`, `network_access.rb:888-890`).
- A label two networked hosts share (two PCs, or a PC and a device whose `name` equals the PC's label) is dropped from the map (`ids.uniq.size == 1`), so the hash resolves to no host and `via`/`access` are reported: fails closed. Confirmed. Test: "an unknown label fails closed" covers the no-match case; **no test covers a shared label** (add one: two PCs with one `host` label, a container answer for either after a grant at one, expect `ops:key:via`).
- The lookup runs only for a hash that has `via` or `access` AND no enclosing `id` (`owner ||=`): a host row is still judged by its own `id`, so a row cannot borrow another PC's step through a label.
- A label equal to something else: the map holds only networked hosts' labels, and the looked-up hash must carry `via` or `access`. A share's `host` field or a room object with the same text has neither key as a scalar (`access` on a sign-in PC object is an array, skipped at LS:2488-2489). No wrong credit found there.
- One way the map can name the wrong PC: it is built from `hosts_on_all` (hosts on a network), so a sign-in PC on NO network that shares its label with one networked PC leaves that label "unique". A session answer about the off-network PC would then be judged with the networked PC's steps. No correct server can send `via: "technique"` or `access: "admin"` for an off-network PC in S3 (a weakness lives on a networked host), so this hides only a server fault of exactly that kind. Folded into R3-1.
- The technique answer fallback (`@ops_answer_pc`) is set only by a fresh grant in the same answer and reset at every row (LS:2081).

**R3-1 (minor, leak scanner soundness, LS:2375-2392 `ops_granted_finding`, LS:2394-2399, LS:2506-2517).** For an untagged SESSION grant the pool is narrowed to findings "confirmed and with no `session:<host>` yet".

## 2. New findings

### N1 (minor) NV `:576` with `:986`: a move's own refetch is dropped by a later press that is refused, and nothing asks again
After a successful sweep, `refetchAfterOps` asks for the view (the only thing that brings the block's `ops` key, so the
Scan controls). If the player presses any other control while that refetch is out, `perform` bumps the epoch (`:986`) and
the refetch drops its answer. If that second press is refused (a Scan on a host with no services answers `not_needed`, the
plan's normal case) or throws, `afterAnswer` returns early (`:1113`) and no refetch follows, so the swept block shows rows
with no Scan control until the next timed tick (up to 5 s, since `_unchanged` was reset). It heals itself and no stale
view is drawn, so it is minor; a scripted tester that presses quickly can see it.
Fix: remember that a drop happened (`this._refetchDropped = true` at `:576`) and, in `afterAnswer`, call
`refetchAfterOps()` when the answer is a refusal or null and that flag is set (clearing it when a refetch is applied); or
simply call `refetchAfterOps()` on every sweep or scan ending. A node test: sweep succeeds with its refetch held, a scan
is refused, release; assert a further `network` call.

### N2 (major) `tools/playtest/lib/access_leak_scanner.rb:1886`, `:1893`, `:1898-1900`: a service string cannot be reported "before its scan" when it arrives on a row
`note_ops_row` earns `scan:<host>` from any row that says `scanned: true`, in a `GET /network` answer (`:1893`) and in a
sweep answer's rows (`:1886`), and it runs before the same answer is judged. The server always sends `scanned: true`
together with `services` (`network_ops.rb:168-171`), so a view or a sweep answer that lists a host's product, version or
label for a host the player never scanned earns the step from the leak itself and passes. The scan is then only able to
catch a service string in a bootstrap or room answer, or on a row with no `scanned` flag (the shape the unit test uses,
`test/unit/access_leak_scanner_ops_test.rb:86-88`, which the server never produces). The stage's claim "no product or
version before the beat that earned it" therefore cannot fail for the likeliest server fault, a wrong `scanned`.
The sweep and `held` steps do not have this problem (a listed row does not earn `sweep`).
Fix: earn `scan:<host>` only from a `POST /network/scan` answer with `host.id` and `success: true` (`:1885`), and from
the caller's `ops_steps` for a log that starts mid-run; delete the two `note_ops_row` calls (within one log the POST
always precedes any later view, a reload included). Add unit tests with the server's real row shape: a `/network` row
`{ id, kind: 'device', scanned: true, services: [...] }` with no scan answer before it is a finding, and the same for a
sweep answer whose row carries `scanned: true`; and in `ops_scan_scenario_test.rb` beat 11 add the mirror of the existing
premature-listing check (the post-scan view alone, with `ops_steps: ['sweep:office_lan']`, must give a finding).

### N3 (minor) `access_leak_scanner.rb:1828-1830`: a `hosts` device's name on an open network is never collected
Names are collected only `if discovery`. Plan 11.4 (`:1767-1768`) lists "host names of `hosts` entries and of sign-in
hosts on discovery networks": a device's name is server-only on any network (`hosts` is withheld from the bootstrap), so
on an open network it should be a `listed` string, as an open network's address is (a leak in a bootstrap or room answer
or before the first `/network` answer that lists the row). `test_ops_scan` has no device on its open network, so this
run is not affected; a later scenario would be.
Fix: for a record of kind `device` on an open network, `add_ops_string(obj['name'], :listed, ..., host: host_id)`; a unit test.

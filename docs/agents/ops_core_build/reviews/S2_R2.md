### New findings

#### M1 (major). The scanner cannot see a real finding given away before its confirm; in `test_ops_findings` it registers no need string at all
- Where: ALS `collect_ops_needs` (:1912-1927), `collect_ops_finding` (:1880-1896), `scan_ops_strings` (:2082-2097).
  PT beat 12 and DOC N14 "Check from the server" claim it.
- Plan: section 7 rows "Whether a finding is real: after the confirm" and "`needs`: after the confirm"; beat 12
  (1731) "no reason or need before a confirm".
- What is wrong: the confirm stage is judged by strings only. A decoy's `falseBecause` text is registered, so a
  decoy given away early is caught. A real finding is not: its signs before the confirm are the `needs` key
  (often `[]`), `fixed: true` and `status: "confirmed"`, none of which is a distinctive string, and its need
  labels are, by the plan's own rule, names the scenario already shows, so the "not already in room text" rule
  drops them. Run over the stage's scenario, the collector registers exactly two confirm strings (the two
  decoy reasons) and nothing for any of the four weaknesses: "Printer manual" is public (the cupboard is not
  locked), `archivist_login` has no `label` (the server falls back to the note's name, the scanner does not),
  and the other two have no needs. So a server that sent `needs`, `fixed` or a settled status on an unconfirmed
  weakness, in a check answer or in `GET /network`, would pass the leak scan of both runs. Since a decoy never
  has those keys, that is exactly the "which one is real" leak N14 exists to prevent. The controller tests do
  cover it (`network_ops_indistinguishable_test`, ST beat 2); the gap is in the playtest proof, which the
  playtest and the docs say covers it.
- Suggested fix: a structural rule beside `scan_ops_services`. Collect the known finding ids. In any answer, a
  hash whose `id` is a known finding id and that carries a `needs`, `fixed` or `falseBecause` key, or a `status`
  other than `unconfirmed`, is a leak before `confirm:<that id>` (owner `ops:finding:<id>`); the confirm answer
  for that id earns it first, as now. Tests in the server's shapes: an unconfirmed row with `needs: []`, one with
  `fixed: true`, one with `status: "confirmed"`, each in a check answer and in a view, each clear after the
  confirm answer and still a leak after another finding's confirm. Mutation: remove the rule, the tests fail.

#### M2 (major). The "never" rule for a gating global is empty in `test_ops_findings`, and no rule reports a `fixedIf`, `grants` or `realism` key
- Where: ALS `collect_ops_globals` (:1929-1944, both the string entry and `@ops_global_names` go through
  `usable`), `scan_ops_global_keys` (:1946-1952). SC lobby `share_switch` (`triggerOnInteract`:
  `{ "type": "set_global", "key": "share_locked" }`).
- Plan: section 7 "`fixedIf` and its global: never"; "`grants`: never"; beat 12 "no `grants`, `fixedIf` or global
  name ever".
- What is wrong: `usable` drops any string that is already in room data. The switch that sets `share_locked`
  carries the name as a string value in the lobby's room data, so it is "public" and the scanner registers
  neither the value entry nor the key entry: run over SC, `@ops_strings` holds no `never` entry and
  `@ops_global_names` is `{}`. The drop itself is right for a bare string (the name is legitimately in the room
  answer), but it leaves nothing: a finding row sent with `"fixedIf": "share_locked"`, or with `share_locked` as
  a key, passes. Any scenario whose fix is a switch, a trigger or a line of dialogue will name its global in
  room data, so this is the usual case, not an odd one. Separately, no rule looks at the key names themselves:
  `fixedIf`, `grants`, `realism`, `weaknesses` and `decoys` are never sent under any route, and a scan that met
  one would say nothing unless its value happened to be a registered string.
- Suggested fix: (a) a key rule with no string test: any hash key named `fixedIf`, `grants`, `realism`,
  `weaknesses` or `decoys`, anywhere in any answer, is a leak (owner `ops:key:<name>`). (b) judge a gating
  global by where it is, not only by whether it is public: inside a hash whose `id` is a known finding id (the
  row and everything under it), a string value or a key equal to a gating global's name is a leak, with no
  `usable` test. Keep today's rule for names that are not public. (c) when `usable` drops a `never` string,
  print a one-line note in the leak check's output ("global share_locked is in room text; judged only inside
  finding rows"), so an empty rule is visible. Tests: a finding row with `fixedIf` as a key; a finding row with
  a public global's name as a value and as a key; the same name in a room answer is clear. Then PT beat 12 and
  DOC can keep their claims, reworded as in N10 and N11.

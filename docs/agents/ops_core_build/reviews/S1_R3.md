## 2. Notes on each check

### 2.1 N2: order, what can earn, what the tests prove
- Order is right for a scan answer. The answer to `POST /network/scan` with a host carries that host's services in the
  same body (`network_ops.rb:101-104`, `ops_host_row`), so the step has to be credited before the body is judged, and
  it is (`:348` before `:349`). The credit now comes only from the route and `success: true`, not from a flag that
  travels with the leaked data, so a view or sweep row can no longer pay for itself.
- A refused scan earns nothing: every refusal is `{ success: false, reason }` or the 404 body (`network_ops.rb:27-33`),
  and the branch needs `success == true`.
- An `already: true` repeat earns the step. That is correct: it is the player's own successful scan request for that
  host, and it is what lets a log that starts after the first scan stay clean without `ops_steps`.
- A sweep answer has `network`, not `host` (`network_ops.rb:90-92`), so it earns `sweep:<net>` only. A `GET /network`
  row earns `listed` and (a PC row with a session) `held`, never `scan`.
- A view or sweep row that lists a product, version, label, banner or unique `cli.service` word for a never-scanned
  host is now a finding (`:1912`, unit tests `:102-114`). A device name, a share name or host label, or an address on a
  never-swept discovery network in a view is a finding (`:1911`; older tests "a host name in the view of an unswept
  network" and "sweeping one network does not earn another network host", both kept).
  Port and the service `name` are not collected at all: see new finding R3-1.
- Row shapes: `scanned_device_row` (`:97-100`) is `{ id, kind: 'device', name, scanned: true, services: [{ name, port,
  product, version }] }`, which is `ops_device_row` plus `ops_add_host_fields!` and `ops_service_row`
  (`network_ops.rb:155-190`, `SERVICE_KEYS` `:23`). The sweep answer helper is the body of `scan_network!` (`:90-92`).
  The scanner walks every string, so the wrapper keys (`footholds`, `hosts`) do not matter.
- Would they fail on a revert: yes, by reading. With `note_ops_row` back, the row at `:97` (has `scanned: true`, an id
  and a `kind`) earns `scan:print_srv` before judgement in both the view test (`:104`) and the sweep test (`:112`), and
  the beat 11 mirror (`ops_scan_scenario_test.rb:305-307`) finds nothing because the last view's rows say `scanned`.
  Not run by this reviewer (no Ruby run was allowed); the fixer records the mutation run.
- Nothing right was lost with `note_ops_row` and `rows_of`. Their only job was to credit a scan from a row; the two
  honest cases they served are covered: a scan made in the log (the POST answer, a repeat included) and a log that
  starts mid-run (`ops_steps`). `rows_of` had no other caller.

### 2.2 N1: the refetch change against the R1 epoch rule
- A stale answer still cannot overwrite a newer view: the check at NV `:576` is unchanged, the new code only records
  that it fired. The refused press bumped the epoch at `:984`; the refetch it now asks for starts after that and reads
  the current epoch.
- Traced: (a) the earlier refetch still out when the refusal lands: `_refetching` is true, `refetchAfterOps` waits for
  `_refetchDone` (that answer drops), then asks once; (b) it already dropped: `_refetchDropped` is true, one refetch at
  once; (c) two refused presses waiting on the same `_refetchDone`: the first starts a refetch, the second returns at
  the `_refetching` guard (`:554`); (d) no refetch out and none dropped: nothing extra is sent, as before.
- No storm: at most one extra request per refused or lost sweep or scan, and never two at once. If the flag stays set
  (the follow-up refetch got no answer, the tab was hidden, or an unplug press caused the drop), the next timer tick
  that passes the epoch check clears it; until then each refused press costs one request, no loop.
- A refused press whose in-flight refetch began after the press (same epoch, so it will be applied) still asks once
  more because `_refetching` is true. One redundant request, harmless; not a finding.
- Closed view: the branch calls `refetchAfterOps`, whose `refetch` returns at its first guard on `_reported` or
  `_ending` (`:554`); no request is sent.

## 3. New findings

### R3-1 (minor) ALS `:1852-1861` (`collect_ops_services`): a service's `port` and `name` are never checked
The scan step protects only `product`, `version`, `label`, `cli.banner` and a unique `cli.service` word. The server
sends `name` and `port` in the same service row (`network_ops.rb:23`, `:184-190`). A services list that reaches the
browser for a never-scanned host is caught only through one of the collected strings, so a service authored with a
name and port alone (allowed by the validator) or with a product shorter than 3 characters or one that is also room
text would leak unseen. `test_ops_scan` is not affected (all nine services carry a product and version). This is how
plan 11.4 lists the strings, not something the R2 fix introduced.
Fix (S2 is a fair time, with the `check` and `confirm` tags): a structural rule beside the string rule: in any answer,
a hash with a string `id` that is a known host and a `services` key, or `scanned: true`, is an `ops_string` finding
(owner `ops:service:<id>`) unless `scan:<id>` is earned. One unit test with a service that has only `name` and `port`.

### R3-2 (minor) NV `:305-309`: `_refetchDropped` is not set in the constructor
The other refetch fields (`_refetching`, `_opsEpoch`, `_refetchDone`) are initialised there; the new one starts
`undefined`. It reads as false, so behaviour is right. Fix: `this._refetchDropped = false;` beside them.

### R3-3 (minor, record only) `docs/agents/ops_core_build/reviews/S1_R2.md`, P3 outcome row
"Both files equal `main`" is true of `network-links.js` only (see 2.5). Fix: say "the plant path in both files equals
`main`".

Observation, not a finding: the scan step is credited from the id in the answer body, not from the request's
`host_id`. A server that answered a scan of one host with another host's row would credit the wrong host. The
controller tests assert the answered id, so this rests there.

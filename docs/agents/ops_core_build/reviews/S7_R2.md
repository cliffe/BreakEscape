# S7 review: server and client, round 2

Reviewed 2026-11-24 on `ops-crack` at `dd39ee7ca` (the last `Ops S7 fix:` commit). Scope: the fixes to
`S7_server_R1.md` and `S7_client_R1.md`, and the whole feature traced end to end in
`scenarios/test_ops_crack/`. Review only; nothing was fixed. The leak scanner under `tools/playtest/`
and its tests are not covered (they have their own round 2).

Counts: 0 blockers, 2 majors, 6 minors. The feature can now be played from the bootstrap to the
sign-in. The two majors are both things the player sees that no test sees.

  `GET /keyring` and `POST /crack` answer (full, `unchanged`, PC-scoped, and each refusal).

## New findings

### R2-1 (major) The token is shown broken into the wrong groups

- **Where:** `public/break_escape/js/utils/remote-host-text.js:271-274` (`hashTokenText`) and
  `public/break_escape/js/minigames/ops-cracker/ops-cracker-model.js:30-32` (`groupToken`), against
  `app/models/break_escape/ops_cracking.rb:37`.
- **What is wrong:** the server already sends the token in fours joined by dashes
  (`N4L9-E9K3-8PBA-...`). Both client functions cut the string into fours again, dashes included.
  The row and the scene show `N4L9 -E9K 3-8P BA-4 TNM- H9EP -9K6 6`.
- **How to see it:** feed a real `GET /keyring` hash row to `buildSignInRow` or the scene. Every JS
  test row uses `ABCDEFGH...` with no dash, so none fails. Equal tokens still look equal, so beat 8
  still reads, but the central thing on the screen is garbled.
- **Smallest fix:** strip everything but letters and digits before grouping in both functions (or
  show the server's string as it is), and use a dashed token in one row test and one scene test.

### R2-2 (major) The sign-in screen treats a cracked password as a password found in a file

- **Where:** `public/break_escape/js/minigames/password/password-minigame.js:441-445`
  (`keyringTagKind`), used at `:405`; effects at `:419-420` and `:2700-2702`.
- **What is wrong:** unit 04 changed `entryTagKind` in `keyring.js` so a `source: "cracked"`
  password is `cracked`. The sign-in screen does not use that function; its own copy still answers
  `in_file`. So at the PC (beat 9) the account's tile is tagged "In file", the ways-in box reads
  "Type the password from" over "Cracked", and after the sign-in the once-per-page teaching toast is
  "People save passwords in files...", the wrong lesson for a cracked password. The password is not
  filled in; the player types it from the capture log. By reading; the scenario test signs in
  through the route with a typed password, so it does not see the screen.
- **Smallest fix:** make `keyringTagKind` answer `cracked` for that source (or call
  `entryTagKind`), and give `cracked` its own branch in `mergeRemoteTiles`: either fill it as a
  captured password is (`tile.keyPassword`), or a line that says to type the cracked password. Add
  a `teachLine` for `cracked` or none. One row in `keyring-signin.test.mjs`. See owner question 3.

### R2-3 (minor) A `grant_fact` in the hash form of `flagRewards` is not withheld

- **Where:** `app/models/break_escape/earned_facts.rb:84-90` (`award_source_fact_ids`).
- **What is wrong:** the walk reads `flagRewards` only as an array. The controller also takes the
  hash form, `{ "<flag>": { "type": "grant_fact", ... } }` (`games_controller.rb:4171`, called
  "preferred" there), and stamps its fact. That fact's text still ships in the bootstrap. The
  cracking validator reads the array form only as well (`validate_cracking.rb:205-206`), so a
  recipe cannot rest on it; the text leak is for facts outside a recipe.
- **How to see it:** by reading. A row in the "bootstrap holds no entry" test with the hash form
  would fail.
- **Smallest fix:** when the key is `flagRewards` and the node is a hash, read its values the same
  way; do the same in the validator.

### R2-4 (minor) A fact with a server source and a client-only source can no longer be granted by the client path

- **Where:** `earned_facts.rb:49-55` with `public/break_escape/js/systems/social-intel.js:205-208`.
- **What is wrong:** every fact named by any `revealsFacts` or flag `grant_fact` is withheld until
  the server sees it earned. `grantFact` refuses an id with no entry ("Unknown fact: not granted").
  If the same fact can also be granted by a path the server does not see (a mail highlight, a
  pretext call, a `grant_fact` action in dialogue or on an object), that path now does nothing and
  says nothing. Before the fix it worked. The social validator errors only for an OSINT element
  plus an item (`validate_social/osint.rb:356`); a highlight or call plus an item, or an action
  plus a flag reward, passes. An item nobody can take (S4 part 2) withholds its fact the same way.
  No shipped scenario has such a fact.
- **How to see it:** by reading.
- **Smallest fix:** a validator error when a fact named by `revealsFacts` or a flag `grant_fact`
  has any other award path, and one line in the docs. See owner question 5.

### R2-5 (minor) A fact from a flag lock shows as its bare id on the chip until a reload

- **Where:** `games_controller.rb:1349-1350` (the unlock answer carries the rewards with `entry`);
  no client code reads `rewards` from an unlock answer.
- **What is wrong:** the docs already say such a fact shows as a chip and not on the intel board.
  Before the fix the chip had its label from the bootstrap. Now the entry is withheld and nothing
  merges it, so the chip reads the id (for example `dana_year`) until the page is reloaded.
- **Smallest fix:** have the unlock path hand `rewards` to `applyActions` as the flag station does
  (which also puts the fact on the board), or merge `entry` there.

### R2-6 (minor) The row's button stays "Open" when its countdown reaches 0

- **Where:** `public/break_escape/js/minigames/capture-log/signin-rows.js:346-360`.
- **What is wrong:** the row's timer rewrites the status line to "Ready to finish" but not the
  button, which keeps "Open" until the log is redrawn.
- **Smallest fix:** set the button text in the same timer when `left` is 0.

### R2-7 (minor) An open cracker does not learn of a fact earned while it is open

- **Where:** `ops-cracker-minigame.js:118-130`: the keyring is asked at start and after a post only.
- **What is wrong:** a feed post that lands while the scene is open (beat 4 has one about 30 s
  after the room loads) adds no chip until the next post or reopen. Nothing refreshes the keyring
  when a fact is earned without a tray item (a notes item, a flag reward, a feed post), so only
  the scene's own start does it.
- **Smallest fix:** re-read the keyring on `intel_collected`, or accept and say so in the docs.

### R2-8 (minor, docs) The new contract is not written down, and one beat is out of date

- `docs/ACCESS_AND_NETWORKS.md` A21 does not say that an item's or flag reward's fact entry is
  withheld from the bootstrap until earned, nor that it arrives as `facts` on the inventory-add
  answer and the `give_item` reward and as `entry` on the `grant_fact` reward. An author needs
  this to understand R2-4; the next person to touch the bootstrap needs it too.
- Known limits should name S5 (a held item with no stamp never earns its fact).
- `scenarios/test_ops_crack/PLAYTEST.md` beat 6 says "a password row sits beside it". The password
  row is now in Sign-ins and the hash row in Hashes.
- `games_controller.rb:1420-1422`: the comment says the stored copy is read; the ids come from the
  client's item (`item.to_unsafe_h`). Harmless, since only earned ids are answered.

## For the owner

1. **Capture log as the only way in.** Should the validator refuse (or warn on) a hash record in a
   scenario with no capture-holding item, or should the cracker also open from the hash file or the
   "Hash collected" toast? Should Close return to the log? (C2, client questions 1 and 5.)
2. **Auto-finish.** A scene reopened after the wait shows "Press Finish" and then posts by itself
   within half a second. Keep the auto-post, or wait for the press? (Client question 7.)
3. **The cracked password at the PC.** Should the sign-in screen fill it in as it does a captured
   password, or make the player type it? Either way it needs its own tag and words (R2-2).
4. **`grant_fact` on a flag: award path or stand-in?** The social validator still warns on it, so
   the feature scenario validates with one warning where the brief says none. (S4.)
5. **One award path per fact.** Is a fact with a server source and any second source an error?
   With the entry withheld, the second source now fails silently (R2-4, server question 3).
6. **How easy is easy.** Unlimited instant guesses on an unsalted guessable record; `missingCount`
   falling by one per recipe fact (close to saying which facts matter); and a guessable password
   that can be typed at the PC from the three facts without the cracker. Intended? (Server
   questions 4 to 6.)
7. **Scenarios edited under live games.** Accept that a player who already holds a fact item never
   earns its fact, and now does not see it on the board either? (S5.)
8. **A strong record in the graph.** Draw the dead end, or leave it out? (S7.)
9. **Hash-form `flagRewards`.** Is the hash form meant to carry `grant_fact` at all? If not, the
   validator should refuse it rather than the server half-supporting it (R2-3).

## Check 1: T2's mechanism (the stored-only `step` and `netLinkSteps`)

### R2-1 (MAJOR). The counter's period equals the merge window, so from the eleventh link step on a row merges into the row ten steps back, and the log stops growing

`app/models/break_escape/network_access.rb:291-301` (`link_step_detail`, `steps % 10`),
`app/models/break_escape/ops_log.rb:768` (`while index >= 0 && rows.length - index <= OpsLog::MERGE_WINDOW`,
`MERGE_WINDOW = 10` at `:43`), `lib/break_escape/ops_log_events.rb:52-53`.

The comment at `network_access.rb:291-293` says "Ten link events is the merge window, so a wrapped
value never meets its own earlier row". It is off by one. The merge search looks at the 10 newest
rows, indices `L-1` down to `L-10`. With ten step values (0 to 9), the row carrying the same value
was written ten link steps ago; nine rows were appended since, so it sits at index `L-10`, the last
row the window covers. On one jack, plant and unplug alternate, so step `k` and step `k+10` are the
same event at the same place with the same `step`: an exact match. The plan's own 13.2 step 5 says
it: "eleven distinct rows sent in rotation never find their own row"; ten do.

What happens (the helper's loop transcribed and run with the fixer's counter, one jack, a source
that takes only the link rows, or any source once its other rows are more than a few rows back):

```
event 11 up   step 1 MERGED into row 0
event 12 down step 2 MERGED into row 1
event 13 up   step 3 MERGED into row 2
... every later event merges; the source holds 10 rows for good
```

A merge appends nothing, so the distance stays ten and EVERY later plant and unplug merges: the log
freezes at ten link rows whose counts climb (`OK x2`, `OK x3`). After five plant and unplug pairs
the reader no longer shows a new plant as a row, the newest row can read `NET_LINK_DOWN` while the
device is planted, and `OK x2` is back. That is T2's original complaint, moved from the second
plant to the sixth. The cap does not help (the minimum cap is 10, `ops_log.rb:36`, and with a
larger cap the matching row is still exactly ten back). An interleaved row (a join, a share open)
only delays it by one cycle: both are once-only in practice, so the rotation settles again.

Not a leak and not unbounded: rows stay under the cap and plant and unplug save anyway. It is a
wrong log, in a fix whose stated guarantee is "a plant after an unplug is its own row", and no test
goes past three link steps (`network_log_rows_test.rb:137-146`, `ops_logs_scenario_test.rb:455-460`).

No value of the wrap is sound inside the helper's present options. A `count` detail is clamped to
`MAX_COUNT = 9` (`ops_log_events.rb:63`, `ops_log.rb:650`), so one detail has at most ten values,
which is exactly the window. Two count details (100 values) would work for a cap of 12 or more but
still merge at caps 10 and 11, because the first row of each event is protected from eviction
(`ops_log.rb:822-824`) and so stays inside the window for ever.

**Smallest sound mechanism (suggested fix).** Say in the registry that these events never merge, and
have step 5 honour it:
- `ops_log_events.rb`: `'net_link_up' => { ..., merge: false }`, the same on `net_link_down`; drop
  the `detail: { 'step' => ... }` from both.
- `ops_log.rb` `ops_log_write_rows`, before the search loop: skip the search when
  `call[:definition][:merge] == false` (one condition on the `while`, or `found = nil` guarded).
- Remove `link_step_detail`, the `detail:` argument at both call sites and the `netLinkSteps` key.
- Plan 13.2 step 5 gains one sentence ("an event registered `merge: false` always appends"); the
  13.8 cell goes back to "none" for detail and says "never merged".
- Tests: twelve alternating plant and unplug calls give twelve rows in order with no `n` (or the cap's
  worth, newest last); a game's state holds no `netLinkSteps`; the registry check in
  `ops_log_events.rb` (near `:300`) accepts `merge: false` only as a Boolean.
This removes the new state key, the hidden detail and the counter, and leaves rows bounded by the
source cap and saves bounded by the routes' own saves, as 13.8 already says. It does edit the
helper (two lines), which the fixer avoided; the fixer's constraint cannot be met soundly.
If the helper must stay untouched, the honest alternative is to keep the counter and write down the
limit ("after ten link steps with no other row between, a step merges into the row ten back") in
13.8, A24 and PLAYTEST, with a test that pins it; I do not recommend it.

### The other questions on the mechanism (answers, for whichever mechanism stays)

  unedited. They diff state across a scan or a technique, with the plant done before the "before"
  snapshot, so the key is in both sides. Neither file, nor any list of state keys, names it.
- (b) **Wrap:** unsound, R2-1. **Bounds:** rows by the source cap (`ops_log_evict`), saves by the
  plant and unplug routes' own saves; `netLinkSteps` is one integer that only counts up.
- (c) **Never sent:** `ops_log_client_detail` (`ops_log.rb:520-532`) drops a key whose rule has
  `show: false`; `network_log_rows_test.rb:145` and the literal rows at
  `ops_logs_scenario_test.rb:457-459` (`'detail' => ''`) assert it. **400 bytes:** the ceiling walk
  (`ops_log_test.rb:573-594`) builds each event's detail from the registry, so `step: 9` is in the
  `net_link_*` ceiling rows. **Secret guard:** `find_secret_hit` compares a count only with numeric
  secrets of 10 or more (`ops_log.rb:232-234`), so a 0 to 9 step can never trip it or hide one.
- (d) **Simpler within the existing options:** no. `once:` drops a repeat instead of appending,
  `save_limit:` bounds saves, and `result` has one value; a detail is the only field left, and it
  cannot carry enough values (above). The simpler sound mechanism is outside the call: R2-1's fix.

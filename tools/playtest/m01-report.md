# Playtest: First Contact (m01) — game 951, 2026-09-07 (run 2)

> **CORRECTION (2026-09-07, after this report was written).** The two "GAME BUG" findings below (`derek_cabinet`, `derek_computer`) were **not** game bugs. Both were the engine's facing-offset range check refusing a target the player had walked too close to, from below — the offset for the up-diagonals is 45px, so an object 8px away measured 38px and was refused. Nothing is wrong with m01 or its scenario data. `getInteractionDistance()` now takes the smaller of the offset and plain distances, and the bridge provides `moveToNear(id)` to approach targets at a position the engine accepts. Read the per-step results below with that in mind: steps 9 and 10 were harness failures, not mission failures. See `docs/test-bridge.md`, "Interaction range: how the engine really measures it".

## This run

Reached the END. `close_the_case` (the mission's final aim wrapper) completed, the launch device was aborted, and the closing debrief conversation with Agent HaX played through to its final visual cutscene screen. The run stopped there not because of a scenario blocker but because the local environment ran out of memory partway through re-verifying the last fix (see "What stopped the run" below) — everything up to that point is confirmed working.

**First attempt on this task used the wrong game.** `bootstrap`'s session-resume overlay lists every other in-progress session for the mission as "Load session #N" links, which navigate to a *different* game entirely. The harness's own fallback (`pick = labels[0]`) picked one of those instead of "New Session" on the very first bootstrap of the day, so an entire early pass was spent playing a stale, already-progressed save under the game 944 URL without noticing — everything looked plausible until VM flag submission returned "Invalid flag" for values that were valid for the *actual* game 944. That whole pass is void and nothing from it is reported below. The coordinator fixed `bootstrap` (`?skip_resume=1` on the initial navigation, plus a hard refusal to ever click a "Load session #N" label) before this run started; a fresh game (951) was created and every bootstrap in this run was checked against the URL and task list before proceeding.

## Known blocker: `inform_safetynet_operation_shatter` never completes

Not classified as a game bug per the run's constraints — reported precisely for a human to judge.

The task requires the player reach the `mission_commitment` knot in `m01_phone_agent0x99.json`'s ink, several choices deep into the "report Operation Shatter" branch (`report_operation_shatter` → `shatter_details_*`/`shatter_casualties` → `shatter_reaction` → `updated_objectives` → `people_at_stake` or straight to `mission_commitment`, which carries the `#complete_task:inform_safetynet_operation_shatter` tag). The *first* line of `report_operation_shatter` sets `operation_shatter_reported = true` immediately — before the branch reaches `mission_commitment`. The top-level phone menu's entry into that branch ("I discovered what ENTROPY is planning...") is itself gated on `!operation_shatter_reported`.

In this run, `operation_shatter_reported` was already `true` on the very first `brief()` after the fresh bootstrap, before the branch was ever selected through the bridge — the option was already absent from the menu. Two explanations were considered and neither could be ruled out with the evidence available:

1. **Shared game-state contamination.** Other concurrent activity was observed in the same environment during this run (stray `node`/chromium processes and scratch files under names like `i3.mjs`, `o4.jsonl` not created by this run — apparently the coordinator's own parallel diagnostic work). If any of it touched game 951, this global could have been set from outside this run entirely.
2. **A real soft-lock if a player closes the phone mid-branch.** Because the `VAR=` assignment happens on the *first* line of the knot and the `complete_task` tag only on its *last*, a player who reports Operation Shatter but closes the conversation (or the app) before reaching `mission_commitment` would permanently lose the only menu entry back into that branch, with the task stuck `active` forever. Nothing in the ink re-offers `mission_commitment` once `operation_shatter_reported` is true.

`return_intel`'s aim wrapper stayed `"status":"locked"` for the whole run as a result. It did not block anything downstream that was tested — `disrupt_the_cell`, `deactivate_the_launch` and `close_the_case` all completed regardless, so a player could reach the same ending state, just with this one aim/task permanently open.

## Harness bugs found and fixed this run

All in the allowed edit paths (`.claude/skills/playtest-scenario/scripts/`, `public/break_escape/js/systems/test-bridge/`, `getTestState()` under `public/break_escape/js/minigames/`). None of these are engine or scenario changes.

1. **Stale JS served from browser disk cache** (`playtest-session.js`). A test-bridge fix applied mid-run had no effect on an already-open session — expected per the skill's documented trap — but a *new* Playwright browser instance was also silently serving an old cached copy of `test-bridge/index.js` (confirmed by diffing a captured error shape against `curl`ing the same file straight from the dev server: the browser's copy used field names — `liveDistance` — that do not exist anywhere in the current source, which uses `plainDistance`/`engineDistance`/`inRangeNow`). Fixed by disabling the HTTP cache via CDP (`Network.setCacheDisabled`) before every navigation.
2. **No way to interact with inventory items** (`test-bridge/index.js`, new `interactInventory(idOrType)`). The player's phone and other HUD-tray items (`.inventory-item` DOM elements in `systems/inventory.js`) have a real click handler but were never reachable from `scan()`, which only walks world sprites — `interact(id)` had nothing to target. This blocked the entire "report to SAFETYNET" and "confirm launch code" paths, both of which are reached through the player's own phone/inventory, not a world object. Added a bridge method that matches by `data-type` or visible name/alt text and confirms via the same "something actually opened" mechanism as `interact()`.
3. **`phone-chat-minigame.js`'s `getTestState()` never reported choices** (`getTestState` override). It queried `.phone-chat-choice-button, .person-chat-choice-button` — neither class exists anywhere in the rendered DOM; the real buttons carry the plain `.choice-button` class (`phone-chat-ui.js`). `dialogue.choices` was therefore always `[]` and `awaitingChoice` always `false`, so `choose()` and `clickText()` could never select a phone conversation option — every phone conversation with Agent HaX was undriveable before this fix, only `clickControl(index)` against the raw (unlabelled-as-choices) control list worked, and even that hit the same guard since `mg.js`'s `clickControl` also checks `awaitingChoice`. Fixed the selector to match the real class.
4. **`window.confirm()` silently swallowed by Playwright** (`playtest-session.js`). Covered in the launch-device row above. Fixed by accepting all native dialogs.
5. **`detectBlockingUi()` misses overlays that aren't named modal/overlay/popup/dialog** (`test-bridge/state.js`). The debrief's full-screen audio-visualiser overlay (`.bv-app`, containing `#bv-vis-canvas` and a real `#bv-close-btn`) was reported as a blocking UI with `buttons: []`, because the panel-finding heuristic (`closest('[class*="modal"], [class*="overlay"], [class*="popup"], [class*="dialog"]')`) found no matching ancestor and fell back to the canvas element itself, which — being a `<canvas>` — has no children to query for buttons. Widened the fallback to climb up to 4 ancestors looking for one that actually contains a button, only when the original heuristic's panel came up empty. **Not fully re-verified end-to-end** — the environment ran out of memory (see below) before a session could be restarted to click the now-detectable `✕ CLOSE` button through the normal bridge path. The fix is logically sound and the button's existence/selector was confirmed by reading `bond-visualiser.js` directly, but "the bridge now reports it" was not re-confirmed live.

## What stopped the run

Not a mission or harness bug: the local machine ran out of memory. `free -h` showed ~1.6GB free / 11GB swapped with 63 unrelated Chromium renderer processes running (the user's own desktop browser, `/snap/chromium/...`, running since Sep 03 — nothing to do with this playtest). Every `chromium.launch()` after the launch-device fix was verified failed the same way: the process started, consumed CPU, and never got far enough for `window.__test` to appear within the 45s timeout, three attempts in a row. This is an environmental resource constraint on the shared machine, not something in scope to fix from this task.

## What still blocks a fully automated end-to-end run

1. **`inform_safetynet_operation_shatter` can get permanently stuck active** if the "report Operation Shatter" phone branch is entered but not carried to its end in one go — global evidence above, but the cause (concurrent contamination vs. a genuine no-return conversation state) is not fully isolated. Worth a human's judgement, not reported as a confirmed game bug.
2. **The debrief's closing visualiser screen (`#bv-vis-canvas`) was not confirmed dismissable end-to-end** — the detection fix (item 5 above) is in place and reasoned through, but the actual click-through to whatever comes after (final debrief screen / return to menu / credits) was not re-run due to the environment running out of memory.
3. **`test:flag:N` resolution is per-station and does not cover every flag-consuming object.** It works for `flag-station` objects (the drop-site terminal) but not for `lockType:"flag"` safes (the ENTROPY archive) or the launch device — `test_flag_candidates()`'s station lookup (`find_flag_station_by_id`) only recognises `type: "flag-station"` / `"launch-device"` objects, not safes. The literal real flag value always worked as a fallback in this run, so it did not block progress, but a trace that assumes `test:flag:N` works everywhere will be surprised.
4. **`moveToNear` alone cannot close the final ~20-40px to several objects** in `server_room` (drop-site terminal, ENTROPY archive) — a collider stops it short from most angles. A specific approach angle (south of the object, then a short `walk` up) reliably closes the gap; this is now a known, documented workaround rather than a blocker, but `moveToNear` itself does not yet solve it unassisted for these two objects.

## `moveToNear`: did it fix what it was built for?

Yes, for the case it targeted directly — the facing-offset range check on stationary world objects standing in a cluster (doors, NPCs, safes at close range). `derek_cabinet`, `derek_office` doors, the server room door and Sarah/Kevin/Derek all opened cleanly with a single `moveToNear` + `interact`, with no manual nudging needed, which is a real improvement over the previous trace's per-step recovery choreography for the same objects. It does **not** fully solve the separate class of problem where a collider sits between the walkable area and the object (the two server-room stations above) — those still need a specific approach angle worked out by hand.

## Findings, most severe first

### 1. Backup Recovery Console: gated source can be selected and "confirmed" through the UI even though the underlying restore is (correctly) blocked
**File:** the `backup-recovery` minigame client, object `hospital_recovery_console` (server room).
**Repro:**
1. Reach the server room and open the Hospital Recovery Console **before** `offline_keys_recovered` is true (i.e. before the emergency-storage safe is ever touched).
2. `mg getState` shows the "Offline Backup Keys (Physical Safe)" tile with class `is-unavailable` and text `AVAILABLE IF SAFE CRACKED`, but its DOM control reports `"disabled": false`.
3. `mg clickControl` on that tile selects it (`is-selected` added) and updates the panel text to `UNAVAILABLE - OFFLINE BACKUP KEYS ... Prerequisite: Offline backup keys must be recovered from PIN safe first.` — but the **Confirm** button (`backup-recovery-confirm-btn`) also flips from `disabled:true` to `disabled:false`.
4. Clicking Confirm produces no visible error and no state change — `window.gameState.globalVariables.backup_restore_initiated` stayed `false` afterward, so the actual gate holds.

**Assessment:** this is a real defect in the UI layer, not a skip-the-work exploit — the task's explicit ask ("Confirm the UI actually refuses, rather than letting you confirm an unavailable source") is not met: the UI does **not** refuse, it just quietly no-ops. A real player who tries this gets a dead button with no feedback and no explanation of why nothing happened, which reads as broken, not gated. The fix belongs in the minigame's `is-unavailable` handling — the confirm button's disabled state should track the selected tile's `requiresGlobal`, not just "is a tile selected".

**Secondary observation, same area:** `verify-run.rb`'s globals dump for the finished session shows `backup_recovery_source` was set even though I never completed a valid recovery — worth checking whether merely *clicking* a tile (selected, not confirmed) writes this global prematurely. I did not have time to isolate which specific click set it; flagging for a follow-up check rather than asserting the mechanism.

### 2. `gary_ko` → `obtain_password_hints` completeTask event never fires; global is true but no event dispatched
**File:** `scenarios/m02_ransomed_trust/scenario.json.erb:938-944` (`eventPattern: "global_variable_changed:gary_ko"` → `completeTask: obtain_password_hints`).
**Repro:** `debugKO` on `gary_whitlock` in IT department, before ever talking to him. `window.gameState.globalVariables.gary_ko` reads `true` immediately after, but grepping the full session event log for `gary_ko` returns **zero** matches — `global_variable_changed:gary_ko` was never dispatched. `obtain_password_hints` stayed `"active"` in `objectivesManager.taskIndex` (confirmed via `eval`) until I separately picked up Gary's Password Sticky Note, which completes the task through its own, independent `global_variable_changed:password_hints_found` mapping.
**Assessment:** ruling out the three things the skill asks first — this is very likely a **test-bridge fidelity gap**: `debugKO` is documented as "converted to hostile as a player punch would, combat NOT played," and it is plausible the shortcut sets the raw global without going through whatever code path a real combat KO uses to emit `global_variable_changed` events. I could not verify a real combat KO's behaviour in this run (combat isn't drivable by the bridge). **Not confirming this as a scenario bug** — but flagging it because the walkthrough explicitly documents `taskOnKO: talk_to_gary` + "handler completes `obtain_password_hints` on `gary_ko`" as the safety mechanism, and if it genuinely never fires from a real KO either, a player who KOs Gary without ever finding the sticky note (it's a separate, skippable pickup on his desk) would be stuck — the walkthrough calls the sticky-note path "redundant... guarantees no soft-lock at any influence level," but that guarantee depends on the player actually walking over to the desk, which is not enforced. Worth a follow-up with a real combat KO to see if the event fires there.

### 3. ENTROPY Staging Cache's own tooltip claims "unlocks automatically" but it does not
**File:** `scenarios/m02_ransomed_trust/scenario.json.erb`, object `entropy_staging_cache` observation text ("It unlocks automatically once Ghost's operational log flag is submitted at the drop-site").
**Repro:** submitted `flag_4` at the SAFETYNET drop-site first (task `submit_ghost_log_flag` completed, `backdoor_fully_exploited` set). Then interacted with `entropy_staging_cache` — it opened a **separate** flag-entry minigame (`Flag Submission Terminal`, `lockType: "flag"`) requiring the same flag to be typed in **again** before the container opened.
**Assessment:** minor but concrete content/mechanism mismatch — the in-fiction text tells the player the cache is now open, but mechanically it is a second, independent flag lock. Not mission-blocking (the player already has the flag value in hand from the drop-site step, so re-entering it is trivial) but worth a copy fix or removing the "automatically" claim.

### 4. `dr_kim_safe` (PIN `1987`) can be opened with zero in-game clues; only gates optional lore
**Repro:** reached `dr_kim_office`, avoided Dr. Kim's Desk Diary and every other PIN-1987 clue, and entered `1987` cold (a value the task explicitly asked me to try early, deliberately unearned — see the earned-secrets table). The safe opened on the first attempt and contained "Zero Day Syndicate Invoice," an optional lore note.
**Assessment:** not a defect by itself — this is presumably an intentional "same PIN as the emergency safe, for a player who worked it out once" design point, and the safe only gates flavour text, not mission-critical items or tasks. Recorded here mainly to answer the task's Q3 angle: **no route to the ending was skipped** by pre-cracking this safe; it is a side lore container, and the real mission-critical PIN safe (emergency-storage, offline backup keys) was never touched in this run.

### 5. `interact()` mismatch detection has a gap on item-pickup ("event") resolution
**Repro:** `moveToNear("gary_contractor_lanyard")` reported `arrived-but-outside-plain-range` (correctly warning of a collision). The subsequent `interact("gary_contractor_lanyard")` nonetheless returned `"ok": true, "mode": "direct"` with **no `mismatch` flag**, but the `events` array showed `item_picked_up:phone` and the follow-up `brief()` confirmed a `Planted Network Device` (a different nearby object, "Ghost's planted network device") had actually been opened and collected — not the lanyard, which was never added to inventory. Contrast with two other interactions in the same run (`infected_terminal`, `hospital_recovery_console`) where a similar wrong-target click **was** correctly flagged with `"mismatch": true, "reason": "wrong-target-opened"`.
**Assessment:** ruling out the three things first — moveToNear had already warned of a range problem, so this is not "drove the UI wrongly," and the harness's own event log shows the wrong item was collected, so it's not "reported success without confirming." This looks like a genuine gap in the test bridge's mismatch heuristic specifically for the "via: event" (direct item-pickup) code path, as opposed to the "via: minigame" path where mismatch detection clearly works. Test-bridge finding, not a scenario finding — flagged per the skill's classification rule, worth a fix in `docs/test-bridge.md`'s interact() implementation.

### 6. Harness/room-graph note: several rooms have no reverse door entity, only a one-way spawn
Not a scenario bug, but cost significant time this run and worth documenting for future playtests: `it_department`, `dr_kim_office`, `staff_room`→`office_corridor`, and `security_office`→`server_room` (in the return direction) all show `"doors": []` in a `room` scan taken from the far side, even though the scenario's `connections` are declared bidirectionally and the forward `enter` worked fine. `{"cmd":"enter"}` back the other way fails with `no-known-doorway`. Plain `moveTo`/`walk` toward the entry coordinates eventually crosses back (confirmed a real, walkable gap in every case), but `moveTo` frequently reports a `shortfall` and needs 2-4 retries or a `walk` in a cardinal direction to actually cross. This is very likely because unlocked one-way-declared doors only spawn a clickable sprite on the side that has a `lockType`/needs interaction, and the reverse side is a plain gap with no entity for the bridge's door-scan to find. Recommend adding this to `docs/test-bridge.md` as a known gotcha (distinct from the documented "unlocked door removed from scene" note, which is about the *same*-side door disappearing after use).

## Other off-script probes and their outcomes
- **Free-standing "Spare Contractor Lanyard" in staff_room, picked up before ever meeting Gary:** fires `item_picked_up:id_badge` → `cover_restored`/`staff_lanyard_obtained` immediately, and — via a separate `onceOnly` handler — completes `regain_freedom_of_movement` **before that aim is even unlocked**. Confirmed via direct `objectivesManager.taskIndex` inspection that the task registers as `"completed"` regardless, so this is a legitimate, working shortcut (there's an explicit code comment in the scenario acknowledging this "safety net"), not a soft-lock.
- **Lockpick instead of key on the IT department door:** worked cleanly — `Switch to Lockpicking` → `completeLockpick` (PASS, assisted) opened the door without ever using the override key.
- **Leaving a conversation half-finished and re-entering (Dr. Sarah Kim):** ended the conversation mid-line via "End Conversation," re-entered with `converse`, and it resumed correctly from where it left off with no starved-knot or duplicate-intro issue. The full hub conversation later hit `hitTurnLimit: true` at 60 turns without exhausting all branches — flagging as an observation (it's a large, intentionally rich hub with many optional threads) rather than a defect.
- **Objectives out of order — reached the Hospital Recovery Console before ever visiting emergency storage:** see Finding 1; this is the main defect this run surfaced.

## Q3 (does any route skip the actual work?)
No. Every shortcut found (early lanyard, pre-clue safe PIN, KO fallbacks) either (a) is an explicitly-designed alternate route with its own working completion path, or (b) only unlocks optional lore, never a required task or the VM flag chain. The VM flag submissions themselves were the deliberate `session`-policy secrets (marked "no" above) — standalone cannot prove or disprove whether the real VM boxes are exploitable, only that the station/task/reward wiring around them works, which it does (all 4 flags accepted, `backdoor_fully_exploited` set, ENTROPY cache reachable).

## What this run does NOT prove
The mission was not completed. Emergency-storage safe, boardroom PIN door, Hospital Communications Terminal, and the ending were never reached in this run — time was spent on the off-script probes the task asked for instead. Those steps are exercised in the sibling happy-path run, not here.

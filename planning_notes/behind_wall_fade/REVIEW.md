# Behind-the-wall fade: adversarial review

Reviewed 2026-11-08 against the working tree (engine read, nothing edited) and phaser@3.60.0 sources fetched from jsdelivr. Paths are relative to `public/break_escape/js/` unless stated. Phaser links are `https://cdn.jsdelivr.net/npm/phaser@3.60.0/<path>`.

Counts: **1 blocker, 6 major, 9 minor.**

## Blocker

### B1. `this.time.delta` doesn't exist: the fade factor becomes NaN and the faded tiles vanish

- **Evidence.** §5 says to call `window.behindWallFade?.update(this.time.now, this.time.delta)`, and §4 steps `k` by "scene.time delta". In Phaser 3.60 `scene.time` is a `Clock`, which has `now`, `startTime`, `timeScale` and `paused` and no `delta` (src/time/Clock.js:57, 68, 142, 355; the only `delta` is the argument to `update(time, delta)` at :353). `update()` in core/game.js:2469 takes no parameters. The existing `npcBehaviorManager.update(this.time.now, this.time.delta)` (core/game.js:2484) already passes `undefined`, but nobody noticed because systems/npc-behavior.js:158 never reads it.
- **Failure.** `k += sign * undefined / 150` gives NaN and stays NaN. `tile.alpha = NaN` passes through `Clamp` unchanged (src/gameobjects/components/Alpha.js:147). RunCull only skips `alpha === 0`, so the tile still renders, but `getTintAppendFloatAlpha` packs `(NaN*255)|0 = 0` (src/renderer/webgl/Utils.js:52). On WebGL the south room's top two rows disappear for good the first time the player steps into the strip. Canvas ignores a NaN `globalAlpha`, so the bug would hide on Canvas. The node tests in §8 drive a fake clock with an explicit dt, so they would pass.
- **Fix.** Change `update()` to `export function update(time, delta)` and pass those, or keep `lastNow` in the module and use `dt = now - lastNow`. In either case clamp dt to `[0, 250]` and add a `Number.isFinite(k)` guard that snaps back to 1. Add a static test asserting the hook call doesn't read `this.time.delta`.

## Major

### M1. Row 1 is drawn twice, so a 50% fade composites to 75% and shows the wrong wall art

- **Evidence.** In every room, `walls` (depth +0.2) and `room` (+0.4) both draw row 1 (core/rooms.js:2032-2084). A script over all 147 maps found 1,471 non-empty `walls` cells in rows 0-1, and only 190 of them have the same gid as the `room` tile above them. In bespoke rooms `walls` row 1 is the generic `office-updated` strip (gids 12-19) while `room` row 1 comes from the room's own tileset. For example, room_aes_control `walls` r1 = `0,12..19,0` and `room` r1 = `711..720`. Today the opaque `room` tile hides the `walls` tile completely. Two door sprites also sit on the same point: S's north door and N's south door (systems/doors.js:92/117 and 187/209). Both are visible until the door opens.
- **Failure.** With both layers at 0.5, row 1 composites to 1 − 0.5² = 75% while row 0 is 50%, so a visible band appears. In about 90% of wall cells the generic office wall also ghosts through the bespoke art. The closed door in the strip shows the same 75% double.
- **Fix.** Fade only the topmost drawn tile per cell. While S is faded, set `tile.visible = false` on `walls` tiles in rows 0-1 wherever `room` has a non-null tile in that cell (RunCull skips `!tile.visible`, src/tilemaps/components/RunCull.js:47), and fade `room` alone. Restore `visible = true` at k = 1, and add that to `reset`. Handle coincident door sprites the same way: fade one and hide the other while faded. Add a unit test for the composite, and check the 75% band in the screenshot step.

### M2. The bottom-edge test catches table items and carried items, and measures rotated props differently from the engine

- **Evidence.** Table items get `elevation = 0` and depth `table.baseDepth + n*0.01` (core/rooms.js:736, 838, 2533-2537). Their sprite bottoms can still sit above `S.y+64`: 56 `table_items`/`conditional_table_items` objects across the maps have bottom ≤ 64 (script survey; e.g. room_aes_ops, room_lw_reception, room_reception, small_office_room1_1x1gu). NPC-held props are repositioned every `postupdate` to the carrier's hands (systems/npc-office-visuals.js:558, ~280). An NPC standing on S's front floor row holds them at about `S.y+50`. The engine's own threshold is `sprite.y + sprite.height < pos.y + 64` (core/rooms.js:432-445, 2722-2727), which is unscaled and unrotated. `getBounds()` grows with rotation (core/rooms.js:347-349 applies Tiled rotation).
- **Failure.** A monitor on a desk against reception's back wall goes to 50% while the desk stays opaque (desks are left alone under the Q1 default). A mug in an NPC's hand fades while the NPC doesn't. A 1-2 angled wall prop flips class depending on its rotated bounding box.
- **Fix.** Classify once, at creation. In `setDepthAndStore` and the Tiled-object path, set `sprite.backWallItem = true` when the auto-elevation branch fires (`bottom < threshold`, and also `=== threshold` if wanted). Never set it on table-group members or on sprites with an explicit `position.elevation`. The fade then reads the flag and also skips anything with a held/carrier marker. This is a two-line engine change, and the flag doesn't move when the sprite moves.

### M3. The strip's light stays the south room's, so the revealed player is a dark silhouette in a common case

- **Evidence.** `fillAreas` gives the strip to the room further south (systems/lighting.js:1335-1355). Fills are drawn brightest first, then the player's room first among dimmer ones, "so its torch … is covered where it crosses into a neighbour" (systems/lighting.js:1070-1085). A motion-sensor room is dark while nobody is in it, and the player in the strip is in N. The test scenario sets reception to `motion` and office1 to `on` (§8).
- **Failure.** The feature's purpose is to let the player see their character. In this case the 50% wall shows a player multiplied by S's dark ambient, and their torch is covered too. Screenshot step 5 will show this. Risk 2 calls it "unchanged from today", but today nothing is revealed, so nobody sees it.
- **Fix.** Make Q4's default "the strip takes the player's room light while faded". In lighting, when `behindWallFade` reports S faded with factor k, draw the strip `[S.x, S.y, S.w, 64]` (clipped to the player's room) with the player's room ambient at weight (1 − k)/0.5 after S's fill, or leave the strip out of S's `fillAreas` while faded. Add this to slice 3 and test it with a dark S and a lit N.

### M4. Under the Q1 default the player stays hidden behind tall furniture in most rooms

- **Evidence.** 102 of 147 maps have a floor object whose bottom is below the threshold but which reaches more than 8 px up into the strip. Most common: bookcase ×35, filing_cabinet ×19, server_rack1 ×13, safe2 ×13, batrack ×12, binder_shelves1 ×11 (script over Tiled object layers). These sort at `bottom + 0.5`, which is above any player in the strip (the player's max depth is about `S.y+54.5`, core/player.js:958-962 with `SPRITE_PADDING_BOTTOM_ATLAS = 6`).
- **Failure.** The commonest back-wall dressing is a bookcase or rack against the wall. A player behind it sees the wall go to 50% around an opaque cabinet that still covers them.
- **Fix.** Put the numbers into Q1 and propose a third option: fade any S sprite (prop, table group or NPC) whose display bounds overlap the **player's sprite bounds** and whose depth is above the player's. That is local and only touches things that actually cover the player, which avoids "fading a whole cabinet to show a wall row". If the user keeps "leave", say in the request that most rooms will still hide the player in places.

### M5. Candidate rebuilds can strand a sprite at 50%

- **Evidence.** §4 builds candidates "when S first enters the faded set" and rebuilds "when objects / doorSprites / animatedDoors length changes". It doesn't say whether records survive a rebuild, or what happens to a sprite that drops out. Objects leave `rooms[S].objects` at runtime: systems/npc-needs.js:3308 moves a sprite to another room, and systems/room-state-sync.js:117 deletes an entry. A length-only key also misses a swap where one object goes out and one comes in.
- **Failure.** The player stands in the strip with reception at 0.5. A needs routine moves a reveal-slot sprite out of reception, the rebuild drops its record, and that sprite keeps `alpha = base*0.5` in its new room for the rest of the session.
- **Fix.** Keep records in a `Map<sprite, {base, applied, roomId}>` separate from the candidate list. On rebuild, restore (or step to 1) every record whose sprite is no longer a candidate before dropping it. Use a version counter or a set comparison, not lengths. Add a unit test: a sprite removed from `objects` mid-fade ends at its base alpha.

### M6. The test scenario can't produce the geometry the plan tests

- **Evidence.** room_reception, room_office and room_ceo are all 10×10. With reception at (0,0), `positionNorthMultiple` centres office1 and office2 and snaps them to the 160 px grid: office1 x ∈ [−160, 160], office2 x ∈ [160, 480] (core/rooms.js:1443-1500). ceo is then placed from office1 by `positionNorthSingle` with equal widths, so x = office1.x = −160 (core/rooms.js:1411-1436, queue order 1806-1858). ceo covers office1 only, and its east wall sits at the office1/office2 seam. §2's "under a wide N, as in test_vertical_layout's ceo above office1 + office2" is false, and so are §8's "two narrow Ss under one wide N" and step 7 ("shared edge under ceo, both offices fade"). office2's north door to ceo is also placed from ceo's spacing (systems/doors.js:80-95), outside office2's x range.
- **Failure.** Live step 7 can't be reached. The "two strips at once" path ships with only a unit test.
- **Fix.** Use a 20-wide N (e.g. room_m10_hall, room_aes_hall1, room_pnw_genhall: 20×10) with `south: [a, b]` over two 10-wide rooms. `positionSouthMultiple` puts them side by side under it (core/rooms.js:1537-1590). Keep reception under office1 for the plain case, and put one office on the north side of a narrower or wider S for the alignment case.

## Minor

1. **Writers later in `update()` win for one frame.** After the hook come `doorGates.update`, `checkObjectInteractions` (which can open a door synchronously and create `animatedDoors`), lighting and the bump effects (core/game.js:2496-2540). §4's "each frame ends with our multiplied value" therefore holds only against writers that run earlier. The effect is a one-frame pop at most. Fix: run the sprite pass in `postupdate` (register it after seating's, systems/seating.js:1520) and keep the tile pass where it is. Lighting then reads `behindWallK` one frame late, which can't be seen.
2. **The door visibility pass is dead code.** `updateDoorSpritesVisibility` (systems/doors.js:1338, 1386-1389) has no callers. It's only imported and re-exported (core/rooms.js:74, 3441). Drop it from the alpha-writer list in §1.
3. **"Never centred" is wrong for groups.** Multiple N/S neighbours are centred on the parent and then snapped to the 160 px grid (core/rooms.js:1452-1456, 1546-1550). Only single neighbours are edge-aligned. The geometry rule doesn't depend on this, so fix the text.
4. **§1 layer details are off.** `walls` row 0 isn't empty in 13 maps (e.g. small_office_room4_1x1gu, small_room_storage_1x1gu), and those tiles get an extra collision box at `S.y+24..32` (systems/collision.js:61-71 runs for `tileY < 2`). `walls` row 1 has empty end columns in the sampled maps (`0,12..19,0`), so it isn't "fully filled". `room` has gaps in rows 0-1 in small_room_closet_east_connections_only_1x1gu. The "every layer" rule absorbs all of this, but M1 needs the per-cell check.
5. **LEDs are always above the light map.** They sit at `LIGHT_DEPTH + 2` in every room (systems/lighting.js:743-746), not only in dark ones. Slice 3 has to multiply LED alpha in lit rooms as well.
6. **Doorway suppression only works because of an accident.** The opener sprite is destroyed but stays in its room's `doorSprites` with `open = true` (systems/doors.js:876). Only the far sprite is spliced out (doors.js:1003-1007). "Already removed" doors can't be found at all. Gate doors also flip `props.open` back (systems/door-gates.js:200). Write this dependency down in the module and test the destroyed-but-listed case. The alternative is to derive doorways from `calculateDoorPositionsForRoom` (doors.js:327).
7. **Live-proof clicks can land on wall objects.** `moveTo` on an on-screen point synthesises a canvas click (systems/test-bridge/index.js:538 onward). A click on reception's back wall at the x of a wall-hung noticeboard interacts with the board instead of walking. In step 3, choose an x clear of the test wall objects or use arrow keys.
8. **`reset` on shutdown.** By the time `shutdown` fires, the tilemap layers may already be destroyed, and `getTileAt` on a destroyed layer throws. Wrap each room's restore in try/catch. Restoring tiles matters less than leaving no state behind, since `rooms` is rebuilt (core/rooms.js:1012-1013).
9. **Small citation slip.** The body size at core/player.js:137 is set in the sprite-swap path. Creation sets it at :231 (same 18×10).

## Claims verified as correct

- Stacking geometry: `stackingHeightPx = (h − 2) * 32` (core/rooms.js:1222, constants.js:29). N = S.y − N.stack (1416), S = N.y + N.stack (1508). All 147 maps have `(h − 2) % 4 == 0` and 32 px tiles, so `alignToGrid` never shifts the two-row overlap.
- Layer creation, depths (+0.1/+0.2/+0.15/+0.3/+0.4), the skipped `doors` layer, `roomWorldY = pos.y + 64`, starting hidden at alpha 0, the `rooms[id].layers` keying, and tiles under doors removed with `replaceWithNull` (core/rooms.js:1995-2089; systems/collision.js:265-270, 483-488, 564-570).
- The player always sorts under S's layers in the strip: N's last-row box and the N/S door body both sit at `S.y+56..64` (collision.js:73-82; doors.js:576-577), so feet stop at `S.y+56` and player depth is at most about `S.y+54.5`, below `S.y+64.2`.
- `updatePlayerRoom` (core/rooms.js:3121-3150) and `roomIdAtFeet`/`playerFeet` (systems/interaction-walls.js:85-99, 211-219) agree with the feet rule in §2.
- `revealRoom` sets layer alpha 1, door alpha 1 and object `originalAlpha || 1` (core/rooms.js:3074-3106); `showRevealedObject` (3047-3051); `hideRoom` is unused (core/game.js:2809).
- Phaser per-tile alpha: WebGL `getTint(tile.tint, camera.alpha * src.alpha * tile.alpha)` (src/tilemaps/TilemapLayerWebGLRenderer.js:27, 84); Canvas `globalAlpha = alpha * tile.alpha` (TilemapLayerCanvasRenderer.js:121); RunCull skips `alpha === 0` and `!visible` (components/RunCull.js:47); `Tile` mixes in Alpha (Tile.js:43-47). Culling is recomputed every frame (CullTiles.js). No engine code bakes, caches, masks or pipelines a tile layer. The renderer is `Phaser.AUTO` (utils/constants.js:77), and both paths honour tile alpha. No engine code writes tile alpha. Per-tile alpha costs nothing extra.
- Tweens and timers run on the scene `UPDATE` event, before `scene.update()` (src/scene/Systems.js:360-366; tweens/TweenManager.js:237; time/Clock.js:162-163). npc-sprite-style ticks there too. The base/applied scheme copes with the `tint_objects` pulse tween (systems/apply-actions.js:318-325).
- The npc-sprite-style base/applied scheme is as described (systems/npc-sprite-style.js:133-150).
- N/S door placement at `S.y+32`, 64 px tall, depth `bottom + 0.45`; `animatedDoors` at +0.45/+0.55 stored on the connected room; far sprite removed on open (systems/doors.js:92-117, 187-209, 480-487, 828, 931-1009, 1150-1195). E/W doors sit at `y + 80` and wall depth, never in a strip.
- Lighting: screen-sized MULTIPLY render texture at `LIGHT_DEPTH` (systems/lighting.js:368-375); `fillAreas` caching by room count (1337-1342); glow alpha written each frame (1152-1153, 1167-1172); `?lighting=off` and `reducedMotion` (346-365).
- Rooms are never unloaded, and `rooms` is replaced in `initializeRooms` (core/rooms.js:1012-1013).
- Test plumbing: `bin/test-js [file…]` runs plain node; every test that touches game.js reads it as text, so a new import there doesn't hit the copy-list problem; the data-URL loading pattern exists (test/js/interaction-walls.test.mjs:17-21); `__test.moveTo` and `waitUntil` exist (systems/test-bridge/index.js:25-26, 42, 538; wait.js:20); the headless loop snippet matches the known fix; the keyless server scripts exist.
- Performance: detection and tile writes are as cheap as stated. The hook position after `updatePlayerRoom()` is right for tiles (see minor 1 for sprites).

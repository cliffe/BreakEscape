## What works

- **The lesson is one a clerk can repeat on Monday** and it matches `concepts.md`: found or posted stick goes to IT unplugged; work stays in work places; free is not free; if the official way is slow, ask IT; no blame for a workaround. The `mondayCard` and the host's closing lines land it plainly.
- **No-blame register throughout.** Colin is likeable and right that the share was slow (`strings.noBlameLine`), Nilesh is quick and kind, the montage shows consequences not idiots, and "nobody's in trouble for a workaround" is said twice (host ink, no-blame line). The spec's "Do not" list (section 18) is honoured.
- **Facts are accurate.** The four "no"s, the Tischer kindness/curiosity point ("Kindness and curiosity are why people plug them in", row 3 reply), "everyone uses it" as how shadow IT spreads (row 4), the DPO route for personal data (`mondayCard`), rota-as-shadow-IT with leaver access (Swap Shop `sw_rota_app`, mistake `rota_app`) all trace to `concepts.md`.
- **The mirror pair is well built.** Row 4 (an "everyone uses it" PDF-tool lure) is immediately followed by row 5, a genuine share-link email from the firm's own `fileshare.tarrowby.example`, to a named person, with an end date, carrying the full `whyFine.default` and a `falseAlarmCost`. That is exactly the "suspicious-looking genuine item after a likely miss" the brief asks for.
- **Fictional-world hygiene is clean.** `.example` on every domain, `07700 900142` in the Ofcom drama range, no real brands, Chuckbox/Benmoor/PDFmangle all plainly outside services (not Tarrowby look-alikes), `BRAND_ADDITIONS.md` lists the pre-ship web-search check.
- **Host lines are easy to voice**: calm-colleague register, no printed variables, all under 30 words (dialoguelint max 24/28).

## Findings

### MA1 — The USB-drop-test reveal has no home anywhere in the build. Major, episode-local.
Spec section 12 (`E15_shadow_it.md:363-364`) names a debrief beat: Nilesh reveals "That stick in the post was ours. Authorised test. It just tells us it was plugged in," showing only the learner's own result, naming nobody, and saying why people plug sticks in. A grep across both shells, all three fragments and both ink files for "was ours" / "authorised test" / "plugged in" returns **nothing**. The line is not in `strings`, not in the host ink, and the debrief view has no dedicated reveal slot (`debrief-view.js` string keys are cards, `defendOnly`, `conceptPanel`, `voicePanel`, `ruleOfThumb`, `mondayCard`, `noBlameLine` only). So the payoff that ties the posted-stick beat together, and the one place the episode would explain the plant and reassure the learner, is simply missing.

Fix (episode-local): the debrief already renders an optional `strings.conceptPanel` (plain text, or an array of `{ heading, text }`) between the per-item cards and the Monday card (`debrief-view.js:375-378`). Add it to `awarenessEpisode.strings` in the shared fragment so it ships in both shells, carrying the reveal, for example:
- `"conceptPanel": { "heading": "About that stick", "text": "The stick that came in the post was ours: an authorised test, and it only tells us a stick was plugged in. We name nobody. Most people who plug a found stick in are being kind, trying to find the owner, or just curious, so the kind move is to hand it to IT." }`

This keeps it in the only slot the engine offers, reuses the real teaching from `concepts.md`, and holds on every path (it does not assume the learner plugged anything in).

### MA2 — `defendIntro` describes the Swap Shop as still to come, but it has already happened. Major, episode-local.
ENG-11 runs the sort drill **first** inside the defend stage, then opens the inbox (`episode-model.js:122` "`episode.sortDrill` runs first inside the defend stage"; `episode-runner-minigame.js:758-767` launches `sort-drill` before the triage set; `defendCopy` sets the inbox panel's text to `strings.defendIntro`, `episode-runner-minigame.js:182-183`). So by the time `defendIntro` is shown, the Swap Shop match is done. Its text (`scenario.json.erb:413`, mirrored `defend.json:208` and the defend shell `scenario.json.erb`) reads:

> "Go through the found sticks and 'quicker way' messages and decide what to do with each, **then match each shortcut to its approved swap.** A found or posted stick goes to IT unplugged; if the official way is slow, ask IT rather than build a way round it. There's no clock on you here."

The "then match each shortcut to its approved swap" clause is now backwards: the match is already behind the learner. (The spec's section 11 prose lists the drill after the scored set, which is what the copy was written to; ENG-11's fixed drill-first order overrides that, so the copy, not the engine, is what should move.)

Fix (episode-local): drop the stale clause so the line introduces only the inbox, and carry the "match the swaps" framing in the Swap Shop's own launch strings (see MI4). Old -> new for `defendIntro` (both shells, shared fragment):
- old: "Go through the found sticks and 'quicker way' messages and decide what to do with each, then match each shortcut to its approved swap. A found or posted stick goes to IT unplugged; ..."
- new: "Now go through the found sticks and 'quicker way' messages and decide what to do with each. A found or posted stick goes to IT unplugged; ..." (rest unchanged)

`strings.brief` and `_defendOnly.brief` list the two activities in the same order but without an explicit "then", so they read as order-neutral and need no change; only `defendIntro` asserts the sequence.

### MI1 — The posted stick is a genuine reception email flagged as action-needed, and `vish_callback_pressure` is a stretch on it. Minor, episode-local.
Row 1 (`defend.json:36-58`, `scenario.json.erb:91-128`) is from Tarrowby Reception on the real `reception@tarrowby.example`, all auth pass, genuinely sent; the hazard is the physical stick and the note's number, which the email only relays. It is modelled `isPhish: true` so Trust scores zero (`triage-scoring.js:76`), i.e. a learner who trusts a genuinely-from-reception email is marked down. This follows the documented E8 "genuine-address but action-needed" pattern and both Verify and Report score full, so it is defensible and the `reportReply` handles it well. Two things still grate: (a) the `vish_callback_pressure` tell is for voice-callback pressure, but nothing in the email pressures a call; a note inside an envelope carries the number, and the email just mentions it. (b) The learner is really being asked to act on the stick, not to distrust reception. Consider dropping `vish_callback_pressure` from this message (leaving `found_media`, the honest tell) and letting the "ring a number you already hold, not the note" point live only in the per-flag note and reply; or keep it but make the body's own line read as pressure. Not a blocker: the reason text already carries the core_02 teaching the spec asked for (section 18 "do not treat the Verify-on-the-note branch as a trap").

### MI2 — Reporting everything is unpenalised, and only one of the two genuine items teaches the cost. Minor, episode-local (with engine context).
The set is 4 action-needed + 2 genuine, which is the right structural answer to "refusing everything shouldn't win", and the mirror pair plus the quick-yes IT reply at row 6 keep the set from ending on "refuse everything". Worth stating plainly, though: under the `awareness` profile, Report scores full verdict points on a genuine item too (`real: { report: 60, verify: 60, delete: 30, trust: 60 }`, `triage-scoring.js:76-77`), so a learner who Reports all six scores full marks numerically. That is a product-wide property of the no-blame profile, not an E15 defect, and the set brief primes it verbally ("a real one does take a colleague's time to check"). The deterrent the brief relies on is the debrief's false-alarm cost, and only row 5 carries a `falseAlarmCost` (`defend.json:145`); row 6 (the IT reply) has none (`defend.json:157-163`), so over-reporting the genuine IT reply teaches nothing. Fix (episode-local): add a `truth.falseAlarmCost` to `e15_it_tool_reply`, e.g. "Reported as a scam, the one quick yes from IT you did get sits in a queue while someone checks a genuine reply." so both genuine items make the point.

### MI3 — The montage flags every beat as the learner's own, and never affirms a good choice. Minor, engine-adjacent / episode-local.
Because E15 authors a line for both options of every beat (`full_only.json:51-68`), `montageProps` finds the learner's chosen option every time, so `taken` is true for all four beats and `flip-view.js:142` paints `.aw-montage-taken` on every one (`episode-model.js:485-502`). For a learner who chose safely throughout, all four lines are the counterfactual "The version where it was taken instead ..." framing (the "Your choice" prefix is only on the unsafe lines), each with a short reassurance tail. So a fully-correct learner is shown four disasters, every beat highlighted as "yours", and no beat says plainly "your call kept the data safe". The engine's `taken`/`safe` flags on those beats and the text (which narrates the path not taken) pull against each other. This is defensible as a teaching montage ("see where each shortcut leads") and the text is verbatim from spec section 10, so it is a deliberate shape rather than a bug; logging it so the owner can decide whether the all-highlighted montage and the absence of any affirmation for the careful learner are what they want. If a change is wanted, it is a spec-section-10 decision (lead the safe-option lines with a short "Your call." before the counterfactual), not a silent edit.

### MI4 — The Swap Shop opens under generic default copy, not its own. Minor, episode-local.
The defend stage's launch panel, while the drill is pending, uses `drillLaunchCopy`, which falls back to the engine default "Sort the cards / Before the inbox, sort a set of cards into their bins. The reason shows after each one. / Open the cards" (`episode-model.js:127-131`) unless the drill sets `sortDrill.strings.launchHeading|launchText|launchButton`. E15 sets none, so the first thing the learner meets in the defend stage is generic copy, not the themed "Swap Shop". Fix (episode-local): add the three launch strings to `sortDrill.strings` (shared fragment, both shells), which also gives the "match each shortcut to the approved way" framing a proper home after MA2 trims it from `defendIntro`:
- `"launchHeading": "Swap Shop"`
- `"launchText": "First, match each shortcut someone might reach for under a deadline to the approved way that does the same job safely. Nothing here is marked."`
- `"launchButton": "Open the Swap Shop"`

### MI5 — The hand-off ink knot is unreachable. Minor, episode-local.
`nilesh_solanki.ink` (full shell) carries a `handoff` knot ("That's six months on. Now sort what's actually in front of you ...") that its own comment says is not reached by the hub, because there is no mid-episode global for the montage-to-defend transition to branch on. The content author already flagged this as an open question for wiring. It is harmless (the kiosk's stage framing covers the transition) but the dead knot should either be wired to the montage-to-defend hand-off if the runner supports a host line there, or removed so it does not read as live content. No learner-facing effect today.

## Verdict

**Approve with changes.** The episode is on-model, factually sound, no-blame throughout, and structurally does what the brief asks (one-aim conclusion, mirror pair, matched genuine item after the likely miss, both shells consistent, validators and E15 parity green). Two majors should be fixed before it ships, both episode-local string work: restore the authorised-USB-test reveal via `conceptPanel` (MA1), and correct `defendIntro` so it no longer promises a Swap Shop the learner has already done (MA2). The five minors are polish and one product-level observation about the forgiving `awareness` scoring. A `bridge-e15-full.jsonl` run and a single render of the montage and debrief are still owed (not done here) to confirm the fixes land on screen.

One line for the orchestrator: the three failing registry tests are caused by unregistered **E12 and E13** shells on disk, not by E15; E15 is registered and its parity passes.

## Findings

1. **Major — section coverage (doc §"The loop"/§"Open questions" OQ1).** BRIEF section 4 (explicit deterministic rules + worked example + exact per-factor feedback + the SecGen failure it avoids) is effectively absent from 02. 02 has its own *judged, interactive* element — the "derive the email pattern" sub-task, plus seeded-search intel detection — but its rules and feedback exist only as a default buried in OQ1 ("show two example addresses, player types the pattern"). No worked example, no pass/fail strings, no wrong-answer feedback. BRIEF calls legible feedback "the whole point". Fix: add a short rules/feedback subsection for 02's own judged interactions (derive-pattern and search): the exact prompt, what counts as correct, and the deterministic message shown on a right/wrong attempt, with one worked example.

2. **Major — intel feed to 03 (doc §"Engine wiring": "emits an intel-collected event the intel board (03) listens for").** Minigame overlays are modal — the manager holds a single `currentMinigame` (`minigame-manager.js` endMinigame logic around :208-230), so the intel board is not instantiated or listening while the browser overlay is open. A live event cannot be the reliable cross-overlay feed. The durable path is the `set_global` / persisted intel store the doc also mentions, which 03 must rebuild from on open (matches how notes persist a saved copy, `systems/interactions.js:1468`). Fix: state that intel is written to a persisted intel store + global as the source of truth, read by 03 when opened; the `intel_collected` event is live-UI flourish only (and only useful if 03 is ever a persistent panel).

3. **Major — feed to 01/06 asserted, not wired (doc §"The loop", §"Engine wiring").** "becomes usable in the composer (01) and pretext system (06)" and "sets a global ... so other components can gate on 'player knows the email pattern'" name no consuming global and no gate. 04's judging (`04` phishTargets.primedFor/trusts) is authored independently of what the player collected in 02, so on current specs collecting intel may gate nothing downstream. Fix: name the consuming global(s) and show at least one concrete gate (e.g. composer withholds a target until its `email_pattern`/`pierce_role` intel is collected), or state plainly that collected intel is advisory and does not gate.

4. **Major — cross-dependency example breaks the flagship chain (doc §"Scenario-authored data" vs `04` §"Worked example").** 04's worked example and hints depend on facts that 02's seeded data does not contain: 04 trusts "Jed Baker" (`j.baker@`) and hints "Re-read Jed's note on the company site about the Friday balance sheet," but 02's team page lists only Melanie Pierce (no Jed Baker staff entry) and no company-site note about a Friday balance sheet; 02's only Jed signal is the social post `pierce_trusts_jed`. The recon→phish chain the two docs are meant to demonstrate is not discoverable end to end. Fix: seed Jed Baker into 02's team page and add the Friday-balance-sheet note as a discoverable company-site fact, and align the `intel` ids across 02/03/04.

5. **Minor — reuse overstated (doc §"Engine wiring": "reuse their rendering where possible").** notes/text-file/examine are single static title+content panels; the browser needs an address bar, multi-page navigation, clickable links, a search box and a metadata panel (correctly listed as new work N1–N4). Fix: soften to "reuse the panel chrome and body-text/markdown rendering; the navigation shell is new."

6. **Minor — "breach-ish" conflation (doc §"Layers" item 4).** Labelling the search layer "breach-ish" while modelling theHarvester/Hunter/Recon-ng risks teaching that those tools return breach data. Breach lookups (HaveIBeenPwned-style) are a separate source (Recon-ng has a HIBP module; theHarvester does not do breach). Fix: relabel to "search / public-mention," or call breach-data lookups out as a distinct source with its own one-liner.

7. **Minor — metadata software value (doc §"Scenario-authored data", deck metadata).** `"software": "Office 365"` is loose; exiftool/doc properties expose an application string such as "Microsoft Word", and the vacancies page already uses "Office 365" as the tech-stack fact. Fix: set the deck's software to an application name (e.g. "Microsoft Excel") to avoid conflating document-metadata intel with tech-stack intel.

8. **Minor — section 3 not screen-by-screen (doc §"The loop").** BRIEF section 3 asks for numbered steps of what the player sees and does; 02 gives source "layers," not a step walk. Fix: add a short numbered loop (open browser → address bar/bookmarks → read page → "noted" flourish on intel → derive-pattern sub-task → return).

9. **Minor — set_global invocation mechanism (doc §"Engine wiring" N2).** `set_global` is normally driven by scenario action descriptors (flag-station `flagRewards`, object `triggerOnInteract`), not emitted ad hoc from inside a minigame's view logic. Fix: state that N2 calls `applyActions([{type:'set_global',...}])` (or patches `gameState.globalVariables` and emits `global_variable_changed:<key>` directly), so the mechanism is explicit.

## Verdict

Majors remain — concept, OSINT accuracy and engine citations are sound, but the doc must specify its own deterministic feedback (F1), fix the modal-overlay intel feed to 03 (F2), wire a concrete gate into 01/06 (F3), and make the 02↔04 example chain actually discoverable (F4) before it is clean.
